# RAG 系统架构

## 一句话理解

RAG（检索增强生成）通过外部知识库为 LLM 提供受控上下文，核心链路为"摄取 → 切分 → 嵌入索引 → 检索重排 → 上下文构造 → 生成引用"，解决 LLM 知识时效性、领域准确性和幻觉问题。

## 1. 概述

LLM 的知识来源于训练数据，存在三个固有局限：
- **时效性**：训练截止后的新知识模型不知道
- **领域深度**：专业领域知识不够精确
- **幻觉**：模型可能生成看似合理但事实错误的内容

RAG 通过在生成前检索外部知识，将相关文档注入提示上下文，让模型"看着参考资料回答"，从而：
- 提供最新、领域专属的知识
- 通过引用溯源增强可信度
- 减少幻觉，提高事实准确性
- 无需重新训练即可更新知识

RAG 解决的核心工程问题：
- **知识摄取**：如何高效处理多种格式的文档
- **切分策略**：如何切分文档使检索粒度最优
- **检索质量**：如何准确找到最相关的文档片段
- **上下文构造**：如何组织检索结果使模型有效利用
- **引用追溯**：如何标注答案来源以支持验证

### 3.2 文档切分策略

| 策略 | 描述 | 优势 | 劣势 |
|:---|:---|:---|:---|
| 固定长度 | 按 N 个 token 切分 | 实现简单 | 可能切断语义 |
| 句子分割 | 按句子边界切分 | 保持语义完整 | 长度不均匀 |
| 段落分割 | 按段落/标题切分 | 结构保持 | 段落过长 |
| 递归切分 | 优先段落→句子→token | 灵活自适应 | 实现复杂 |
| 语义切分 | 按 embedding 相似度切分 | 语义最优 | 计算成本高 |
| 父子切分 | 检索小块，返回大块 | 上下文完整 | 索引复杂 |

**Chunk 大小建议**：
- 通用场景：256-512 tokens
- 代码文档：按函数/类切分
- 长文档摘要：1024-2048 tokens

**Overlap（重叠）**：相邻 chunk 重叠 50-100 tokens，避免边界信息丢失。

### 3.3 嵌入模型

| 模型 | 维度 | 特点 | 适用场景 |
|:---|:---|:---|:---|
| OpenAI text-embedding-3-large | 3072 | 通用，API 服务 | 通用英文 |
| BGE-large-zh-v1.5 | 1024 | 中文优化 | 中文场景 |
| E5-mistral-7b | 4096 | 高质量，大模型 | 高精度需求 |
| bge-m3 | 1024 | 多语言，多功能 | 多语言场景 |
| GTE-large | 1024 | 阿里达摩院 | 中英文 |
| Cohere embed-v3 | 1024 | 商业 API | 企业场景 |

**选择考虑**：
- 语言匹配（中文/英文/多语言）
- 维度与存储成本
- 推理速度
- 是否需要本地部署

### 3.4 检索方法

| 方法 | 原理 | 优势 | 劣势 |
|:---|:---|:---|:---|
| 稠密检索 | 双编码器 + 向量相似度 | 语义匹配 | 精确匹配弱 |
| 稀疏检索 (BM25) | TF-IDF + 词袋 | 精确匹配，可解释 | 语义匹配弱 |
| 混合检索 | 稠密 + 稀疏 + RRF 融合 | 兼顾语义和精确 | 系统复杂 |
| 多向量检索 | ColBERT 式 token 级向量 | 细粒度匹配 | 存储成本高 |

**RRF（Reciprocal Rank Fusion）**：

$$\text{RRF}(d) = \sum_{r \in R} \frac{1}{k + \text{rank}_r(d)}$$

- $R$：多路检索结果集合
- $\text{rank}_r(d)$：文档 $d$ 在第 $r$ 路检索中的排名
- $k$：平滑参数（通常 60）

### 3.5 重排序（Reranking）

检索阶段用轻量模型快速获取 Top-K（如 50-100），重排序阶段用精确模型重新排序取 Top-N（如 5-10）：

| 重排模型 | 类型 | 特点 |
|:---|:---|:---|
| Cross-Encoder | 交互式 | Query-Doc 联合编码，精度最高 |
| ColBERT v2 | 延迟交互 | Token 级相似度，平衡精度和速度 |
| BGE-Reranker | Cross-Encoder | 中文优化 |
| Cohere Rerank | API 服务 | 商业服务，质量稳定 |

**为什么需要重排序**：
- 双编码器独立编码 Query 和 Doc，丢失交互信息
- Cross-Encoder 联合编码，精度高但慢
- 两阶段：先粗筛（快）→ 再精排（准）

## 4. 技术原理

### 4.1 查询改写

用户原始查询可能模糊、不完整或缺少关键词，需要改写以提升检索效果：

| 策略 | 描述 | 示例 |
|:---|:---|:---|
| Query Expansion | 扩展同义词和相关词 | "GPT" → "GPT, Generative Pre-trained Transformer, LLM" |
| Query Decomposition | 分解复杂问题 | "比较A和B" → "A的特点" + "B的特点" + "A vs B" |
| HyDE | 生成假设答案用于检索 | 用 LLM 生成假答案 → 用假答案嵌入检索 |
| Step-back Prompting | 抽象到更高层问题 | "X在Y条件下的表现" → "X的基本原理" |
| Multi-Query | 生成多个变体查询 | 一个问题生成 3-5 个不同表述 |

### 4.2 上下文构造

检索到文档后，如何组织成 LLM 的 prompt：

```text
[System]
你是一个知识助手。请根据以下参考文档回答问题。
如果参考文档中没有相关信息，请回答"根据现有资料无法回答"。
回答时请标注引用来源。

[Context]
[Doc 1] (来源: 产品手册.pdf, 第3页)
xxxxxxx...

[Doc 2] (来源: FAQ.md, 第12行)
yyyyyyy...

[Doc 3] (来源: 技术规范.pdf, 第8页)
zzzzzzz...

[Question]
用户的具体问题

[Instructions]
1. 仅基于参考文档回答
2. 每个事实陈述后标注 [Doc N]
3. 如果文档间有矛盾，指出矛盾
4. 如果信息不足，明确说明
```

**上下文管理技巧**：
- 按相关性排序（最重要的放最后，利用 recency bias）
- 控制总 token 数（通常 2000-4000 tokens）
- 去重和冲突检测
- 包含元数据（来源、时间、作者）

### 4.3 引用追溯

RAG 系统应支持答案到来源的映射：

```text
回答: "GPT-4 的上下文窗口为 128K tokens [Doc 1]，支持多模态输入 [Doc 2]。

[Doc 1] 来源: OpenAI 官方文档, 2024-03
[Doc 2] 来源: 技术白皮书, 2024-06
```

实现方式：
- **后处理映射**：生成后用 NLP 匹配答案片段到文档
- **结构化输出**：要求 LLM 输出 JSON 格式，每句标注引用
- **Token 级标注**：在生成过程中标注每个 token 的来源文档

### 4.4 GraphRAG

传统 RAG 基于向量相似度检索，难以处理多跳推理。GraphRAG 引入知识图谱：

```text
传统 RAG:
  Query → 向量检索 → 相关文档片段 → LLM 生成
  问题: 多跳推理（A→B→C）难以通过单次检索完成

GraphRAG:
  摄取阶段:
    文档 → 实体抽取 → 关系抽取 → 知识图谱构建

  查询阶段:
    Query → 实体链接 → 子图检索 → 图遍历 → 上下文构造 → LLM 生成
    优势: 支持多跳推理，提供结构化知识
```

## 5. RAG 评估

RAG 质量应分层评估：

| 评估层次 | 指标 | 说明 |
|:---|:---|:---|
| 检索质量 | Recall@K, Precision@K, MRR | 检索是否找到相关文档 |
| 上下文相关性 | Context Relevance | 检索结果与问题的相关度 |
| 答案事实性 | Faithfulness | 答案是否基于检索到的文档 |
| 答案相关性 | Answer Relevance | 答案是否回应了用户问题 |
| 端到端 | Task Success Rate | 完整任务是否成功 |
| 拒答准确率 | Refusal Accuracy | 无法回答时是否正确拒答 |

**RAGAS 框架**自动评估 RAG 系统的关键指标。

## 6. 优势与局限

### 6.1 优势

- **知识时效性**：更新知识库即可获取最新信息，无需重新训练
- **领域准确性**：注入领域专属知识，提高专业回答质量
- **减少幻觉**：基于检索到的真实文档生成，事实性更强
- **引用溯源**：答案可追溯到来源，增强可信度
- **成本效率**：相比微调，RAG 更新成本低、迭代快

### 6.2 局限与挑战

- **检索质量瓶颈**：检索不到相关文档时，RAG 无法提供正确答案
- **上下文窗口限制**：检索结果过多超出上下文窗口
- **延迟增加**：检索 + 重排序 + 生成增加了端到端延迟
- **文档质量依赖**：原始文档质量差直接影响 RAG 效果
- **多跳推理困难**：标准 RAG 难以处理需要跨文档推理的问题
- **长上下文替代**：128K+ 上下文模型可能替代部分 RAG 场景

## 7. 应用场景

| 场景 | RAG 变体 | 关键设计 |
|:---|:---|:---|
| 企业知识库 | 标准 RAG + 权限过滤 | 文档权限、版本控制 |
| 客服系统 | RAG + 对话历史 | 多轮上下文、意图路由 |
| 代码文档 | RAG + 代码切分 | 按函数/类切分 |
| 法律/医疗 | RAG + 高精度重排序 | Cross-Encoder, 引用必须 |
| 实时新闻 | RAG + 时效性排序 | 时间衰减、增量索引 |
| 多语言 | RAG + 跨语言检索 | 多语言嵌入模型 |

## 9. 前沿发展

- **Self-RAG**：模型自主判断是否需要检索，避免不必要的检索开销
- **Adaptive RAG**：根据问题复杂度动态调整检索策略
- **GraphRAG**：知识图谱增强的多跳推理检索
- **Agentic RAG**：Agent 控制检索-推理循环，支持多轮检索
- **多模态 RAG**：图文混合检索与生成
- **长上下文 vs RAG**：研究何时用长上下文替代 RAG，何时仍需 RAG
- **RAG 预训练**：在预训练阶段集成检索能力（如 RETRO, Atlas）
