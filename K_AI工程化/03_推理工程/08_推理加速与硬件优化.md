# 推理加速与硬件优化

## 一句话理解

LLM 推理是访存密集型任务（Arithmetic Intensity ≈ 1），硬件优化的核心是通过 FlashAttention 分块计算、算子融合、低精度运算和模型编译等手段，最大化利用 GPU 内存层次和 Tensor Core，将 GPU 利用率从 ~5% 提升至 > 50%。

## 1. 概述

硬件加速是指利用专为并行计算和低精度运算优化的硬件器件（GPU、TPU、NPU、FPGA 等）来加速 AI 模型的训练与推理。与通用 CPU 相比，专用加速器通过大规模并行计算单元、高带宽显存和定制化数据路径，实现了数量级的性能提升。

硬件加速解决的核心问题：
- **计算密度**：深度学习模型包含海量矩阵乘法，CPU 的少量 ALU 无法高效处理
- **内存带宽**：模型参数和激活值的访存开销远大于计算开销，需要高带宽存储
- **能效比**：数据中心推理成本中电力消耗占比高，专用芯片能效比 CPU 高 10-100 倍
- **规模化训练**：千亿参数模型的训练需要数百卡协同，硬件互联成为瓶颈

LLM 推理是**访存密集型**任务（Arithmetic Intensity ≈ 1），而训练则是**计算密集型**任务，两者对硬件的需求侧重点不同。

## 3. 核心概念

### 3.1 计算密度与 Roofline 模型

Roofline 模型描述硬件性能上限与计算访存比的关系：

$$\text{Performance} = \min\left(\text{Peak Compute}, \quad \text{Peak Bandwidth} \times \text{Arithmetic Intensity}\right)$$

其中 Arithmetic Intensity（AI）= FLOPs / Bytes。

- **计算上限**：硬件峰值算力（TFLOPS）
- **带宽上限**：显存带宽 × AI
- **平衡点**：$AI^* = \frac{\text{Peak Compute}}{\text{Peak Bandwidth}}$

以 A100 为例：FP16 峰值 312 TFLOPS，带宽 2.0 TB/s，$AI^* = 156$ FLOP/Byte。LLM 推理的 $AI \approx 1$，远低于平衡点，是访存密集型。

### 3.2 内存层次

AI 加速器的内存层次直接影响性能：

| 层级 | 容量 | 带宽 | 延迟 | 用途 |
|:---|:---|:---|:---|:---|
| 寄存器 | 256 KB/SM | ~20 TB/s | 1 cycle | 即时计算 |
| 共享内存 / L1 Cache | 192 KB/SM | ~10 TB/s | ~30 cycles | 块内数据复用 |
| L2 Cache | 40 MB | ~4 TB/s | ~200 cycles | 跨 SM 数据复用 |
| HBM（全局显存） | 80 GB | 2.0 TB/s | ~400 cycles | 模型权重与 KV-Cache |
| 主机内存 | 1-2 TB | ~100 GB/s | ~10 μs | CPU-GPU 数据传输 |

FlashAttention 的核心优化就是通过分块计算（tiling）最大化利用 SRAM，减少 HBM 访问。

### 3.3 Tensor Core

NVIDIA GPU 中的专用矩阵计算单元，执行矩阵乘加（MMA）操作：

```
D = A × B + C   (A: m×k, B: k×n, C: m×n)
```

- 一个 Tensor Core 在一个时钟周期内执行 $16 \times 8 \times 16$ 或类似维度的矩阵乘加
- A100 的 432 个 Tensor Core 提供 312 TFLOPS (FP16) 算力
- H100 的 Transformer Engine 自动选择 FP8/FP16 精度

### 3.4 数据格式与精度

| 格式 | 位宽 | 指数 | 尾数 | 动态范围 | 适用场景 |
|:---|:---|:---|:---|:---|:---|
| FP64 | 64 | 11 | 52 | ~10^308 | 科学计算 |
| FP32 | 32 | 8 | 23 | ~10^38 | 训练默认精度 |
| TF32 | 19 | 8 | 10 | ~10^38 | A100 训练加速 |
| BF16 | 16 | 8 | 7 | ~10^38 | LLM 训练标准 |
| FP16 | 16 | 5 | 10 | ~65504 | 训练/推理 |
| FP8 (E4M3) | 8 | 4 | 3 | ~448 | H100 推理加速 |
| FP8 (E5M2) | 8 | 5 | 2 | ~57344 | H100 训练加速 |
| INT8 | 8 | — | — | [-128, 127] | 量化推理 |
| INT4 | 4 | — | — | [-8, 7] | LLM 量化推理 |
| FP4 | 4 | 2 | 1 | ~6 | B200 极致推理 |

BF16 相比 FP16 的优势：保留 FP32 的 8 位指数，动态范围相同，训练不易溢出。

## 4. 技术原理

### 4.1 GPU 并行计算模型

CUDA 编程模型将计算组织为三级层次：

```
Grid → Block → Thread
  ↓       ↓       ↓
 GPU     SM    CUDA Core
```

- **Thread**：最小执行单元，拥有私有寄存器
- **Block**：线程块，映射到一个 SM（Streaming Multiprocessor），块内通过共享内存通信和 `__syncthreads()` 同步
- **Grid**：所有线程块的集合，在 GPU 上全局调度

**矩阵乘法的并行映射**（以 $C = A \times B$ 为例）：

```
每个 Block 计算输出矩阵 C 的一个 B×B 子块
  → 从全局内存加载 A 和 B 的对应子块到共享内存
  → 每个 Thread 计算子块内一个或多个元素
  → 使用共享内存进行块内规约
```

### 4.2 算子融合

将多个连续算子合并为一个自定义 kernel，减少中间结果的显存读写：

**未融合**（PyTorch 默认 eager 模式）：
```
Y₁ = MatMul(X, W₁)    → 写 HBM → 读 HBM
Y₂ = LayerNorm(Y₁)     → 写 HBM → 读 HBM
Y₃ = GELU(Y₂)          → 写 HBM → 读 HBM
Y₄ = MatMul(Y₃, W₂)    → 读 HBM
```
HBM 读写次数：6 次（3 写 + 3 读）

**融合后**：
```
Y₄ = FusedMLP(X, W₁, W₂)  → 仅读 X, W₁, W₂，仅写 Y₄
```
HBM 读写次数：4 次（3 读 + 1 写），中间结果保留在寄存器/共享内存中。

**融合策略**：
- **水平融合**：将多个独立算子合并（如多 Head 的 QKV 投影）
- **垂直融合**：将流水线上的连续算子合并（如 MatMul + Bias + GELU + LayerNorm）
- **模板化融合**：Triton、TVM 等工具通过模板自动生成融合 kernel

### 4.3 FlashAttention

FlashAttention 是最重要的硬件感知算法优化之一，通过分块计算避免实例化完整 $n \times n$ 注意力矩阵：

**标准 Attention**：
$$\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d}}\right) V$$

- 需要存储 $n \times n$ 的注意力矩阵，HBM 读写 $\mathcal{O}(n^2 d)$

**FlashAttention**：
1. 将 $Q, K, V$ 分为大小为 $B_r \times B_c$ 的块
2. 逐块计算 $S_{ij} = Q_i K_j^T / \sqrt{d_k}$
3. 使用**在线 softmax** 增量更新归一化因子
4. 累积输出 $O_i += P_{ij} V_j$

- HBM 访问降为 $\mathcal{O}(n^2 d / M)$（$M$ 为 SRAM 大小）
- 空间复杂度从 $\mathcal{O}(n^2)$ 降为 $\mathcal{O}(n)$
- 实测 2-4 倍加速

**在线 Softmax** 是关键创新——无需存储完整 softmax 矩阵，通过维护运行最大值 $m$ 和归一化因子 $l$ 增量更新：

$$\tilde{m}_{new} = \max(\tilde{m}_{old}, m_{block}), \quad \tilde{l}_{new} = e^{(\tilde{m}_{old} - \tilde{m}_{new})} \tilde{l}_{old} + e^{(m_{block} - \tilde{m}_{new})} l_{block}$$

### 4.4 KV-Cache 的硬件影响

LLM 自回归推理中，KV-Cache 随序列长度线性增长，是显存占用的主要来源：

$$\text{KV-Cache Size} = 2 \times n_{layers} \times n_{kv\_heads} \times d_{head} \times seq\_len \times \text{dtype\_size}$$

以 LLaMA-2-70B 为例（FP16）：
- 80 层 × 8 KV heads × 128 dim × 2 (K+V) × 2 bytes = 327,680 bytes/token ≈ 320 KB/token
- 序列长度 4096 时，KV-Cache 占用约 1.3 GB
- 批处理 64 个请求时，KV-Cache 占用约 83 GB，超过模型权重（140 GB 的 59%）

这意味着**显存容量而非算力是 LLM 推理的瓶颈**，推动了 PagedAttention、GQA/MQA、KV-Cache 量化等技术。

### 4.5 模型编译与图优化

模型编译器将高层计算图优化为硬件特定的高效代码：

```
PyTorch 模型 → 计算图 → 图优化 → 内核选择 → 代码生成 → 可执行引擎
```

**图优化**：
- 常量折叠：预计算可静态确定的子图
- 死代码消除：移除不影响输出的算子
- 算子融合：合并相邻算子
- 布局转换：优化数据排布（NHWC vs NCHW）

**主要编译器**：

| 编译器 | 来源 | 特点 |
|:---|:---|:---|
| XLA | Google | TensorFlow/JAX 编译后端，算子融合与内核自动调优 |
| TensorRT | NVIDIA | NVIDIA 推理优化引擎，支持 INT8/FP8 量化 |
| TVM | Apache | 跨平台编译器，AutoTVM 自动调优 |
| TorchInductor | Meta | PyTorch 2.0 编译后端，Triton kernel 生成 |
| Triton | OpenAI | Python DSL 编写 GPU kernel，无需 CUDA C |
| ONNX Runtime | Microsoft | 跨平台推理引擎，Execution Provider 架构 |

### 4.6 GPU 互联技术

多 GPU 训练需要高速数据交换，互联带宽直接决定并行效率：

| 互联技术 | 带宽 | 延迟 | 特点 |
|:---|:---|:---|:---|
| PCIe 4.0 x16 | 32 GB/s | ~6 μs | 通用标准，成本低 |
| PCIe 5.0 x16 | 64 GB/s | ~5 μs | 最新标准 |
| NVLink 3.0 | 50 GB/s/GPU | ~1.5 μs | V100 时代 |
| NVLink 4.0 | 100 GB/s/GPU | ~1 μs | A100，8 卡全互联 |
| NVLink 5.0 | 200 GB/s/GPU | ~0.8 μs | H100，72 卡互联 |
| NVSwitch | 900 GB/s 聚合 | — | DGX A100/H100 内全互联 |
| InfiniBand HDR | 200 Gb/s | ~1 μs | 节点间互联 |
| InfiniBand NDR | 400 Gb/s | ~0.5 μs | 最新节点间互联 |

**张量并行**对互联带宽要求最高（每层通信），适合 NVLink 互联的同节点 GPU；**流水线并行**通信量小但存在气泡，适合跨节点部署。

## 6. 关键优化技术

### 6.1 混合精度训练

利用低精度格式加速计算，同时保持训练稳定性：

```
FP32 Master Weights → FP16/BF16 Forward/Backward → FP32 Gradient Update
```

- **权重主副本**：FP32 存储，避免累积舍入误差
- **前向/反向**：FP16/BF16 计算，利用 Tensor Core 加速
- **梯度缩放**（FP16）：$\text{loss}_{scaled} = \text{loss} \times S$，防止小梯度下溢
- **BF16 无需缩放**：动态范围与 FP32 相同

### 6.2 FP8 训练与推理

H100 引入 FP8 支持，两种格式分别适用于不同场景：

- **E4M3**（4 位指数，3 位尾数）：精度更高，适合前向传播
- **E5M2**（5 位指数，2 位尾数）：动态范围更大，适合反向梯度

FP8 训练流程：
```
权重: E4M3 存储 → 前向计算 (E4M3) → 激活: E4M3
梯度: E5M2 反向计算 → 梯度缩放 → FP32 权重更新
```

### 6.3 推理量化部署

| 量化方案 | 精度 | 硬件支持 | 加速比 | 适用场景 |
|:---|:---|:---|:---|:---|
| FP16 | 16-bit | 所有 GPU | 1×（基准） | 通用推理 |
| BF16 | 16-bit | A100+ | 1× | 训练/推理一致 |
| INT8 (W8A8) | 8-bit | T4+ | 2× | 通用量化推理 |
| SmoothQuant | 8-bit | A100+ | 2× | 激活值异常值平滑 |
| GPTQ | 4-bit (权重) | A100+ | 3-4× | 后训练权重量化 |
| AWQ | 4-bit (权重) | A100+ | 3-4× | 激活感知量化 |
| FP8 | 8-bit | H100+ | 2× | H100 原生支持 |
| FP4 | 4-bit | B200 | 4-8× | B200 原生支持 |

### 6.4 推测解码的硬件利用

推测解码利用小模型生成候选 Token，大模型并行验证。从硬件角度：
- **减少串行访存**：大模型每次前向只读一次权重，验证 $k$ 个 Token
- **提高计算密度**：将 $AI \approx 1$ 的逐 Token 生成变为 $AI \approx k$ 的批量验证
- **硬件利用率提升**：大模型的 Tensor Core 利用率从 ~5% 提升到 ~30%

## 7. 优势与局限

### 7.1 优势

- **数量级加速**：GPU 相比 CPU 在矩阵运算上有 10-100 倍加速
- **能效比**：专用芯片单位功耗的计算量远高于通用 CPU
- **规模化**：多卡集群支持千亿参数模型训练
- **精度灵活**：从 FP64 到 FP4，支持精度-性能-显存的多维权衡
- **生态成熟**：CUDA 生态覆盖几乎所有深度学习框架和工具

### 7.2 局限与挑战

- **访存瓶颈**：LLM 推理是访存密集型，算力利用率低（~5%）
- **显存容量限制**：大模型权重 + KV-Cache 超出单卡显存
- **互联瓶颈**：跨节点通信延迟限制大规模并行效率
- **供应链风险**：高端 GPU 产能受限，地缘政治影响供应
- **能耗与散热**：H100 功耗 700W，B200 功耗 1000W，数据中心散热挑战大
- **成本高昂**：H100 单卡价格约 3 万美元，集群投入达数亿美元
- **编程复杂度**：手写 CUDA kernel 门槛高，依赖 Triton 等高级工具降低难度

## 11. Mega Kernel：从算子融合到整层融合（CS336 P18）

> CS336 P18 视角（Dan Fu, Stanford × Together AI）：理解推理和 GPU 内核的深层机制，就能在机器学习算法上实现全栈创新。

### 11.1 问题：Decode 阶段的 GPU 停摆

标准推理中，每个操作（LayerNorm、MatMul、Attention、Softmax...）各写一个 kernel，顺序执行：

```
kernel1: Norm     [████████] [______]    ← 启动/拆卸开销 + 等待
kernel2: MatMul            [████████] [______]
kernel3: Attn                        [████████] [______]
...
```

**停摆来源**：
- **Kernel 启动/拆卸开销**：每个 kernel 之间都有空隙（洪荒区域）
- **尾部效应**：一批输入中长短不一，必须等最长的处理完
- **间隙叠加**：跨多个 kernel 运行时，这些间隙逐层累积

H100 有 132 个 SM（B200 约 148 个），理想状态是所有 SM 持续工作，但传统方式下 GPU 总有大量停摆时间。

### 11.2 Mega Kernel：一个 kernel 搞定多个操作

**核心思想**：不单独为每个操作写 kernel，而是用一个 kernel 一次完成多个操作——类似 FlashAttention 的融合，但覆盖更广、更激进。

**关键设计转变**：把 GPU 看作一个庞大的分布式系统——有大量工作要处理，有些任务存在依赖关系，需要调度和分配以最大化利用率。

**具体融合示例（LLaMA 模型一层）**：
- 整个层合并为一个 kernel
- **QKV 投影 + RoPE 与 Attention 重叠**：在 QKV 计算完成前，就开始加载 KV Cache 进 Attention（Decode 阶段的带圆圈橙色条）
- **Attention 与 O 投影重叠**：在 Attention 运算结束前，O 投影就已开始加载权重
- 前一层的权重加载与当前层的注意力机制重叠

### 11.3 ThunderKittens：mega kernel 的编程框架

> 开源项目：[ThunderKittens](https://github.com/HazyResearch/ThunderKittens)（Stanford Hazy Research）

- 基于**指令的抽象**：每个子 kernel 独立写进各自文件
- 搭建大型虚拟化共享内存系统协调操作运行
- 属于编写 kernel 的底层库，可看作"更底层的 Triton"，对硬件的精细控制远超高级 DSL

### 11.4 性能表现

| 指标 | 数值 |
|:---|:---|
| Attention 推理 kernel 加速 | 30%-70% |
| H100 带宽利用率 | 72%（接近物理极限） |
| 对比顶尖引擎 | 显著更快 |

72% 带宽利用率意味着已接近 GPU 执行该操作的物理极限。

### 11.5 Mega Kernel 的代价与挑战

> CS336 P18 Q&A："代价是什么？"——"工程师的血汗。"

- **开发难度极高**：顶尖工程师一年可能只为一种硬件做出 2-3 个模型的 mega kernel
- **批大小敏感**：batch 1-16 还行，到 17 就可能推倒重来
- **可移植性差**：跨硬件需重写
- **编译器自动化尝试**：正在用编译器把部分工作自动化，但目前仍非常困难
- **跨多机通信**：初步研究发现 NCCL 调用也能融进 mega kernel；DeepSeek-V3 已为 MoE 推理层做了专门 mega kernel，部分通信也融了进去

> **核心启示**：如果能深度掌控 kernel、理解硬件，就能解锁全然不同的计算范式。这些细节只有深入推理底层摸索时才会发现。

### 11.6 硬件协同设计（CS336 P18 Q&A）

模型架构选择需匹配目标推理硬件：

| 硬件平台 | 量化格式选择 | 架构考量 |
|:---|:---|:---|
| NVIDIA GPU | NVFP4（专有 FP4 格式） | 用 NeMo-TRT 训练时需匹配 |
| AMD GPU | MXFP4 | 不同于 NVIDIA 的 FP4 格式 |
| Cerebras / Groq | 晶圆级 / LPU | 晶圆算内存 → 调整模型大小以容纳 KV Cache |
| 华为昇腾 | 国产芯片生态 | 中国模型的量化选择暗示在考虑华为新芯片 |

**选型原则**：内存是推理主要瓶颈，模型大小需在目标芯片上留出 KV Cache 余量；量化格式需匹配硬件原生支持。

## 12. 硬件感知优化的完整图景：六大技巧与矩阵乘法之谜（CS336 P5）

> CS336 P5 视角：GPU 计算吞吐量超指数增长，而内存带宽与互联带宽增长缓慢，这一"剪刀差"决定了现代 LLM 系统优化的主战场在内存——几乎所有 kernel 优化技巧都是"减少内存移动"这一主题的变奏。

### 12.1 六大技巧总览：一切为了减少内存移动

| # | 技巧 | 核心思想 | 备注 |
|:---|:---|:---|:---|
| 1 | 控制流平坦化 | SIMT 下 if 的两个分支都会执行（控制发散），错误一侧线程空等 | 用乘掩码代替分支，别写 if 写乘 0 |
| 2 | 低精度计算 | 位数减半 → 搬运字节减半 → 算术强度翻倍 | 见 §12.2 |
| 3 | 算子融合 | 多算子合并为一个 kernel，中间结果留在 SM 内 | 只付两次 HBM 带宽（工厂类比：原材料一次进厂、成品一次出厂） |
| 4 | 重计算 | 反向传播时现算激活值，用廉价计算换昂贵内存 | 见 §12.3 |
| 5 | 合并访问 | 对齐 DRAM 突发传输段（~128B），一次传输服务整个 warp | 见 §12.4 |
| 6 | 分块与填充 | 数据分块装入共享内存反复复用；尺寸对齐消除碎块 | 见 §12.5，对性能影响最大 |

融合、合并访问、分块是在**减少或复用**内存搬运；低精度与重计算则是**用其他资源（位数、计算）换内存**。

### 12.2 低精度的黑魔法：逐操作选精度与 MX 多缩放因子格式

低精度远不止"把位数砍半"：

- **逐操作选精度**：矩阵乘法中权重与激活先降精度（down-convert），但部分和累加以 FP32 全精度执行、结果以 FP32 输出；softmax/指数运算可能需要 FP32 或 BF16。哪些操作能降到什么精度，是多年经验性试错积累出的"黑魔法"
- **FP8 无统一标准**：E4M3（尾数多、精度高，适合前向）与 E5M2（指数多、动态范围大，适合反向梯度）并存——位数少到这个程度就不存在通用格式了
- **MXFP8 多缩放因子**：传统 FP8 用单个 FP32 缩放因子缩放整张矩阵，但指数位只有 4 位，数值极易溢出/下溢。MX 格式改为**每 32 个元素一组**，各组共享一个 E8M0 格式（纯指数、恒为 2 的幂）的缩放因子，适配矩阵内部的量级差异
- **转置陷阱**：分块缩放模式下，转置后的矩阵不再满足原缩放模式，转置前须整矩阵重量化。生产环境的解法颇为"疯狂"：**为每个量化矩阵保存两份副本**（原始与转置各量化一次），用显存换正确性
- **首尾层跳过量化**：第一层与输出层（主导损失的异类因素/outlier）量化后易出现不稳定与损失大幅上升
- **只量化矩阵乘法**：其他操作的量化收益不抵量化/反量化开销，实际 FP4 训练方案中所有量化都发生在矩阵乘法上
- **实际收益**：FP4 训练在矩阵乘法上节省约 20%-30%（不是 2×，量化本身有开销）；MXFP4 数值范围仅 ±6、每 16 个元素一个缩放因子——前沿实验室正朝 FP4 训练推进

### 12.3 重计算：用计算换内存的账本

以三层 sigmoid 堆叠为例（CS336 P5）：

- **朴素反向传播**：前向保存全部中间激活（S2、S1、输出），总计 **8 次**内存读写
- **重计算方案**：前向只存输入与输出；反向时由输入即时重算激活，内存访问降为 **5 次**

计算量不变，内存访问降为 5/8。在"计算极廉价、内存极昂贵"的现代 GPU 上，这笔账越来越划算。梯度检查点（activation checkpointing）即此思想的系统级应用；FlashAttention 更进一步，连 $O(n^2)$ 注意力矩阵都不保存（见 §12.6）。

### 12.4 合并访问的物理根源：DRAM 突发传输

- DRAM 存储单元呈网格排列，放大器按**列**激活：激活一列开销大，但激活后读取该列多个元素近乎免费 → 一次突发传输（burst）约 128 字节，段内数据不额外付费
- **合并访问（Coalescing）**：warp 内 32 线程的地址落在同一突发段 → 一次传输服务全部线程
- **行主序矩阵的陷阱**：沿行移动的线程访问是合并的；逐列读取时每个元素落在不同突发段——只想要一列，却付了整个矩阵的传输费。解法：**先转置再读取**，让每线程一次读取即拿到数据

### 12.5 分块、波量化与填充：矩阵乘法吞吐量之谜

**分块（Tiling）的数学**：

- 朴素 $N \times N$ 矩阵乘：每个输入元素从全局内存读 $N$ 次
- 分块大小 $T$：全局内存读取降为 $N/T$ 次，其余 $T$ 次访问发生在共享内存；$T = N$ 时全局内存只读一次
- 分块大小是最重要的调优参数：共享内存容量、矩阵尺寸、突发窗口宽度共同决定最优值。PyTorch 的 `max-autotune` 会花约 15 分钟对实际矩阵跑基准测试，扫描各种分块方案

**波量化（Wave Quantization）——矩阵尺寸之谜的答案**：

分块被调度到 SM 上执行（A100 有 108 个 SM）。以 256×128 分块、方阵为例：

```
矩阵 1792：分块数 = 7 × 14 = 98   ≤ 108 个 SM → 一个波次装下
矩阵 1793：分块数 = 8 × 15 = 120  > 108       → 需两个波次，第二波仅 12 个分块在忙
```

维度只 +1，吞吐量断崖式下跌——多出的分块让大部分 GPU 空转近一整个波次。这就是方阵尺寸-吞吐量曲线上周期性低谷的来源。

**整除性法则与填充（Padding）**：

- 矩阵维度应能被分块大小整除（理想为 2 的幂，最好能被 32 整除）；能被 16/32 整除时性能几乎无损失（突发窗口被填满），奇数维度吞吐量显著更差
- 维度偏移一个位置会让读取无法对齐突发段：读取一个分块实际触发约两个分块大小的传输量
- **经典案例**：Karpathy 在 nanoGPT 加速实验中将词表从 50257 填充到 50304（128 的倍数，仅 +0.09% 参数），获得约 **25% 加速**——填充使行边界与突发段对齐

### 12.6 FlashAttention：三块积木的组装

FlashAttention（数学细节见 §4.3）没有任何新发明，只是把基础技巧组装到极致：

1. **分块矩阵乘法**：Q、K、V 切块，$QK^T$ 的结果留在 SRAM 中计算指数——不落 HBM
2. **在线 softmax**：softmax 是全局操作，会把所有块耦合在一起而破坏分块。关键观察：softmax 可以**流式计算**——维护运行最大值 $m$（遇到更大值就重缩放修正）与指数累加和 $l$，逐块更新，最后统一除以 $l$；需保留的状态极小，可存于寄存器
3. **重计算**：连 $O(n^2)$ 的注意力矩阵都不存，反向传播时按块现算

FA2 的数据流可视化：虚线框（SRAM）内完成分块乘法、指数与 softmax 累积；蓝框（HBM）只存放 Q/K/V 与最终输出。

> **方法论启示**：几乎所有高效 GPU 实现都是这六个基础技巧的组合。与其背诵结论，不如掌握硬件模型——从 Roofline 到 DRAM 突发段，每一层"反直觉"现象（填充反而更快、维度 +1 反而暴跌、先转置反而更快）都能一步步推导出来。

## 13. GPU 编程模型的硬件约束：从编程正确性到性能现实（CS336 P6）

> CS336 P6 视角：GPU 的编程模型（Thread → Block → Grid）提供了一个干净的抽象——只要关注正确性，写到这一层就够了。但**性能**完全取决于硬件细节：Warp、Bank Conflict、Occupancy、Memory Coalescing 这些不在编程模型中、却决定实际吞吐的物理约束。

### 13.1 Warp：隐藏在 Thread Block 中的执行单元

Thread Block 是逻辑编程单元，但硬件以 **Warp**（32 个线程为一组）为执行单元：

- 同一 Warp 内的所有线程**必须执行相同指令**（SIMT 模型）
- **控制发散（Control Divergence）**：如果 Warp 内线程走了不同分支（if/else），则两个分支会被串行执行——这是性能杀手
- **Warp 调度器隐藏延迟**：SM 同时驻留多个 Warp，当某个 Warp 等待 HBM 数据（~100 cycles）时，调度器零开销切换到另一个 Warp 执行 Tensor Core 运算
  - 这与 CPU 的上下文切换不同——GPU 的 Warp 切换是**硬件级零开销**的

> **设计哲学**：GPU 不是通过缩短单次延迟来提升性能，而是通过**大量并发 Warp 来掩盖长延迟**。只要 SM 上有足够的 Warp 可调度，HBM 的访问延迟就可以被完全隐藏。

### 13.2 Occupancy：寄存器用量与并发能力的博弈

**Warp Occupancy** = 实际驻留 SM 的 Warp 数 / SM 最大 Warp 数

占用率并非越高越好——它受限于物理资源：

```
示例（B200）：
  每个 SM 最多 65536 个寄存器
  每个 SM 最多 64 个 Warp
  每个线程最多 255 个寄存器

  假设 Thread Block = 128 threads，每线程用 160 registers：
    Block 寄存器总量 = 128 × 160 = 20480
    SM 可同时运行 Block 数 = floor(65536 / 20480) = 3
    实际 Warp 数 = 3 × (128/32) = 12
    Occupancy = 12 / 64 = 18.75%
```

> **反直觉**：低 occupancy 未必是坏事。如果减少线程数但让每个线程做更多工作（**线程粗化 Thread Coarsening**），可能因为减少了调度开销和同步开销反而更快。Triton 编译器会自动做这个优化。

### 13.3 Bank Conflict：Shared Memory 的隐形串行化

Shared Memory 被划分为 32 个 Bank（每个 Bank 宽 4 字节），对应一个 Warp 的 32 个线程：

- **规则**：每个 Bank 每个时钟周期只能服务一个线程
- **Bank Conflict**：如果同一 Warp 的多个线程访问同一 Bank 的不同地址，访问会被串行化
  - 最坏情况：32 路冲突（所有线程访问同一 Bank 的不同地址）→ 32 倍串行化
- **解决方法**：**Swizzling**——重排 Shared Memory 的数据布局，使访问模式不再冲突

> **矩阵乘法的必然冲突**：做 $A \times B$ 时，需要读 A 的行和 B 的列。如果矩阵按行优先存储，读列就是跨步访问，极易引发 Bank Conflict。这就是为什么高性能 kernel 中经常需要 swizzling 或数据布局转换。

### 13.4 Memory Coalescing：HBM 访问的合并条件

与 Bank Conflict（针对 Shared Memory）不同，Memory Coalescing 针对 **HBM 访问**：

- Warp 中 32 个线程的 HBM 访问会被硬件尝试合并为**一次 128 字节的事务**（一个 Cache Line）
- **完全合并**：线程 0 访问地址 0，线程 1 访问地址 4，线程 2 访问地址 8……→ 一次事务取回所有数据
- **非合并访问**：如果线程按列访问（跨步 = 行长 × 4 字节），则每次访问都需要一个独立的 Cache Line → 32 次事务，带宽利用率仅 1/32

> **编程启示**：确保 Warp 内的线程访问**连续内存地址**是获得峰值 HBM 带宽的前提条件。这与 Bank Conflict 的约束方向一致但物理根源不同。

### 13.5 Wave Quantization 与 Tail Effect

Thread Block 被调度到物理 SM 上执行。如果 SM 数 = 148，启动 160 个 Block：

- 前 148 个 Block 占满所有 SM（一个 Wave）
- 剩余 12 个 Block 形成第二个 Wave——此时 148 个 SM 中有 136 个空闲
- **尾部效应（Tail Effect）**：最后一个 Wave 如果 Block 数远少于 SM 数，GPU 利用率骤降

> **实践建议**：让 Block 数量能被 SM 数量整除，或选择合适的 Block 大小使 Wave 数最小化。

## 14. 基准测试与性能分析方法论（CS336 P6）

### 14.1 成功的秘诀：测量 → 修改 → 再测量

```
基准测试（Benchmark） → 性能分析（Profile） → 修改代码 → 基准测试 → ...
```

> **核心原则**：永远先测量，再优化。不要凭直觉修改代码——Profiler 会告诉你时间花在哪里。

### 14.2 基准测试的正确姿势

| 要点 | 说明 | 代码示例 |
|:---|:---|:---|
| **预热（Warmup）** | 首次运行包含编译开销，必须排除 | `for _ in range(3): fn()` |
| **CUDA Events 计时** | CPU 时间不准确，必须用 GPU 事件 | `torch.cuda.synchronize()` |
| **多次运行取平均** | 单次结果有波动 | `times = [measure() for _ in range(10)]` |
| **同步屏障** | GPU 操作是异步的，必须等待完成 | `torch.cuda.synchronize()` |
| **维度扫描** | 观察耗时随输入规模的变化趋势 | 矩阵从 64 到 4096 |

```python
# 正确的基准测试模板
def benchmark(fn, warmup=3, iters=10):
    for _ in range(warmup):  # 预热：触发 JIT 编译
        fn()
    torch.cuda.synchronize()
    
    times = []
    for _ in range(iters):
        start = torch.cuda.Event(enable_timing=True)
        end = torch.cuda.Event(enable_timing=True)
        start.record()
        fn()
        end.record()
        torch.cuda.synchronize()  # 等待 GPU 完成
        times.append(start.elapsed_time(end))
    return sum(times) / len(times)
```

### 14.3 性能分析（Profiling）

基准测试告诉你**总耗时**，性能分析告诉你**时间花在哪**：

- **PyTorch Profiler**：内置工具，显示每个 kernel 的调用次数和耗时
- **NVIDIA Nsight Systems**：系统级时间线，显示 kernel 执行、内存传输、CPU/GPU 重叠
- **NVIDIA Nsight Compute**：单个 kernel 的深度分析（寄存器用量、Bank Conflict、Occupancy）

> **关键观察**（CS336 P6）：在 PyTorch 中 `a + b` 看起来是一个操作，但 Profiler 显示底层调用了 `cuda::binary_kernel`。`a @ b` 的 kernel 名称会**随矩阵维度变化**——PyTorch/cuBLAS 会根据形状自动选择不同的 kernel 实现（名称中编码了 tile 形状、精度、架构代号如 `sm_100` = Blackwell）。

> **方法论**：Profile 的价值不仅是找瓶颈。即使你不关心性能，Profiler 也能帮你理解高层代码**底层到底在做什么**——哪些操作被融合了、哪些没有、是否触发了预期的 kernel。
