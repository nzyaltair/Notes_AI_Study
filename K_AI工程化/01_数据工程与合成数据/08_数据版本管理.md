# 数据版本管理

## 一句话理解

数据版本管理使任一训练或评测结果都能回到确定的数据快照、变换代码和质量报告——以不可变 manifest、内容哈希和分区快照标识版本，以 Schema Contract 阻止破坏性变更，记录血缘追踪每个产物的来源。

## 1. 概述

数据版本管理是可复现性的基础。没有数据版本管理，训练实验无法复现，问题无法追溯，模型表现变化无法归因。

数据版本管理的核心目标：

- **可复现**：相同数据版本 + 相同代码 = 相同结果
- **可追溯**：任意模型版本可追溯到训练数据版本
- **可对比**：不同数据版本间可对比差异
- **可回滚**：数据问题发现后可回滚到之前版本

## 2. 最小可追溯单元

一个完整的数据版本应包含：

```text
数据版本 = 数据来源 + 原始快照 + 变换配置 + 标注版本 + 切分规则 + 质量报告
```

| 组成 | 说明 | 版本化内容 |
|:---|:---|:---|
| 数据来源 | 数据从哪里来 | source_url, source_version |
| 原始快照 | 采集的原始数据 | content_hash, snapshot_id |
| 变换配置 | 清洗/过滤规则 | cleaning_version, filter_config |
| 标注版本 | 标注指南和标注者 | guideline_version, annotators |
| 切分规则 | 训练/验证/测试切分 | split_method, split_seed |
| 质量报告 | 数据质量指标 | quality_metrics, eval_results |

## 3. 版本化策略

### 3.1 不可变 Manifest

每个数据版本对应一个不可变的 manifest 文件：

```json
{
  "dataset_id": "pretrain_corpus_v2.1.0",
  "version": "2.1.0",
  "created_at": "2024-01-15T10:00:00Z",
  "created_by": "data_pipeline_job_12345",
  "sources": [
    {"name": "commoncrawl", "version": "2023-50", "hash": "sha256:abc..."},
    {"name": "github", "version": "2024-01", "hash": "sha256:def..."}
  ],
  "transformations": [
    {"step": "parse", "config_version": "v1.0"},
    {"step": "clean", "config_version": "v2.1"},
    {"step": "filter", "config_version": "v1.3"},
    {"step": "dedup", "config_version": "v1.1", "threshold": 0.8}
  ],
  "statistics": {
    "total_documents": 1500000000,
    "total_tokens": 4500000000000,
    "languages": {"zh": 30, "en": 50, "other": 20}
  },
  "quality_report": "reports/quality_v2.1.0.json",
  "content_hash": "sha256:ghi..."
}
```

### 3.2 内容哈希

- **文件级哈希**：每个文件的 SHA-256 哈希
- **数据集级哈希**：所有文件哈希的聚合哈希
- **用途**：验证数据完整性、检测变更

### 3.3 分区快照

大规模数据不做全量复制，而是分区快照：

```text
dataset_v2.1.0/
├── partition_000/
│   ├── data.parquet
│   └── manifest.json
├── partition_001/
│   ├── data.parquet
│   └── manifest.json
└── manifest.json (顶层)
```

- **增量版本**：只记录变更的分区
- **共享分区**：未变更的分区跨版本共享
- **对象存储**：基于 S3/GCS 的存储后端

## 4. Schema Contract

### 4.1 什么是 Schema Contract

数据生产者与消费者之间的协议，定义：

- **字段名和类型**：每个字段的名称和数据类型
- **必填/可选**：哪些字段必须有值
- **值约束**：字段值的范围、格式、枚举
- **变更规则**：哪些变更是兼容的

### 4.2 兼容性级别

| 级别 | 说明 | 示例 |
|:---|:---|:---|
| 向后兼容 | 新版本可读旧数据 | 新增可选字段 |
| 向前兼容 | 旧版本可读新数据 | 旧代码忽略新字段 |
| 完全兼容 | 双向兼容 | 不改变字段 |
| 破坏性变更 | 不兼容 | 删除字段、改变类型 |

### 4.3 变更管理

```text
Schema 变更提案 → 影响评估 → 审批 → 版本升级 → 通知消费者
                    ↓
              破坏性变更 → 需迁移计划
```

## 5. 数据血缘

### 5.1 血缘追踪

记录每个数据产物的完整来源链：

```text
原始数据源 → 采集作业 → 清洗管线 → 过滤管线 → 去重管线 → 训练数据集
    ↓            ↓          ↓          ↓          ↓
  source     job_id     code_ver   code_ver   code_ver
  version    timestamp  params     params     params
```

### 5.2 血缘记录内容

| 维度 | 字段 |
|:---|:---|
| 数据来源 | 上游数据集 ID + 版本 |
| 处理作业 | 作业 ID、类型、时间 |
| 代码版本 | Git commit、配置文件版本 |
| 参数 | 处理参数（阈值、规则等） |
| 执行者 | 触发者（用户/调度系统） |

### 5.3 血缘查询

- **向前追溯**：这个数据集是怎么来的？
- **向后影响**：这个数据集被哪些下游使用？
- **影响分析**：原始数据变更会影响哪些下游？

## 6. 版本管理工具

### 6.1 工具对比

| 工具 | 类型 | 特点 | 适用场景 |
|:---|:---|:---|:---|
| DVC | Git 扩展 | 类似 Git LFS，数据版本控制 | 中小规模 |
| Delta Lake | 数据湖格式 | ACID 事务、时间旅行 | 大规模数据湖 |
| Apache Iceberg | 数据湖格式 | 快照隔离、分区演化 | 大规模数据湖 |
| Apache Hudi | 数据湖格式 | 增量更新、CDC | 流式数据 |
| LakeFS | Git-for-Data | 对象存储上的版本控制 | 大规模对象存储 |
| Pachyderm | 数据版本 | 管线 + 版本一体化 | ML 管线 |

### 6.2 Delta Lake 时间旅行

```sql
-- 查询历史版本
SELECT * FROM dataset VERSION AS OF 5;

-- 查询指定时间的数据
SELECT * FROM dataset TIMESTAMP AS OF '2024-01-01 00:00:00';

-- 查看版本历史
DESCRIBE HISTORY dataset;
```

### 6.3 DVC 工作流

```bash
# 添加数据到 DVC
dvc add data/raw/

# 推送到远程存储
dvc push

# 切换到历史版本
git checkout v1.0
dvc checkout  # 恢复对应数据

# 对比版本差异
dvc diff v1.0 v2.0
```

## 7. 与可复现性的关系

### 7.1 可复现性三角

```text
        可复现性
       /        \
  数据版本    代码版本
       \        /
      模型版本
```

- **数据版本**：训练用的确切数据集
- **代码版本**：训练代码和配置
- **模型版本**：训练产出的模型权重

三者缺一不可，共同构成可复现性基础。

### 7.2 实验记录

每次训练实验记录：

```json
{
  "experiment_id": "exp_001",
  "dataset_version": "pretrain_v2.1.0",
  "code_version": "git:abc1234",
  "model_version": "model_v0.3",
  "hyperparameters": {...},
  "results": {...}
}
```

## 8. 常见问题

- **全量复制**：每次版本更新全量复制数据，存储成本爆炸
- **血缘断裂**：管线某环节未记录血缘，追溯链中断
- **Schema 漂移**：字段类型/含义悄然变化，下游未感知
- **版本爆炸**：频繁更新导致版本过多，管理困难
- **数据不一致**：同一数据集在不同环境版本不一致
