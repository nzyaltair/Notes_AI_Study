# 持久化恢复与运行时不变式

## 一句话理解

可靠恢复依赖版本化的追加日志、明确的未知事件处理和持续执行的不变式检查；任何无法从日志重建的关键状态都会在刷新、fork 或崩溃恢复时失真。

---

## 持久化原则

会话后端负责将事件流落盘并回放；大文本可外溢为 spill 引用。未知且非 `ignorable` 的事件必须使重建失败，而非静默跳过。新事件必须兼顾旧日志兼容、投影逻辑与模型历史边界。

---

## SessionHeader：日志旁的元数据

每个会话的元数据与事件日志**分开**存储——格式版本、cwd、血统与 seed 边界是存储层关注点而非对话事件：

| 字段 | 说明 |
|---|---|
| `version` | 写入时的格式版本号（`SESSION_FORMAT_VERSION`）；后端在加载时拒绝其他版本 |
| `id` | 会话 ID |
| `createdAt` | Unix epoch 毫秒创建时间 |
| `cwd?` | 绝对工作目录（可选） |
| `parentSession?` | fork 来源的会话 ID（血统） |
| `seedLength?` | 继承事件数；让恢复与回放区分父历史与子工作 |
| `origin?` | 粗粒度产品分类（`'subagent'`）；是展示元数据，不证明可恢复性 |
| `delegationDepth?` | 委托深度（持久化）；0=顶层，子代理 = 父 depth+1；持久化使递归预算在重启后存活 |
| `agentPreset?` | 组装 agent 时的 preset id；持久化因为恢复时 preset 必须一致，否则历史与工具不匹配 |

> header 通过 `session.header` 附加到 `Session`；不进入 `SessionEventMap`，也不会到达 `deriveMessages()`。

---

## flush 检查点协议

`session/event` 是**同步**通知；持久化插件将事件复制到逐会话控制器，不阻塞生产方：

```
事件产生 → session/event 同步通知 → 持久化插件入队
                                      ↓
                              首个待处理事件开启固定批处理窗口
                              后续事件加入，不重置截止时间
                                      ↓
                              窗口到期 → 启动持久化批次
                              批次写入期间接纳的事件 → 下一批次
```

- **`session/flush`**：取消等待并排空至完全停稳（quiescence），循环用它作每个普通轮次之前的顺序与错误观察检查点；
- **后台写入被拒**：保留对应事件，暂停自动重试；新事件开启新固定窗口；显式 flush 立即重试；
- **错误报告**：通过 `agent/error` 和 logger；**绝不**把失败记录成已关闭轮次之后的会话事件；
- **dispose**：执行同样的最终排空；
- **配置最大值**：只限制有意的批处理等待，不限制事件循环调度或后端完成持久化的延迟。

---

## 崩溃恢复：保留被中断的轮次

后端重新加载在轮次中途崩溃的日志时，会发现已打开的 `turn/start` 却没有 `turn/end`：

- **不截断**：单个轮次可能非常庞大（许多步骤、大量工具输出），已持久追加的事件需保留；
- **合成关闭**：改用合成的 `turn/end { reason: { kind: 'interrupted' } }` 关闭遗留轮次；
- `interrupted` 是唯一一个**不由循环发出**的 `TurnEndReason`。

**修复仅适用于冷会话**：

| 场景 | 行为 |
|---|---|
| 冷会话（未活跃） | 写入合成 `turn/end { kind: 'interrupted' }` |
| 活跃 id | `load(id)` 等待权威内存快照完成持久化；轮次仍未闭合则拒绝，不写合成边界 |
| HMR 热重载 | 接管活跃前缀，不关闭正在进行的轮次 |

`SessionPersistence.inspect(id)` 构造不可变逻辑 Session，不发布，不写恢复内容；冷检查在内存中配平中断的轮次，保持撕裂的物理尾部不变。

## 格式拒绝策略

后端用 `SessionFormatUnsupportedError` 拒绝无法可靠解读的日志（与 `SessionPersistenceCorruptionError` 区分，数据未损坏）：

| 情形 | 行为 |
|---|---|
| `version` 比 `SESSION_FORMAT_VERSION` 新 | 提示方向："由更新的 harness 写入，请升级 harness 后打开" |
| `version` 比当前旧 | 提示本构建无升级路径 |
| 事件类型不在 `KNOWN_SESSION_EVENT_TYPES` 中，且无 `ignorable: true` | 拒绝（静默跳过可能改变日志其余部分的解读） |
| JSONL 后端 | 从原始 header 行拒绝外来版本，先于任何事件行解码 |
| SQLite 后端 | 先由 `SCHEMA_VERSION` pragma 把关整个文件结构 |

---

## SessionLocation：逐会话产物目标

`SessionPersistence.locate(meta)` 同步解析归后端所有的独立产物，不读取、创建或 flush：

| 后端 | 返回值 |
|---|---|
| JSONL | 项目/会话目录内 transcript 的绝对路径 |
| SQLite | `undefined`（各会话共享一个数据库） |

> 返回的路径是**位置提示**，不是授权或新鲜度保证：文件可能尚不存在，或尚未包含当前未 flush 轮次。

---

## 后端对比

| 特性 | JSONL 后端 | SQLite 后端 |
|---|---|---|
| 存储方式 | 每个会话一份仅追加逻辑 JSONL 日志 | 每个 `SessionEvent` 一行（共享 DB） |
| 物理编码 | 默认带 checksum 的连续 Zstandard frame；可配置原始行 | `(session_id, seq, type, time, data, source_event_seqs, surface_op)` |
| 原子写入 | 崩溃安全的原子写入 | 事务写入 |
| 逐会话工件 | 有（绝对路径） | 无（`locate` 返回 `undefined`） |
| seq 后缀读 | 全量解析后跳转（`readFrom`） | 直接 `seq >= fromSeq` 索引 |

## Spill 存储：工具超大文本的外溢机制

工具输出超过 `maxInlineBytes` 时，可通过 spill seam 持久化，将超长文本替换为模型可访问的引用：

### 三包结构

| 角色 | 包 | 说明 |
|---|---|---|
| Service Definition | `dsh-spill`（`ctx.spillStore`） | 抽象服务，定义 `saveText` 接口 |
| Service Provider | `dsh-spill-local` | 本地文件系统会话作用域私有文件 |
| Consumer | `dsh-spill-policy` | `tools/post-execute` 策略，触发 spill |

### 本地后端存储路径

写入 `<root>/session-<sha256(sessionId)>/<random>-<safeName>`：
- 根目录：已配置或延迟创建的私有（0700）目录；
- 写入模式：排他且仅所有者可访问（`open(path, 'wx', 0o600)`）——防止预先植入的符号链接重定向写入；
- `locator`：本地路径；`retrievalHint`：告知模型在该路径上用 `read` 或 `grep`。

### 最佳努力语义

spill 策略是**尽力而为**：保存失败时保留原始内联结果，不把成功的调用变成 `isError`。

### Fork 后的继承

fork 后的会话从种子日志**继承**已有的 spill 定位符；这些产物不被复制或重新取得所有权；fork 后产生的 spill 使用子会话 id。

## 运行时不变式：可执行的跨模块约束

### 角色定位

`ctx.invariants`（`InvariantRegistry`）是面向包自有运行时不变式检查的可配置注册表服务：
- **不是**一般异常日志，而是跨模块关系的可执行约束（事件顺序、配置一致性、模型可见内容可从日志重建等）；
- **不是** core seam，是 support 组的包；每个工作区包发布 `./invariant` 配套插件注册检查。

### 可检查项约定

不变式**只**断言：
- **权威事件流**（如 `turn/start` 必须先于 `step/start`）
- **可变数据关系**（如配置字段组合是否一致）

不变式**绝不**断言服务或方法是否存在（那是 Cordis 注入机制的职责）。

### 配置选项

```ts
interface Config {
  enabled?: boolean             // 全局开关，默认 true
  package_allowlist?: string[]  // JS 正则，匹配包名则准入；空=准入全部
  package_blocklist?: string[]  // JS 正则，匹配包名则排除；阻止列表优先
}
```

- 过滤器在**服务生命周期内固定**不变；
- 有效模式可不匹配任何当前已加载的包（HMR 友好）。

### 安装器 API

```ts
interface InvariantInstaller {
  (ctx: Context, fail: InvariantFailure): void | Promise<void>
  readonly inject?: Inject  // 安装器 fiber 可访问的服务
}

// fail(message) 抛出 InvariantError：
// - code: 'INVARIANT'
// - packageName: 注册包名
// - message: `invariant violated by "<package>": …`
```

- 被启用的安装器在专属子 Cordis fiber 中运行；
- 安装器失败→原子 dispose 子 fiber + 释放保留；
- 卸载任一侧（服务或配套插件）均移除监听器、trace 状态和保留项，允许 HMR 重载后再次注册同一名称。

### 配套插件约定

每个工作区包的 `./invariant` 配套插件：
- 有可检查项：注册检查；
- 无可检查项：导出空安装器，起始注释以 `No runtime invariant:` 开头，具体解释原因；
- `pnpm run verify-package-invariants` 机械验证：生成文件标记、无解释的空安装器、非空安装器遗漏报告器等均报错。

## 恢复设计清单

- 状态是否可由事件纯函数投影？
- 新事件是否 JSON 可序列化、有稳定语义并定义版本兼容？
- 错误发生在流式分片前后时，是否会错误派生消息或工具副作用？
- 无法恢复时，是否明确失败而非显示伪造状态？
- 新事件是否为 `ignorable`？若非纯信息型记录，不应设为 `ignorable`。
