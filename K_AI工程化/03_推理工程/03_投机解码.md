# 投机解码

## 一句话理解

投机解码（Speculative Decoding）利用小型 Draft 模型一次猜测多个 token，再由大型 Target 模型并行验证并接受有效前缀，在不损失精度的前提下将 LLM 自回归解码的访存效率提升 2-3 倍。

## 1. 概述

LLM 逐 token 解码的根本瓶颈是**访存密集型**：每生成一个 token，需要从 HBM 读取全部模型权重，但只执行极少量计算（Arithmetic Intensity ≈ 1 FLOP/Byte）。GPU 的计算单元利用率仅 5-15%。

投机解码的核心洞察：

- **串行 → 批量**：Draft 模型一次生成 $k$ 个候选 token，Target 模型用一次前向传播并行验证全部 $k$ 个 token
- **计算量基本不变**：验证 $k$ 个 token 的计算量 ≈ 生成 1 个 token 的 $k+1$ 倍（多出的 $k$ 倍用于验证），但权重只读一次
- **Arithmetic Intensity 提升**：从 $AI \approx 1$ 提升至 $AI \approx k$，GPU 利用率从 ~5% 提升至 ~30%
- **无损精度**：通过拒绝采样（rejection sampling）保证输出分布与 Target 模型完全一致
- **利用生成/验证的不对称性**：验证（并行检查一批 token）远比生成（逐 token 自回归）便宜——Draft 模型虽小且同样访存受限，但逐 token 生成开销可忽略；Target 模型虽贵，但一次前向并行验证 $k$ 个 token，恰好落回它擅长的计算受限区间

投机解码的收益取决于三个因素：
1. **接受率（Acceptance Rate）**：Draft 模型猜测的正确比例
2. **Draft 成本**：Draft 模型的推理开销
3. **批处理状态**：在线服务中 Draft 和 Target 的调度竞争

## 3. 核心概念

### 3.1 基本流程

```
输入: "The capital of France is"

Step 1: Draft 模型生成 k 个候选 token
  Draft → "Paris" "," "which" "is"     (k=4)

Step 2: Target 模型并行验证
  Target 一次性处理: "The capital of France is Paris , which is"
  得到每个位置的概率分布: P₁, P₂, P₃, P₄, P₅

Step 3: 逐 token 接受/拒绝
  Position 1: Draft="Paris",  Target 分布也指向 "Paris"  → 接受 ✓
  Position 2: Draft=",",      Target 分布指向 ","         → 接受 ✓
  Position 3: Draft="which",  Target 分布指向 "a"         → 拒绝 ✗
  → 从 Target 分布采样 "a" 作为修正
  → 停止，最终接受 2 个 token + 1 个修正 token = 3 个 token

Step 4: 回到 Step 1，从 "The capital of France is Paris , a" 继续
```

### 3.2 接受率与加速比

**理论加速比**：假设每个位置接受概率为 $\alpha$（接受率），Draft 长度为 $k$：

$$E[\text{接受 token 数}] = \frac{1 - \alpha^{k+1}}{1 - \alpha}$$

理想情况下（Draft 成本可忽略），加速比 ≈ $E[\text{接受 token 数}]$。

**典型数据**：

| 接受率 α | Draft 长度 k | 期望接受数 | 理论加速比 |
|:---|:---|:---|:---|
| 0.5 | 4 | 1.94 | 1.94× |
| 0.7 | 4 | 2.78 | 2.78× |
| 0.8 | 4 | 3.36 | 3.36× |
| 0.7 | 8 | 3.42 | 3.42× |
| 0.8 | 8 | 4.45 | 4.45× |

**实际加速比**通常低于理论值，原因：
- Draft 模型有计算成本（约占 Target 的 5-15%）
- 批处理大时 Target 模型已接近算力瓶颈，投机解码收益减小
- 拒绝后需要重新调用 Draft 模型

**Draft 长度 $k$ 的权衡**：$k$ 太小，浪费 Target 模型的并行验证能力（没吃满批量）；$k$ 太大，被拒绝的概率随长度累积（$\alpha^k$ 衰减），尾部 token 大概率白算。多数场景的平衡点在 **3~4 个**。

### 3.3 拒绝采样（Rejection Sampling）

保证输出分布与 Target 模型完全一致的关键机制：

对于 Draft 提议的 token $x$，在位置 $i$：
- Draft 概率：$q(x)$
- Target 概率：$p(x)$

**接受规则**：
$$\text{accept}(x) = \begin{cases} 1 & \text{if } r < \min(1, \frac{p(x)}{q(x)}) \quad (r \sim U[0,1]) \\ 0 & \text{otherwise} \end{cases}$$

**拒绝后的修正**：
$$p_{\text{residual}}(x) = \frac{\max(0, p(x) - q(x))}{\sum_{x'} \max(0, p(x') - q(x'))}$$

从残余分布 $p_{\text{residual}}$ 中采样一个 token 作为修正。这保证了最终输出分布与直接使用 Target 模型完全一致。

## 4. 技术原理

### 4.1 Draft 模型选择策略

| 方案 | Draft 来源 | 优势 | 劣势 | 代表方法 |
|:---|:---|:---|:---|:---|
| 独立小模型 | 另一个小 LLM | 灵活选择 | 需要加载两套模型 | Speculative Decoding (原版) |
| 同模型浅层 | Target 模型的前几层 | 无额外模型 | 接受率较低 | LayerSkip, Self-Speculative |
| 附加 Head | Target 模型上的预测头 | 共享权重 | 需训练 Head | Medusa, Hydra |
| Hidden State 预测 | Target 的隐状态 | 接受率最高 | 需训练适配层 | EAGLE, EAGLE-2 |
| 无 Draft | Jacobi 迭代 | 无需训练 | 收益不稳定 | Lookahead Decoding |

**Draft 模型从哪来**：理想 Draft 应尽量贴近 Target 的输出分布——通常直接从 Target 蒸馏得到；此外，压缩实验（剪枝、减 KV Cache）中精度不达标的模型，恰好可以降级作为 Draft 模型二次利用。

### 4.2 Medusa：多头并行预测

Medusa 在 Target 模型的最后一个隐藏层上添加 $k$ 个额外的预测头：

```
Target 模型最后一层 Hidden State h
  ├── LM Head → tokenₜ (正常预测)
  ├── Medusa Head 1 → tokenₜ₊₁ (预测下一个 token)
  ├── Medusa Head 2 → tokenₜ₊₂ (预测下下个 token)
  ├── Medusa Head 3 → tokenₜ₊₃
  └── Medusa Head 4 → tokenₜ₊₄
```

- 每个 Head 独立预测未来第 $i$ 个 token
- 每个 Head 返回 Top-$n$ 候选（通常 $n=2\sim4$），形成候选树
- Target 模型一次前向传播验证整棵树
- 无需独立 Draft 模型，训练成本低

**候选树展开**（每个 Head Top-2）：
```
                    tokenₜ
                   /       \
            Head1: A         B
                 / \       / \
          Head2: C   D     E   F
               / \  / \   / \  / \
          Head3:G H I J   K L  M N
```
Tree Attention 并行验证所有路径，选择最长接受前缀。

### 4.3 EAGLE：Hidden State 层面预测

EAGLE 的核心改进是在 **Hidden State 层面**而非 token 层面进行预测：

```
传统方案:  token → Draft Model → token → Target 验证
                     ↑ 词表层面

EAGLE:     hidden_state → 轻量 transformer → hidden_state → Target 验证
                           ↑ 特征层面，信息更丰富
```

- Draft 结构：1 层 Transformer + 特征融合层
- 输入：Target 模型的 Hidden State + Embedding
- 输出：预测的下一个 Hidden State → 通过 LM Head 得到 token
- **接受率远高于 token 级预测**（Hidden State 携带更多语义信息）
- EAGLE-2 进一步引入动态 Draft 树结构和上下文感知

### 4.4 Tree Attention

验证多个候选 token 时，需要高效的并行验证机制：

```
序列: [已知 tokens] [Draft 候选 tree]

Tree Attention 的 Causal Mask:
  - 已知 tokens 互相可见（标准 causal）
  - 候选 token 只能看到其路径上的前驱
  - 不同分支的候选 token 互相不可见

示例:
  路径1: [known] → A → C → G
  路径2: [known] → A → C → H
  路径3: [known] → A → D → I
  路径4: [known] → B → E → K

  G 只能看到 [known, A, C]
  H 只能看到 [known, A, C]
  I 只能看到 [known, A, D]
  K 只能看到 [known, B, E]
```

一次前向传播即可验证所有候选路径，选出最长接受前缀。

### 4.5 批处理场景下的投机解码

在线服务中，投机解码的收益与批处理大小存在权衡：

| 批处理大小 | GPU 利用率 | 投机解码收益 | 原因 |
|:---|:---|:---|:---|
| 1-8（低并发） | ~5-15% | 显著（2-3x） | 访存瓶颈，验证提高 AI |
| 8-32（中并发） | ~20-40% | 中等（1.3-1.8x） | 部分计算瓶颈 |
| 32-128（高并发） | ~50-80% | 微弱甚至负面 | 已接近计算瓶颈，Draft 反而增加计算 |

**调度策略**：
- 低并发时启用投机解码，高并发时禁用
- 根据实时批处理大小动态调整 Draft 长度 $k$
- 将 Draft 模型部署在独立 GPU 或 CPU 上，避免与 Target 竞争显存

## 5. 优势与局限

### 5.1 优势

- **无损精度**：拒绝采样保证输出分布与 Target 模型完全一致
- **降低延迟**：单请求场景延迟降低 2-3x
- **提升 GPU 利用率**：将串行解码变为批量验证，AI 从 ~1 提升至 ~k
- **无需重训 Target**：现有模型可直接使用（部分方案需训练 Draft）

### 5.2 局限与挑战

- **接受率依赖**：Draft 模型与 Target 差距大时接受率低，收益有限
- **高并发失效**：大批处理下 Target 模型已饱和，投机解码反而增加开销
- **Draft 训练成本**：EAGLE/Medusa 需在 Target 模型上训练额外参数
- **内存开销**：Draft 模型和 Tree Attention 的 KV Cache 增加显存占用
- **实现复杂度**：Tree Attention、动态调度、接受率监控增加系统复杂度
- **输出长度不确定**：每次迭代接受的 token 数不确定，影响延迟预测

## 6. 应用场景

| 场景 | 推荐方案 | 原因 |
|:---|:---|:---|
| 低延迟在线对话 | EAGLE-2 + 动态 Draft | 接受率高，单请求加速最大 |
| 代码补全 | Medusa + 长 Draft | 代码结构规律性强，接受率高 |
| 本地推理（单用户） | Lookahead Decoding | 无需训练 Draft，CPU 友好 |
| 高并发 API 服务 | 自适应投机解码 | 低并发启用，高并发禁用 |
| 结构化生成 | SGLang + Speculative | 共享前缀 + 批量验证 |
| 翻译/摘要 | 独立小模型 Draft | 输出较确定，接受率高 |

## 8. 前沿发展

- **大模型 Draft**：使用 7B 模型为 70B 模型做 Draft，接受率极高但 Draft 成本也高
- **上下文感知 Draft**：根据输入类型动态调整 Draft 策略（代码 vs 对话 vs 翻译）
- **多级投机**：Draft 模型本身也使用投机解码，形成级联
- **推测解码 + 投机解码**：结合推测执行和投机解码，进一步并行化
- **Draft 模型蒸馏**：从 Target 模型蒸馏专门的 Draft 模型，提高接受率
- **硬件级支持**：GPU 厂商探索 tree attention 的硬件加速指令
