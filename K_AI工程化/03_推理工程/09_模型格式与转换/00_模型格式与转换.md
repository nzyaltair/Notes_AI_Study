# 模型格式与转换

## 一句话理解

模型格式是训练框架与推理引擎之间的契约：ONNX 提供跨框架交换标准，TensorRT Engine 提供 NVIDIA 极致优化，GGUF 服务本地量化部署，SafeTensors 提供安全加载——选对格式并做好转换验证，是模型从训练到生产的必经之路。

## 1. 概述

模型训练通常在 PyTorch/TensorFlow 中完成，但生产推理可能运行在 TensorRT、ONNX Runtime、llama.cpp 等不同引擎上。训练框架与推理引擎之间的**格式鸿沟**需要通过模型格式转换来桥接。

模型格式转换解决的核心问题：

- **框架解耦**：训练用 PyTorch，推理用 TensorRT/ONNX Runtime，格式转换打破绑定
- **硬件适配**：不同格式针对不同硬件优化（NVIDIA/Intel/ARM/NPU）
- **部署优化**：推理格式通常包含图优化和量化信息
- **安全加载**：避免 pickle 反序列化的代码执行风险

转换后必须验证：
1. **数值一致性**：输出 logits 误差 < 1e-3
2. **功能等价**：相同输入产生相同输出
3. **性能达标**：推理延迟/吞吐满足要求
4. **动态 Shape**：支持变长输入（LLM 的核心需求）

## 3. 核心概念

### 3.1 主要模型格式对比

| 格式 | 全称 | 提出者 | 特点 | 适用场景 |
|:---|:---|:---|:---|:---|
| **ONNX** | Open Neural Network Exchange | Microsoft/Meta | 跨框架交换标准 | 跨框架部署 |
| **TensorRT Engine** | — | NVIDIA | NVIDIA 极致优化 | NVIDIA 生产推理 |
| **GGUF** | GPT-Generated Unified Format | llama.cpp | 量化+元数据，单文件 | 本地/边缘部署 |
| **SafeTensors** | — | HuggingFace | 安全加载，无 pickle | 模型存储/分发 |
| **OpenVINO IR** | Intermediate Representation | Intel | Intel 硬件优化 | Intel CPU/iGPU/VPU |
| **Core ML** | — | Apple | Apple 生态 | iOS/macOS 部署 |
| **TFLite** | TensorFlow Lite | Google | 移动端轻量 | Android/IoT |
| **MLIR** | Multi-Level IR | LLVM | 多级中间表示 | 编译器研究 |

### 3.2 PyTorch 原生格式

| 格式 | 说明 | 安全性 |
|:---|:---|:---|
| `.pt` / `.pth` | pickle 序列化 | ⚠️ 可执行任意代码 |
| `.bin` | 同上 | ⚠️ 可执行任意代码 |
| `safetensors` | 安全二进制格式 | ✓ 无代码执行 |

**SafeTensors 的优势**：
- 零拷贝加载：内存映射直接使用，无需反序列化
- 安全：纯数据格式，无代码执行风险
- 快速：加载速度比 pickle 快 10-100 倍
- 跨语言：Rust/C++/Python/JS 均可读取

### 3.3 ONNX 格式

ONNX 定义了一组标准算子（Operators）和计算图（Graph）表示：

```
ONNX 模型结构:
┌─────────────────────────────┐
│ ModelProto                  │
│ ├── ir_version: 7           │
│ ├── opset_imports: [17]     │  ← 算子集版本
│ ├── metadata_props          │  ← 自定义元数据
│ └── GraphProto              │
│     ├── name: "model"       │
│     ├── inputs: [X]         │  ← 输入描述
│     ├── outputs: [Y]        │  ← 输出描述
│     ├── initializers: [W]   │  ← 权重常量
│     └── nodes:              │  ← 计算图节点
│         ├── Conv(X, W) → C  │
│         ├── BatchNorm(C) → N│
│         ├── Relu(N) → R     │
│         └── MaxPool(R) → Y  │
└─────────────────────────────┘
```

**ONNX 的核心价值**：
- **互操作性**：PyTorch → ONNX → TensorRT / ONNX Runtime / OpenVINO
- **算子标准化**：统一算子语义，消除框架差异
- **图优化**：ONNX 格式支持图级优化（融合、常量折叠）
- **动态维度**：支持动态 batch 和序列长度

**ONNX 的局限**：
- 自定义算子需注册为 Contrib Op
- 部分 Transformer 操作（如 KV Cache）支持较晚
- 模型大小可能膨胀（未压缩的权重）

### 3.4 GGUF 格式

详见 [[07_SGLang与llama_cpp#4.1 GGUF 格式|SGLang 与 llama.cpp - GGUF 格式]]。

GGUF 的核心特点：
- 单文件存储（权重 + 元数据 + 量化参数）
- 支持多种量化精度（Q2_K ~ Q8_0）
- 向后兼容新量化方案
- 模型分发友好（HuggingFace 直接下载）

### 3.5 TensorRT Engine

TensorRT Engine 是 NVIDIA 特定的二进制格式：

**特点**：
- **不可移植**：绑定 GPU 架构 + CUDA 版本 + TRT 版本
- **已优化**：包含图优化和 kernel 选择结果
- **不可读**：二进制格式，无法反序列化为模型
- **高性能**：运行时零解释开销

**构建流程**：
```
PyTorch 模型 (.pt)
    ↓  torch.onnx.export()
ONNX 模型 (.onnx)
    ↓  trtexec / trtllm-build
TensorRT Engine (.engine)
    ↓  部署到 Triton / 自定义服务
生产推理
```

## 4. 转换流程与验证

### 4.1 PyTorch → ONNX

```python
import torch

model = MyModel().eval()
dummy_input = torch.randn(1, 3, 224, 224)

torch.onnx.export(
    model,
    dummy_input,
    "model.onnx",
    input_names=["input"],
    output_names=["output"],
    dynamic_axes={
        "input": {0: "batch", 2: "height", 3: "width"},
        "output": {0: "batch"}
    },
    opset_version=17
)
```

**LLM 转换的特殊处理**：
- KV Cache 需作为输入/输出显式建模
- 动态序列长度需设置 dynamic_axes
- 自定义算子（如 RoPE）需注册 ONNX Custom Operator
- 注意力机制需导出为标准 Attention 算子

### 4.2 ONNX → TensorRT

```bash
# 方式 1：命令行工具
trtexec --onnx=model.onnx \
  --saveEngine=model.engine \
  --fp16 \
  --minShapes=input:1x3x224x224 \
  --optShapes=input:8x3x224x224 \
  --maxShapes=input:32x3x224x224

# 方式 2：Python API
import tensorrt as trt

builder = trt.Builder(TRT_LOGGER)
network = builder.create_network(1 << int(trt.NetworkDefinitionCreationFlag.EXPLICIT_BATCH))
parser = trt.OnnxParser(network, TRT_LOGGER)

with open("model.onnx", "rb") as f:
    parser.parse(f.read())

config = builder.create_builder_config()
config.set_flag(trt.BuilderFlag.FP16)
engine = builder.build_engine(network, config)
```

### 4.3 HuggingFace → GGUF

```bash
# 使用 llama.cpp 的转换脚本
python3 convert.py \
  --outfile model.gguf \
  --outtype f16 \    # 或 q4_k_m, q8_0
  ./huggingface-model/
```

### 4.4 HuggingFace → TensorRT-LLM

```bash
# Step 1: 转换为 TRT-LLM checkpoint
python3 convert_checkpoint.py \
  --model_dir ./hf-model \
  --output_dir ./ckpt \
  --tp_size 1

# Step 2: 构建引擎
trtllm-build \
  --checkpoint_dir ./ckpt \
  --output_dir ./engine \
  --gemm_plugin fp8 \
  --max_batch_size 256
```

### 4.5 转换验证

**验证层次**：

| 层次 | 验证内容 | 方法 | 通过标准 |
|:---|:---|:---|:---|
| 数值验证 | 输出一致性 | 相同输入对比 logits | 最大误差 < 1e-3 |
| 功能验证 | 端到端行为 | 相同输入对比生成结果 | 语义等价 |
| 性能验证 | 延迟/吞吐 | 基准测试 | 满足 SLA |
| 动态验证 | 变长输入 | 多种 batch/seq_len | 全部通过 |
| 边界验证 | 极端输入 | 空、超长、特殊字符 | 不崩溃 |

**验证脚本示例**：
```python
import torch
import onnxruntime as ort

# 原始模型
model.eval()
with torch.no_grad():
    pt_output = model(dummy_input)

# ONNX 模型
session = ort.InferenceSession("model.onnx")
onnx_output = session.run(None, {"input": dummy_input.numpy()})

# 对比
max_diff = np.max(np.abs(pt_output.numpy() - onnx_output[0]))
assert max_diff < 1e-3, f"数值差异过大: {max_diff}"
print(f"验证通过，最大差异: {max_diff}")
```

## 5. 常见问题与解决

### 5.1 算子不兼容

| 问题 | 原因 | 解决方案 |
|:---|:---|:---|
| ONNX 不支持某算子 | 自定义算子未注册 | 注册 Custom Op 或用等价算子替换 |
| TensorRT 不支持某算子 | ONNX 算子 TRT 未实现 | 编写 Plugin 或使用 TRT-LLM |
| 精度不匹配 | FP32 → FP16 截断 | 检查敏感层，保持 FP32 |

### 5.2 动态 Shape

LLM 推理需要动态 batch 和序列长度：

```python
# ONNX 导出时指定动态维度
dynamic_axes = {
    "input_ids": {0: "batch", 1: "seq_len"},
    "attention_mask": {0: "batch", 1: "seq_len"},
    "output": {0: "batch", 1: "seq_len"}
}

# TensorRT 构建时指定 shape 范围
profile.set_shape("input", min=(1,1), opt=(8,128), max=(32,2048))
```

### 5.3 Tokenizer 和前后处理

模型格式转换通常只转换模型本身，Tokenizer 和前后处理需单独处理：

```
完整推理管线:
  原始文本 → Tokenizer → input_ids → 模型 → output_ids → Detokenizer → 结果文本
                         ↑                      ↑
                    需要单独部署            格式转换覆盖范围
```

- Tokenizer 应与训练时完全一致（版本、配置）
- 前后处理（如 BPE 合并、特殊 token）需打包到部署工件
- 建议使用 HuggingFace tokenizers 库的 JSON 格式

- **MLIR 统一 IR**：多级中间表示试图统一 ONNX/TensorRT/TVM 的中间格式

- **自动格式选择**：根据目标硬件自动选择最优格式和量化方案
