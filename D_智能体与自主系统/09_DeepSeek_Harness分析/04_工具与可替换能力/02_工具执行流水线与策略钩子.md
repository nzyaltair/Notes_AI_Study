# 工具执行流水线与策略钩子

## 一句话理解

工具调用先被记录，再依序经过前置策略、不可绕过守卫、执行包装、结果变换与最终观察；不同扩展点的可修改权限不同，不能用错误的钩子实现安全规则。

## 完整执行链

```text
[模型输出 tool-call 块]
  │
  ▼
tool/call（会话事件，在执行前记录）
  │
  ├─► UI pending card（presentCall(args)）
  │
  ▼
tools/pre-execute（waterfall）
  ├─► allow → 单调 guards
  ├─► deny  → 直接进入 post-execute（跳过 execute 和 toolBody）
  └─► ask   → ctx.approval 一次性审批
              ├─► allowed-once → 单调 guards
              └─► rejected/cancelled/unavailable → deny 路径
                                                         │
单调 guards（按注册顺序）                                 │
  ├─► allow → tools/execute（waterfall）                 │
  └─► deny  → post-execute ◄────────────────────────────┘

tools/execute（waterfall，围绕实际分发）
  └─► 执行 Tool.execute() 体
        │
        ├─► fs 工具：fs/write-intent、fs/edit-intent waterfall
        ├─► 工具自有会话事件（todo/write、fs/observed、hook/invoked 等）
        └─► 返回 → tools/execute 包装层收到结果

tools/post-execute（waterfall）
  └─► 可 accept、block、replace 结果，或附加 additionalContexts

Registry 外层归一化（pipeline/result 快照；抛出 → isError）

ToolDefinition.finalizeContent（同步仅内容不变式，已固定在快照上）

tools/result（同步通知，不可变的权威结果）
  │
  ▼
tool/result（会话事件，单个面向模型的结果）
  │
  ├─► UI completed card（presentResult(args, result)）
  └─► 批次全部 settle 后：active-batch additionalContexts FIFO
      作为 user/message 注入（在 tool/result 事件之后）
```

## 各扩展点职责与边界

| 扩展点 | 可以做什么 | 不能做什么 |
|---|---|---|
| `tools/pre-execute` waterfall | 允许/拒绝/要求审批；修改执行上下文 | 不保证单调性（后续插件可重新允许） |
| 单调 guards（`ctx.tools.guard()`） | 不可被后续插件放宽的最终拒绝；所有者策略 | 不能 allow（只能 deny 或 abstain） |
| `tools/execute` waterfall | 包裹实际分发：超时/重试/指标；替换 `exec.signal` | 替换内容：结果只能通过 post-execute 改写 |
| `tools/post-execute` waterfall | 接受、阻断、替换结果、追加 `additionalContexts` | 无法修改已记录的 `tool/call` 事件 |
| `tools/result` | 观察不可变的权威结果；指标/审计/捕获 | 不能再改写结果 |

## 单调 Guard 语义

`ctx.tools.guard()` 注册单调守卫，其拒绝决策具有 identity-protected 特性：被注册守卫拒绝的调用无法在同一执行链中被任何后续插件重新允许。这与 `pre-execute` waterfall 不同——waterfall 是可重排的策略层，而 guard 是不可撤销的终端策略。

使用场景：不可变的所有者策略（如工作区边界检查）应注册为 guard，而不是 `pre-execute` 监听器，以防策略被意外降级。

## `finalizeContent` 的角色

`ToolDefinition.finalizeContent` 是工具定义自己拥有的最后一道同步内容检查，在 registry 外层归一化（快照固定）之后运行。因为快照已经固定，它只能做内容层面的不变式——例如确保 result 的某个字段符合 schema——不能改变结果的整体形状。若 `finalizeContent` 抛出，异常在此处规范化，而不是继续向上传播。

## Code Mode 子调用的特殊路径

`run_code`（Code Mode 保留工具）及其子调用都走同一流水线，但有以下区别：
- 子调用携带父级 token，表明调用者身份；
- 子调用记录 `tool/code-dispatch` 会话事件而非普通 `tool/call`；
- 子调用的拒绝被呈现为具有约束力的驳回；
- 子调用**省略** `additionalContexts`，保持调用与结果在日志中相邻，不被额外上下文打断。

## 文件系统的额外边界

文件系统读后编辑检查在 `tool-fs` 内部通过 `fs/write-intent`、`fs/edit-intent` waterfall 实现。通用的前置/后置 waterfall 和 `ctx.approval` 处理询问，而不得重新排序的所有者文件系统策略仍作为已注册的 guard。二者互不替代：文件工具内的 `fs/*` 事件检查文件效果，通用钩子检查工具调用策略。
