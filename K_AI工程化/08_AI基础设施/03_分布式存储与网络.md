# 分布式存储与网络

## 一句话理解

分布式存储解决 AI 工作负载中海量训练数据、模型权重和检查点的高效读写问题，高速网络（InfiniBand/RoCE）解决多节点间低延迟高带宽通信问题，二者共同构成 GPU 集群的"血管系统"——存储是数据供给，网络是节点协同。

## 1. AI 工作负载的存储需求

### 1.1 存储场景分析

| 场景 | 规模 | I/O 模式 | 延迟要求 | 吞吐要求 |
|:---|:---|:---|:---|:---|
| **训练数据集** | TB-PB | 顺序读，多客户端并发 | 中 | 极高 |
| **模型检查点** | GB-TB | 周期性批量写，偶发读 | 低（不阻塞训练） | 高写入 |
| **推理模型权重** | GB-百GB | 一次性加载到显存 | 低 | 中 |
| **特征/向量库** | GB-TB | 随机读 | 极低（在线） | 中 |
| **日志/指标** | GB-TB/天 | 持续追加写 | 低 | 中 |
| **用户数据/RAG** | GB-TB | 混合读写 | 中 | 中 |

### 1.2 存储性能瓶颈

```text
AI 训练中的存储瓶颈：

场景 1：数据加载瓶颈
┌──────────┐     ┌──────────┐     ┌──────────┐
│ Storage  │ →→→ │  CPU     │ →→→ │   GPU    │
│ 10 GB/s  │     │ Decode   │     │ 80% idle │
└──────────┘     └──────────┘     └──────────┘
问题：GPU 空等数据，利用率 < 50%

场景 2：检查点写入瓶颈
┌──────────┐     ┌──────────┐
│   GPU    │ →→→ │ Storage  │
│ 等待...  │     │ 5 GB/s   │
└──────────┘     └──────────┘
问题：70B 模型检查点 280GB，写入需 56 秒

场景 3：模型权重分发
┌──────────┐     ┌──────────┐
│ Storage  │ →→→ │ 8× GPU   │
│ 1 GB/s   │     │ 等待加载 │
└──────────┘     └──────────┘
问题：70B 模型权重 140GB，分发需 140 秒
```

## 2. 存储方案

### 2.1 存储类型对比

| 方案 | 延迟 | 吞吐 | 容量 | 成本 | 适用场景 |
|:---|:---|:---|:---|:---|:---|
| **本地 NVMe SSD** | < 0.1ms | 极高 (>20 GB/s) | TB 级 | 高 | 热数据/检查点缓存 |
| **分布式文件系统** | 1-5ms | 高 (>50 GB/s) | PB 级 | 中 | 训练数据/共享存储 |
| **对象存储 (S3)** | 10-100ms | 中 | EB 级 | 低 | 数据归档/模型仓库 |
| **块存储 (EBS)** | 1-10ms | 中 | TB 级 | 中 | 云上持久卷 |
| **内存文件系统** | < 0.01ms | 极高 | GB 级 | 极高 | 临时数据/元数据 |

### 2.2 分布式文件系统

| 系统 | 特点 | 适用场景 |
|:---|:---|:---|
| **Lustre** | HPC 标杆，极高吞吐 | 大规模训练集群 |
| **GPFS/Spectrum Scale** | IBM，企业级，强一致 | 企业 AI 平台 |
| **CephFS** | 开源，POSIX 兼容 | 通用分布式存储 |
| **JuiceFS** | 云原生，元数据分离 | 云上 AI 平台 |
| **Alluxio** | 内存级缓存层 | 加速远端存储 |
| **WekaFS** | NVMe 原生，低延迟 | 高性能 AI 存储 |

### 2.3 存储分层架构

```text
AI 存储分层架构：

层 1：GPU 显存（HBM）
├── 当前训练 batch / KV Cache
├── 延迟：~1 ns
└── 容量：80-192 GB

层 2：节点内存 (DRAM)
├── 数据预取缓冲 / 页缓存
├── 延迟：~100 ns
└── 容量：512 GB - 2 TB

层 3：本地 NVMe SSD
├── 热检查点 / 数据缓存
├── 延迟：~0.1 ms
└── 容量：4-30 TB

层 4：分布式文件系统
├── 训练数据集 / 共享检查点
├── 延迟：1-5 ms
└── 容量：PB 级

层 5：对象存储
├── 数据归档 / 模型仓库
├── 延迟：10-100 ms
└── 容量：EB 级

数据流动策略：
├── 训练数据：对象存储 → 分布式 FS → 本地缓存 → 内存 → GPU
├── 检查点：GPU → 内存 → 本地 NVMe → 分布式 FS → 对象存储
└── 模型权重：对象存储 → 本地 NVMe → GPU 显存
```

### 2.4 训练数据加载优化

```text
数据加载优化策略：

1. 预取 (Prefetch)
   ├── DataLoader(num_workers=8, prefetch_factor=4)
   ├── 后台进程提前解码下一批数据
   └── CPU 解码与 GPU 计算重叠

2. 数据本地化
   ├── 首次访问时缓存到本地 NVMe
   ├── 后续从本地读取，避免网络 I/O
   └── 使用 Alluxio/JuiceFS 自动缓存

3. 格式优化
   ├── 小文件 → 合并为 WebDataset/TFRecord
   ├── 压缩格式：Parquet/Arrow
   ├── 避免过多小文件（inode 瓶颈）
   └── 列式存储减少读取量

4. 数据分片
   ├── 按 worker 分片，避免重复读取
   ├── 全局 shuffle vs 局部 shuffle
   └── 流式读取避免全量加载

5. 编码优化
   ├── 图像：JPEG → 解码 → resize
   ├── 文本：tokenize 预处理并缓存
   └── 视频：抽帧预处理并存储
```

## 3. 检查点存储

### 3.1 检查点写入策略

```text
检查点写入优化：

策略 1：异步检查点
├── 训练继续，后台线程写入
├── 内存中保留副本直到写入完成
├── 风险：内存占用增加
└── 工具：PyTorch Distributed Checkpoint

策略 2：分布式检查点
├── 每个 worker 并行写自己的分片
├── 避免单点聚合的带宽瓶颈
├── N 个 worker → N 倍写入带宽
└── 工具：torch.distributed.checkpoint

策略 3：增量检查点
├── 只保存变化的参数
├── 配合周期性全量检查点
├── 减少写入数据量
└── 适用：微调/增量训练

策略 4：压缩检查点
├── FP32 → BF16/FP16 保存
├── 量化压缩（INT8）
├── 减少存储和 I/O
└── 风险：精度损失
```

### 3.2 检查点存储分层

```text
检查点存储生命周期：

活跃检查点（当前训练）
├── 存储：本地 NVMe
├── 延迟要求：< 10 秒写入
├── 保留：最近 2-3 个
└── 操作：故障恢复

近期检查点（回滚用）
├── 存储：分布式文件系统
├── 延迟要求：< 60 秒读取
├── 保留：最近 10-20 个
└── 操作：回滚到任意版本

历史检查点（归档）
├── 存储：对象存储（S3）
├── 延迟要求：分钟级读取
├── 保留：关键里程碑
└── 操作：复现/审计

检查点管理策略：
├── 保存频率：每 1000 步 / 每 30 分钟
├── 清理策略：保留最近 N 个 + 里程碑
├── 校验：写入后计算 hash 验证完整性
├── 压缩：BF16 保存 + gzip
└── 加密：敏感数据加密存储
```

## 4. 高速网络

### 4.1 网络技术对比

| 技术 | 带宽 | 延迟 | 成本 | 适用场景 |
|:---|:---|:---|:---|:---|
| **InfiniBand HDR** | 200 Gb/s | ~1μs | 高 | 大规模训练集群 |
| **InfiniBand NDR** | 400 Gb/s | ~1μs | 极高 | 万卡训练集群 |
| **InfiniBand XDR** | 800 Gb/s | ~0.5μs | 极高 | 下一代集群 |
| **RoCE v2** | 400 Gb/s | ~2μs | 中 | 成本敏感的 AI 集群 |
| **普通以太网** | 100-400 Gb/s | ~10μs | 低 | 推理/管理网络 |
| **CXL** | 64 GB/s | ~0.5μs | 中 | CPU-GPU 内存共享 |

### 4.2 RDMA（远程直接内存访问）

```text
RDMA 工作原理：

传统网络：
  App A → Kernel → NIC → Network → NIC → Kernel → App B
  （多次内存拷贝 + 系统调用，延迟高）

RDMA：
  App A → NIC → Network → NIC → App B
  （绕过内核，零拷贝，延迟 < 2μs）

RDMA 优势：
├── 零拷贝：数据直接在用户空间和网卡间传输
├── 内核绕过：无系统调用开销
├── CPU 卸载：不占用 CPU 资源
├── 低延迟：< 2μs（vs TCP ~50μs）
└── 高吞吐：充分利用链路带宽

RDMA 实现：
├── InfiniBand：原生 RDMA 支持
├── RoCE v2：在以太网上实现 RDMA
├── iWARP：TCP 上的 RDMA（较少使用）
└── NVLink：GPU 间专用互联（非网络 RDMA）
```

### 4.3 网络拓扑设计

```text
大规模 AI 集群网络拓扑：

Fat-Tree / Spine-Leaf 拓扑：

         ┌───┐ ┌───┐ ┌───┐ ┌───┐
         │S0 │ │S1 │ │S2 │ │S3 │     ← Spine 层
         └─┬─┘ └─┬─┘ └─┬─┘ └─┬─┘
           │     │     │     │
     ┌─────┴─────┴─────┴─────┴─────┐
     │        Oversubscription       │
     └─────┬─────┬─────┬─────┬─────┘
           │     │     │     │
      ┌────┴┐ ┌──┴──┐ ┌─┴──┐ ┌┴────┐
      │ L0 │ │ L1  │ │ L2 │ │ L3  │   ← Leaf 层
      └─┬──┘ └─┬──┘ └─┬──┘ └─┬───┘
        │      │      │      │
     ┌──┴──┐┌──┴──┐┌──┴──┐┌──┴──┐
     │节点0││节点1││节点2││节点3│    ← 计算节点
     │8 GPU││8 GPU││8 GPU││8 GPU│
     └─────┘└─────┘└─────┘└─────┘

设计原则：
├── 无阻塞（Non-blocking）：1:1 收敛比
├── 冗余路径：多路径 ECMP 负载均衡
├── 故障域隔离：单交换机故障不影响全集群
├── 拓扑感知调度：同 Leaf 优先
└── 万卡集群需 3 层 Fat-Tree
```

### 4.4 网络拥塞控制

```text
RDMA 网络拥塞控制：

问题：大规模 AllReduce 可能导致网络拥塞
├── 多个节点同时发送 → 交换机缓冲区溢出
├── PFC（Priority Flow Control）暂停发送
├── 拥塞扩散 → 整体性能下降

解决方案：
├── ECN（Explicit Congestion Notification）
│   └── 交换机标记拥塞包 → 接收方通知发送方降速
│
├── DCQCN（RoCE 拥塞控制）
│   ├── 基于 ECN 的速率控制
│   ├── 发送方根据 ECN 反馈调整速率
│   └── NVIDIA RoCE 默认算法
│
├── HPCC（High Precision Congestion Control）
│   ├── 基于 INT（In-band Network Telemetry）
│   ├── 精确感知链路负载
│   └── 更稳定的吞吐
│
├── PFC（Priority Flow Control）
│   ├── 链路级流量控制
│   ├── 接收方缓冲快满时暂停发送方
│   └── 避免丢包但可能导致 HoL blocking
│
└── 流量隔离
    ├── 训练流量 vs 存储流量分离
    ├── RDMA 流量 vs 管理流量分离
    └── 使用 VLAN / PFC 优先级
```

## 5. 存储与网络的容量规划

### 5.1 训练集群容量规划

```text
训练集群容量规划公式：

存储容量：
├── 训练数据：数据集大小 × 2（含副本）
├── 检查点：模型大小 × 保留数量 × worker 数
│   └── 例：70B FP16 (140GB) × 10 保留 × 8 worker = 11.2 TB
├── 日志/指标：日志率 × 训练时长
└── 总存储 = 数据 + 检查点 + 日志 + 20% 余量

存储吞吐：
├── 数据加载吞吐 ≥ GPU 消费吞吐
│   └── 例：8 × H100 × batch=32 × 3 channels × 224² × 4 bytes × 4 steps/s
│       = 8 × 32 × 3 × 50176 × 4 × 4 ≈ 1.5 GB/s（图像训练）
├── 检查点写入吞吐 ≥ 模型大小 / 检查间隔
│   └── 例：140GB / 1800s = 78 MB/s（可接受）
└── 分布式 FS 聚合吞吐 ≥ 所有节点需求之和

网络带宽：
├── AllReduce 通信量 ≈ 模型参数量 × 2（梯度同步）
├── 每 step AllReduce 时间 ≤ 计算时间的 30%
├── 每节点网络带宽 ≥ 2 × 参数量 × 元素大小 / 步骤通信预算
│   └── 例：70B FP16 = 140GB
│       步骤通信预算 0.3s → 带宽需求 ≈ 93 GB/s（需多路并行）
└── 实际带宽 = InfiniBand 带宽 × 利用率（通常 70-90%）
```

### 5.2 推理集群容量规划

```text
推理集群容量规划：

模型权重存储：
├── 每模型版本大小 × 版本数
├── 多副本缓存（每节点缓存一份）
└── 分发带宽 ≥ 模型大小 / 冷启动 SLA

KV Cache 存储：
├── 每请求 KV Cache = 2 × 层数 × 隐藏维度 × 序列长度 × 元素大小
├── 并发请求数 × 每请求 KV Cache = 总 KV Cache 需求
└── 总显存需求 = 模型权重 + KV Cache + 激活值

网络带宽：
├── 每请求输入/输出 token × 并发请求数
├── 推理流量通常远小于训练通信
└── 100 Gb/s 足够大部分推理场景
```

## 6. 监控与运维

### 6.1 存储监控

| 指标 | 说明 | 告警阈值 |
|:---|:---|:---|
| **IOPS** | 每秒 I/O 操作数 | 接近上限 |
| **吞吐** | MB/s 读写速率 | < 需求的 80% |
