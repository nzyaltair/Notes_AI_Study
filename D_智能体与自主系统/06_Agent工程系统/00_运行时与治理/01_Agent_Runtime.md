# Agent Runtime

## 一句话理解

Agent Runtime 是承载 Agent 自主循环执行的基础设施层，负责状态持久化、任务调度、事件驱动与错误恢复，使长时间运行的任务不必依赖单次超长模型调用完成。

## 概述

当 Agent 从演示原型走向生产系统，"一次 LLM 调用循环到底"的简单实现会在长任务、并发请求、故障恢复等场景下迅速失效。Agent Runtime 借鉴操作系统和分布式系统的成熟经验（进程调度、检查点、事件驱动），为 Agent Loop 提供可靠的执行环境。它是 [[../00_Agent工程系统_综述|Agent 工程系统]]中承上启下的一层：向上支撑 [[../01_Agent系统与框架|Agent 系统与框架]]的业务逻辑，向下依赖 [[../01_工具调用与MCP/00_工具调用与MCP_综述|工具调用]]与状态存储等基础组件。

## 发展历史

早期 Agent 实现（如 2023 年的 AutoGPT）将整个任务循环放在一个 Python 进程的 while 循环中，状态保存在内存变量里，一旦进程崩溃或需要人工介入，整个任务上下文丢失，必须从头重来。这种"脆性"促使框架引入检查点机制：LangGraph（2024）率先将 Agent 循环建模为显式状态图，配合 `Checkpointer` 将每一步状态持久化到数据库，支持任意节点的暂停、恢复与时间旅行调试。随着 Agent 任务时长从分钟级延伸到小时甚至天级（如 Devin 式软件工程 Agent），Runtime 逐渐发展为独立的工程学科，吸收了 Actor 模型（Hewitt, 1973）、工作流引擎（Temporal、Airflow）和事件驱动架构的设计思想。

## 核心概念

- **Agent Loop**：Agent 执行任务的核心循环，即"观察-决策-行动-观察"的迭代过程
- **检查点（Checkpoint）**：将 Agent 在某一时刻的完整状态（对话历史、中间变量、待执行步骤）持久化，支持故障后从断点恢复而非重新开始
- **状态（State）**：需区分会话状态（多轮对话上下文）、任务状态（当前子任务进度）、环境状态（外部世界的最新观测）与记忆状态（长期知识），四者生命周期和存储策略不同
- **事件驱动执行**：Runtime 不是持续轮询，而是由工具回调完成、外部系统通知、人工输入等事件触发下一步执行，节省资源并支持异步长任务
- **幂等性（Idempotency）**：同一操作重复执行（如网络重试导致的工具重复调用）不应产生副作用叠加，是故障恢复安全性的基础

## 技术原理

### Agent Loop 的标准流程

```text
加载检查点 → 观察/状态估计 → 决策或规划 → 策略与权限检查
→ 调用工具 → 记录事件/Trace → 校验结果 → 完成、重试、重规划或暂停
```

每一步都可能因为超时、工具失败、权限拒绝而中断；Runtime 的职责是让中断后的恢复代价最小化，而不是让 Agent 逻辑本身处理所有异常分支。

### 状态管理的分层设计

| 状态类型 | 生命周期 | 典型存储 |
|:---|:---|:---|
| 会话状态 | 单次对话/任务期间 | 内存 / Redis |
| 任务状态 | 任务开始到结束 | 数据库（可查询、可恢复） |
| 环境状态 | 随外部世界变化 | 实时查询，不缓存或短期缓存 |
| 记忆状态 | 跨任务持久 | 向量数据库 / 知识图谱，见 [[../../05_记忆与持续学习/02_记忆架构与检索|记忆架构与检索]] |

### 调度与并发

Runtime 需处理任务队列、优先级排序、并发限流、超时熔断与资源配额（如单任务最大工具调用次数、最大 Token 预算），防止单个失控任务耗尽系统资源。

## 关键方法与模型

| 能力 | 要求 | 代表实现 |
|:---|:---|:---|
| 状态管理 | 区分会话、任务、环境与记忆状态；支持检查点和幂等恢复 | LangGraph Checkpointer |
| 调度 | 处理队列、优先级、并发、超时、取消与资源配额 | Temporal、Celery |
| 事件驱动 | 工具回调、长任务完成、人工输入和外部变更可触发继续执行 | 消息队列（Kafka/RabbitMQ） |
| 工具运行 | 输入校验、最小权限、隔离、重试和补偿事务 | 沙箱容器、Function Calling 校验层 |
| 人机协作 | 对风险动作、歧义和低置信度提供升级与接管接口 | Human-in-the-loop 中断节点 |

## 优势与局限

**优势**：将容错、恢复、调度等通用问题从 Agent 业务逻辑中剥离，使开发者可以专注任务本身；支持长程任务的可靠执行与可观测性。

**局限**：引入 Runtime 层增加了系统复杂度和延迟开销；状态序列化/反序列化在涉及复杂对象（如打开的文件句柄、数据库连接）时需要额外设计；跨 Runtime 的状态迁移和版本兼容是持续的工程挑战。

## 应用场景

- 长程编程 Agent（如 Devin 类系统）需要在数小时任务中支持暂停与人工审查
- 客服/业务流程 Agent 需要在等待外部系统响应（如支付回调）时释放资源，事件触发后继续
- 多步审批流程 Agent 需要在关键节点暂停等待人工批准

## 与其他技术关系

- 工作流适用于路径预定义的任务；Runtime 需同时支持工作流场景和状态驱动的动态分支，两者互补而非互斥，参见 [[../02_工作流与编排/00_Agent工作流|Agent工作流]]
- 所有可恢复的决策都应持久化，而不是仅保留在模型上下文窗口中——上下文窗口会被压缩或截断，不是可靠的状态存储
- 与 [[02_监控_评测与安全治理|监控、评测与安全治理]]共同构成生产级 Agent 系统的运行时基座

## 前沿发展

- **分布式 Agent Runtime**：支持多 Agent 跨机器协作调度，如 AutoGen 的分布式运行时
- **时间旅行调试**：LangGraph 等支持回放任意历史检查点，便于定位失败根因
- **Agent 操作系统化**：AIOS 等研究尝试将 Agent 调度提升为操作系统级原语，统一管理多 Agent 的资源竞争

## 常见问题

**Q: 为什么不能简单地把整个对话历史放进上下文窗口作为"状态"？**
上下文窗口有长度上限，且模型提供商可能在压缩/截断历史时丢失关键信息；此外上下文窗口不具备持久化、可查询、可回滚的特性，无法支撑故障恢复。

**Q: 检查点越频繁越好吗？**
不是。检查点写入有 I/O 开销，过于频繁会拖慢执行；通常在关键决策点（工具调用前后、子任务完成时）设置检查点即可。
