# 编译器栈与中间表示

## 一句话理解

AI 编译器（XLA/TensorRT/MLIR）将高层模型定义（PyTorch/TensorFlow）转换为底层硬件可执行代码，是连接 AI 框架和 GPU/NPU 的关键桥梁。

## 核心概念

### 编译器层级

```
模型定义 (PyTorch/TF/JAX)
    ↓
高级IR (Graph IR / HLO / TorchDynamo)
    ↓
中级IR (MLIR / StableHLO)
    ↓
低级IR (LLVM IR / PTX)
    ↓
硬件指令
```

### 主流编译器

| 编译器 | 来源 | 输入 | 输出 | 特点 |
|-------|------|------|------|------|
| XLA | Google | HLO | 设备代码 | JIT/AOT，优化 HLO 图 |
| TensorRT | NVIDIA | ONNX/TF | TensorRT Engine | 算子融合、INT8/FP8 量化 |
| MLIR | LLVM | 多种方言 | LLVM IR | 多级 IR，可扩展 |
| TorchDynamo | PyTorch | PyTorch 图 | 多种后端 | 图捕获 + 编译 |
| Triton | OpenAI | Python | PTX/CUDA | 手写 kernel 替代 |

## 优化技术

- **算子融合**：将多个小算子合并为一个大算子，减少 kernel launch 和内存访问
- **内存规划**：静态分析内存分配，减少碎片
- **自动调优**：搜索最优的 kernel 参数配置
- **量化插入**：自动插入量化/反量化操作

## 5. Triton 编程范式：以 Thread Block 为核心的抽象（CS336 P6）

> CS336 P6 视角：Triton（OpenAI 开发）的编程模型介于 PyTorch 的高层张量操作和 CUDA 的单线程视角之间——**以 thread block 为最小编程单元**，开发者思考的是"一个 block 做什么"而非"一个 thread 做什么"。

### 5.1 Triton vs CUDA：抽象层级的选择

| 维度 | CUDA (NVIDIA) | Triton (OpenAI) |
|:---|:---|:---|
| **编程单元** | 单个 thread | thread block |
| **心智模型** | "我是线程 id=N，处理元素 N" | "我是 block id=pid，加载一段数据到 shared memory，处理后写回 HBM" |
| **同步** | 显式 `__syncthreads()` | 隐式（block 内自动同步） |
| **Shared Memory** | 显式分配和管理 | 编译器自动决定（开发者只需 `tl.load` / `tl.store`） |
| **适用场景** | 极致优化、element-wise 简单操作 | Transformer 相关计算、需要 block 间通信的复杂操作（softmax、matmul） |
| **灵活性** | 最高（可控制每个线程） | 中等（足够覆盖大部分 LLM kernel 需求） |

> **CUDA 的 element-wise 陷阱**：对于纯 element-wise 操作（如激活函数），CUDA 的 per-thread 模型非常自然。但一旦涉及跨线程通信（如 softmax 的行规约、矩阵乘法的分块累加），CUDA 就需要大量样板代码来管理同步和 shared memory。Triton 通过 block 级抽象自动处理这些细节。

### 5.2 Triton Kernel 的通用结构

所有 Triton kernel 遵循同一模式：

```python
@triton.jit
def kernel(X_ptr, Y_ptr, N, BLOCK_SIZE):
    # 1. 醒来：确定我是哪个 block
    pid = tl.program_id(0)
    
    # 2. 计算偏移：确定处理哪些数据
    offsets = pid * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
    mask = offsets < N  # 处理边界（padding）
    
    # 3. 从 HBM 加载数据到 block
    x = tl.load(X_ptr + offsets, mask=mask, other=0.0)
    
    # 4. 计算（在 shared memory / register 中）
    y = x * 0.5 * (1.0 + tl.tanh(x))  # 例如 GELU
    
    # 5. 写回 HBM
    tl.store(Y_ptr + offsets, y, mask=mask)
```

> **关键洞察**：`tl.load` 和 `tl.store` 是 HBM 与 block 之间的数据移动操作。计算发生在中间层级（寄存器或 shared memory，由编译器决定）。开发者不需要显式管理 shared memory——这是 Triton 相比 CUDA 的核心简化。

### 5.3 Kernel 融合的自动实现：torch.compile

> CS336 P6 演示：对朴素的 PyTorch GELU 实现调用 `torch.compile()`，编译器会自动分析计算图并生成**单个融合的 Triton kernel**。

**朴素实现的问题**（PyTorch 计算图中的每个原语对应一个独立 kernel）：
```
GELU 朴素 = tanh kernel → 乘法 kernel → 加法 kernel → 乘法 kernel
每次 kernel 调用：HBM 读取 → SM 计算 → HBM 写回 → 下一个 kernel 再从 HBM 读取
```

**torch.compile 的自动融合**：
- 分析计算图，识别可融合的操作链
- 生成单个 Triton kernel，一次性从 HBM 读取数据，完成所有计算，写回一次
- 效果：HBM 读写次数从 O(操作数) 降为 O(1)

> **性能对比**（CS336 P6 实测）：朴素实现 ~3.5ms → 内置实现/torch.compile ~0.5ms。性能差距完全来自 kernel 融合——数学计算相同，但内存移动次数天差地别。

### 5.4 从 Triton 到硬件：PTX 中间表示

Triton 代码并非直接在 GPU 上执行，而是经过编译生成 **PTX（Parallel Thread Execution）**——NVIDIA 的低级虚拟指令集：

```
Triton 代码 → 编译器 → PTX（虚拟汇编） → 驱动 → SASS（实际机器码）
```

**PTX 关键指令**（CS336 P6 示例）：
- `ld.global` — 从 HBM 加载数据到寄存器
- `mov.r32` — 寄存器间数据移动
- `mul.f32` — 浮点乘法
- `st.global` — 将寄存器数据写回 HBM
- `ctaid.x` / `tid.x` — 获取 block/thread 索引

> **编译器的自动优化**：Triton 编译器会自动进行**线程粗化（thread coarsening）**——如果判断单个线程的工作量太轻，会让每个线程处理多个元素，减少线程总数但增加每线程工作量。这在 PTX 层面可以看到：一个 thread 的代码循环处理 8 个元素而非 1 个。

> **何时手写 PTX？**：NVIDIA 编译器通常足够成熟，一般不需要手写 PTX。但对于不成熟的加速器（如某些 NPU/TPU），可能需要手动生成或调整 PTX 以获得合理性能。

## 6. Kernel 编写的三个递进范式（CS336 P6）

### 6.1 Element-wise：最简单的 kernel

以 GELU 为例：每个 block 处理 `BLOCK_SIZE` 个元素，load → 计算 → store。无需跨线程通信，CUDA 和 Triton 的实现复杂度差异不大。

### 6.2 Reduction（行内可放下）：Softmax

当一行能放进一个 thread block 时：
- 每个 block 负责一行
- load 整行 → 计算 max（规约）→ 减去 max → exp → 求和（规约）→ 除法 → store
- block 间互不交互（各自处理独立的行）
- Triton 的写法几乎与朴素 PyTorch 完全一致

### 6.3 Reduction（行内放不下）：分块累加 + 跨块规约

当一行（N 列）远大于 `BLOCK_SIZE` 时：
```python
# 伪代码：行求和 kernel（分块版）
acc = 0.0  # 累加器（寄存器或 shared memory）
for start in range(0, N, BLOCK_SIZE):
    offsets = start + tl.arange(0, BLOCK_SIZE)
    mask = offsets < N
    x = tl.load(X_ptr + offsets, mask=mask)
    acc += tl.sum(x)  # 分块内部求和，累加到 acc
# 最终 acc 即整行之和
tl.store(Y_ptr + row_idx, acc)
```

**关键区别**：引入了 block 内的 for 循环——每个 thread 维护自己的累加器，遍历多个 tile 后再做跨 thread 的规约。

### 6.4 矩阵乘法 + Tiling + Kernel 融合

分块矩阵乘法是 tiling 技术的典型应用，也是 FlashAttention 的基础：

```
朴素方法：逐元素计算 C[m,n] = Σ A[m,k] × B[k,n]
  → 算术强度 = O(1)（每次乘法都从 HBM 读取）
  → 读取量 = O(M×K×N)

理想方法：全部加载到 shared memory
  → 算术强度 = O(N)（无冗余读取）
  → 但矩阵太大，shared memory 放不下

分块方法（实际使用）：
  → 将 C 切分为 M×N 的 tile，每个 tile 由一个 block 负责
  → 沿 K 维度迭代：加载 A 的行 tile + B 的列 tile 到 shared memory
  → 在 shared memory 中做矩阵乘法，累加到部分和
  → 遍历完 K 后，将结果写回 HBM
  → 算术强度 = O(tile_size)
```

**Kernel 融合的附加收益**：在写回 HBM 前，可以直接在 shared memory 中对结果施加激活函数（如 ReLU），实现 matmul + activation 的零开销融合。

> **方法论**：所有复杂 kernel 都是这三个范式（element-wise → reduction → tiled matmul）的组合。FlashAttention = 分块 matmul + 在线 softmax（流式 reduction） + 重计算。
