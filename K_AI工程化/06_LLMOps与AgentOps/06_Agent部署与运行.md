# Agent 部署与运行

## 一句话理解

Agent 是有状态、可调用外部工具的长运行系统，部署需要任务队列、状态持久化、幂等键、超时、重试、取消、并发控制和人工接管；工作流版本、模型版本、工具版本和权限策略必须随任务记录，才能回放失败并安全恢复。

## 1. Agent 部署的特殊性

Agent 与传统 LLM 调用的核心区别：

| 维度 | LLM 调用 | Agent |
|:---|:---|:---|
| 运行时长 | 秒级 | 分钟到小时级 |
| 状态 | 无状态 | 有状态（任务进度、中间结果） |
| 外部交互 | 仅模型 API | 工具调用（API、数据库、代码执行） |
| 错误恢复 | 简单重试 | 复杂（需回滚副作用） |
| 资源管理 | 仅 Token | Token + 计算资源 + 工具配额 |
| 并发控制 | 请求级 | 任务级 + 步骤级 |

核心挑战：**如何让长时间运行、有状态、有副作用的 Agent 可靠运行**。

## 2. Agent 运行架构

```text
用户请求 → 任务队列 → Agent Worker → 执行循环
                           ↓
                    状态持久化 (DB/Redis)
                           ↓
                    步骤执行:
                    ├── LLM 调用
                    ├── 工具调用
                    ├── 人工审批 (可选)
                    └── 状态更新
                           ↓
                    任务完成 / 失败 / 超时
```

### 2.1 任务队列

- **异步提交**：用户请求入队，返回 task_id
- **优先级**：按用户级别、任务紧急度排序
- **并发控制**：限制同时运行的 Agent 数量
- **死信队列**：多次失败的任务转入死信队列人工处理

### 2.2 Agent Worker

- **无状态实例**：Worker 本身无状态，状态存储在外部
- **水平扩展**：按队列长度自动扩缩容
- **优雅停止**：收到停止信号时完成当前步骤后退出
- **健康检查**：心跳检测，异常 Worker 自动重启

## 3. 状态持久化

### 3.1 状态结构

```json
{
  "task_id": "task_abc123",
  "status": "running",
  "current_step": 5,
  "max_steps": 20,
  "context": {
    "messages": [...],
    "variables": {...}
  },
  "tool_calls": [...],
  "checkpoints": [...],
  "metadata": {
    "workflow_version": "v1.2.0",
    "model_version": "gpt-4o-2024-08-06",
    "tool_versions": {"search": "v2.0", "code_exec": "v1.1"},
    "permission_policy": "policy_v3"
  }
}
```

### 3.2 检查点 (Checkpoint)

- **频率**：每完成一个步骤后保存
- **内容**：完整任务状态快照
- **用途**：断点续跑、失败回放、调试
- **存储**：数据库 + 对象存储（大对象）

### 3.3 断点续跑

```text
任务运行中 → Worker 故障 → 状态从最后 Checkpoint 恢复 → 继续执行
```

- **幂等性**：恢复后重新执行的最后一步必须幂等
- **幂等键**：每个步骤有唯一 ID，防止重复执行
- **副作用追踪**：记录已执行的工具副作用，避免重复

## 4. 超时与停止条件

### 4.1 多级超时

| 超时级别 | 说明 | 典型值 |
|:---|:---|:---|
| 步骤超时 | 单个 LLM/工具调用超时 | 30-60s |
| 任务超时 | 整个任务最大运行时间 | 5-30min |
| 人工审批超时 | 等待人工确认的超时 | 24h |

### 4.2 停止条件

- **最大步数**：防止 Agent 无限循环
- **最大成本**：Token 消耗超过预算时停止
- **最大工具调用次数**：限制外部副作用
- **完成条件**：Agent 声明任务完成
- **用户取消**：用户主动取消任务
- **错误阈值**：连续失败次数超限

### 4.3 取消机制

```text
用户取消 → 标记任务为 cancelling → Worker 检测到取消信号
    → 完成当前步骤（不中断工具调用）→ 清理资源 → 标记为 cancelled
```

- **协作式取消**：Worker 在步骤间检查取消信号
- **资源清理**：取消后释放占用的资源（沙箱、文件锁）
- **副作用处理**：已执行的不可逆操作需记录并通知

## 5. 错误恢复与重试

### 5.1 错误分类

| 错误类型 | 示例 | 恢复策略 |
|:---|:---|:---|
| 瞬时错误 | API 超时、限流 | 指数退避重试 |
| 模型错误 | 输出格式错误、幻觉 | 重新生成 + 约束 |
| 工具错误 | API 返回错误 | 重试 + 降级方案 |
| 逻辑错误 | Agent 进入死循环 | 步数限制 + 人工接管 |
| 系统错误 | Worker 崩溃 | 从 Checkpoint 恢复 |

### 5.2 重试策略

- **指数退避**：1s → 2s → 4s → 8s，最大 3 次
- **抖动**：加入随机抖动避免重试风暴
- **工具级配置**：不同工具不同重试策略
- **副作用保护**：非幂等工具不自动重试

## 6. 并发控制

### 6.1 任务级并发

- **每用户并发限制**：同一用户最多 N 个运行中任务
- **全局并发限制**：系统总并发任务数上限
- **资源池**：按资源类型（GPU、沙箱）分配

### 6.2 步骤级并发

- **并行工具调用**：多个独立工具调用可并行
- **依赖管理**：有依赖的工具调用需顺序执行
- **结果合并**：并行调用的结果合并到上下文

## 7. 人工接管

### 7.1 人工审批节点

```text
Agent 执行 → 到达高风险操作 → 暂停 → 通知人工 → 等待审批
                                                    ↓
                                              批准 → 继续
                                              拒绝 → 终止/跳过
                                              超时 → 默认策略
```

### 7.2 人工接管场景

- **高风险操作**：删除数据、发送邮件、执行支付
- **低置信度决策**：模型不确定时的兜底
- **合规要求**：特定操作需人工确认
- **Agent 卡住**：循环或无法进展时升级

## 8. 版本与回放

### 8.1 版本绑定

每个任务记录完整版本信息：

- 工作流版本（DAG 定义）
- 模型版本
- 工具版本
- Prompt 版本
- 权限策略版本

### 8.2 失败回放

从 Checkpoint 恢复失败任务，可以：

- **原样重放**：使用相同版本和参数
- **修改重放**：调整参数后重放
- **版本对比**：用新版本重放，对比结果

## 9. 资源隔离

### 9.1 代码执行沙箱

- **容器隔离**：每个代码执行在独立容器中
- **资源限制**：CPU、内存、磁盘、网络配额
- **网络策略**：限制出站网络访问
- **文件系统**：临时文件系统，任务结束清理

### 9.2 工具权限

- **最小权限**：工具只拥有完成任务所需的最小权限
- **权限令牌**：短期有效的令牌，任务结束失效
- **审计日志**：记录所有工具调用参数和结果

## 10. 常见问题

- **任务卡死**：Agent 无限循环，需步数限制和心跳检测
- **状态丢失**：Worker 崩溃后状态未持久化，需频繁 Checkpoint
- **副作用重复**：重试导致工具副作用重复执行，需幂等设计
- **资源泄漏**：任务结束未清理沙箱/文件锁，需垃圾回收
- **版本不兼容**：工作流升级后旧任务无法恢复，需版本兼容策略
