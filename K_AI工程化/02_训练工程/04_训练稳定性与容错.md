# 训练稳定性与容错

## 一句话理解

大规模长周期训练（数天至数周）中，硬件故障、数值不稳定和数据异常是常态；训练稳定性工程通过监控、预防和恢复机制确保训练任务可靠完成。

## 概述

一个千卡级 LLM 预训练任务可能运行数周至数月，在此期间几乎必然发生 GPU 故障、网络中断或 loss 异常。如果不做容错设计，一次故障就可能浪费数天计算资源。

本笔记回答的核心问题：
- 长周期训练有哪些失败模式？
- 如何检测和预防 loss spike 等数值异常？
- 故障恢复的工程实践是什么？

## 核心概念

### 失败模式分类

| 类型 | 原因 | 频率 | 检测方式 |
|---|---|---|---|
| 硬件故障 | GPU 掉卡、NVLink 断开、网络超时 | 高 | 心跳检测、NCCL 超时 |
| 数值不稳定 | loss spike、NaN/Inf、梯度爆炸 | 中 | loss/梯度监控 |
| 数据异常 | 损坏样本、格式错误、分布偏移 | 中 | 数据质量校验 |
| 软件故障 | OOM、框架 bug、配置错误 | 低 | 异常捕获、日志分析 |
| 基础设施 | 电力中断、机房故障 | 极低 | 多可用区容灾 |

### Loss Spike

训练过程中 loss 突然大幅跳升的现象。常见原因：

- 学习率过大导致参数跳到不稳定区域
- 梯度爆炸
- 异常数据批次
- 数值精度溢出
- Attention 溢出（softmax 上溢）

## 技术原理

### 监控体系

训练过程必须持续监控以下指标：

| 类别 | 监控指标 |
|---|---|
| 训练状态 | loss、learning rate、gradient norm |
| 数值健康 | NaN/Inf 计数、激活值范围、权重范数 |
| 系统状态 | GPU 利用率、显存占用、温度 |
| 通信状态 | All-Reduce 耗时、NCCL 错误率 |
| 数据流 | 数据吞吐、数据加载等待时间 |

### 预防措施

#### 学习率调度

- Warmup：训练初期线性增长学习率，避免早期梯度方向不稳定
- Cosine decay：平滑衰减，避免后期学习率跳变
- 学习率上限：设置硬性上限防止意外跳升

#### 梯度裁剪

对梯度范数进行约束，防止梯度爆炸：

$$\text{if } \lVert g \rVert > \tau: \quad g \leftarrow \frac{\tau}{\lVert g \rVert} g$$

典型阈值 $\tau$ 为 1.0。

#### 异常批次隔离

检测到 loss 异常时跳过当前批次，不更新参数：

- 计算 loss 值与历史均值的偏差
- 若偏差超过 $k$ 个标准差，标记为异常并跳过
- 记录异常批次的索引和数据内容用于事后分析

#### 数值稳定性

- 优先使用 BF16 而非 FP16（更大动态范围）
- Attention score 减去最大值再做 softmax（防止上溢）
- Embedding 层保持 FP32
- 优化器状态使用 FP32

### 恢复机制

#### 检查点策略

| 策略 | 说明 | 适用场景 |
|---|---|---|
| 定期保存 | 每 N 步保存一次 | 基础策略 |
| 异步保存 | 后台线程保存，不阻塞训练 | 大模型 |
| 分片保存 | 每卡保存自己分片 | ZeRO-3 |
| 冗余保存 | 保存到多位置 | 高容错需求 |

检查点必须包含：
- 模型权重（所有分片）
- 优化器状态
- 数据游标（当前数据位置）
- 随机种子
- 并行拓扑配置
- 训练步数和调度器状态

#### 恢复验证

恢复后必须验证：

- 权重一致性（检查分片拼接是否正确）
- 数据游标连续性（避免重复或跳过数据）
- 训练曲线连续性（loss 不应突变）
- 并行拓扑一致性（TP/PP/DP 分组不变）

## 关键方法与模型

### OPT 开放日志的启示

Meta 的 OPT-175B 训练日志记录了 1746 次中断，其中约 40% 为硬件故障，35% 为软件问题，25% 为数据或训练问题。这表明：

- 千卡级训练的平均无故障时间（MTBF）约为数小时
- 检查点频率应匹配 MTBF，不应超过几小时
- 自动化恢复是必需的，人工干预成本过高

### Megatron-LM 的容错实践

- 检查点保存到分布式文件系统（如 Lustre）
- 保存时校验和验证
- 支持从任意检查点恢复并改变并行拓扑
- 内置 NCCL 超时检测和自动重试

## 优势与局限

### 有效的措施

- 梯度裁剪 + warmup 基本消除梯度爆炸
- BF16 训练显著减少数值溢出
- 异步检查点减少恢复开销

### 仍有挑战的领域

- Loss spike 的根因分析困难（可能是多种因素叠加）
- 恢复后训练曲线可能不完全连续
- 超大规模训练（万卡级）的 MTBF 极低，需要新的容错架构

## 应用场景

- 预训练：完整容错体系必需
- 微调：相对简单，检查点频率可降低
- 强化学习训练：需要额外关注 reward 异常

## 前沿发展

- **弹性训练**：支持 GPU 动态加入/退出，无需重启
- **在线检查点压缩**：减少检查点存储和 I/O 开销
- **根因分析自动化**：利用 ML 模型自动诊断 loss spike 原因
- **冗余计算**：关键阶段使用冗余 GPU 进行验证

## 常见问题

- **检查点应该多频繁保存？**：取决于 MTBF。千卡级建议每 1000-2000 步（约 1-2 小时）。太频繁影响吞吐，太稀疏浪费恢复成本。
- **Loss spike 一定要回滚吗？**：不一定。轻微 spike 可以通过降低学习率继续训练。严重 spike（loss 超过初始值）必须回滚到上一个稳定检查点。
- **恢复后训练曲线会完全连续吗？**：通常不会完全连续，因为数据 shuffle 顺序、浮点非确定性等因素会导致微小差异。应设定统计容差。
