# 事件响应与恢复

## 一句话理解

事件响应涵盖发现、分级、止损、沟通、恢复、复盘和防复发七个阶段，每个告警必须绑定包含负责人、开关、回滚版本、数据保留与外部沟通方案的 Runbook，并通过定期混沌演练验证系统在模型服务故障、提示注入、数据泄露和 GPU 不可用等场景下的韧性。

## 1. AI 事件响应的特殊性

传统软件事件响应主要处理服务宕机、数据库故障和网络问题。AI 系统的事件响应还需应对传统 SRE 未涉及的新型故障：

| 维度 | 传统 SRE 事件 | AI 系统事件 |
|:---|:---|:---|
| 故障发现 | 监控告警（5xx、延迟） | 可能还需用户反馈或质量评测才发现 |
| 故障定位 | 日志、链路追踪 | 还需排查模型版本、Prompt、数据、供应商 |
| 止损手段 | 回滚代码、扩容 | 还可降级模型、调整 Prompt、关闭工具 |
| 影响范围 | 服务不可用 | 服务可用但输出有害/错误（更隐蔽） |
| 恢复验证 | 服务恢复正常 | 还需验证质量、安全回归 |
| 合规要求 | 一般无需外部通知 | 可能需通知用户/监管（如数据泄露） |

## 2. 事件响应全流程

### 2.1 七阶段流程

```text
① 发现（Detection）
   ├─ 自动告警触发
   ├─ 用户反馈聚集
   └─ 定期评测发现
         ↓
② 分级（Triage）
   ├─ 影响范围评估
   ├─ 严重程度定级（P0-P3）
   └─ 指定事件指挥官（Incident Commander）
         ↓
③ 止损（Mitigation）
   ├─ 限流/降级/回滚
   ├─ 功能隔离/关闭
   └─ 目标：尽快恢复服务，而非根因修复
         ↓
④ 沟通（Communication）
   ├─ 内部同步（IM 群、状态页）
   ├─ 外部通知（用户、合作伙伴）
   └─ 定期更新（每 15-30 分钟）
         ↓
⑤ 恢复（Recovery）
   ├─ 根因修复
   ├─ 灰度发布验证
   └─ 全量恢复
         ↓
⑥ 复盘（Post-mortem）
   ├─ 时间线梳理
   ├─ 根因分析（5 Whys）
   ├─ 行动项制定
   └─ blameless（对事不对人）
         ↓
⑦ 防复发（Prevention）
   ├─ 行动项落地
   ├─ 回归测试补充
   ├─ 监控/告警完善
   └─ 混沌演练验证
```

### 2.2 事件定级标准

| 级别 | 定义 | 响应时间 | 升级条件 | 示例 |
|:---|:---|:---|:---|:---|
| **P0** | 核心服务完全不可用或严重安全事件 | 立即（< 5 分钟） | 自动通知 VP 级 | 模型服务全面宕机；有害内容大规模泄露 |
| **P1** | 核心功能严重退化或 SLO 严重超标 | 5 分钟 | 30 分钟无响应升级 | 错误率 > 10%；P99 延迟翻 3 倍 |
| **P2** | 部分功能退化，影响部分用户 | 30 分钟 | 2 小时无响应升级 | 某工具调用失败率 > 20% |
| **P3** | 潜在问题或轻微退化 | 工作日内 | 无 | 质量评分下降 3% |

### 2.3 角色与职责

```text
事件响应角色分工：

事件指挥官（Incident Commander, IC）
  ├─ 统筹协调整个响应过程
  ├─ 做关键决策（是否回滚、是否通知外部）
  ├─ 不参与具体修复，保持全局视角
  └─ 通常由资深 SRE 或技术负责人担任

运营负责人（Operations Lead）
  ├─ 执行止损操作（限流、回滚、降级）
  ├─ 协调基础设施变更
  └─ 监控恢复进度

沟通负责人（Communications Lead）
  ├─ 内部状态更新（每 15-30 分钟）
  ├─ 外部通知（状态页、用户邮件）
  └─ 管理利益相关方预期

根因调查员（Root Cause Investigator）
  ├─ 深入分析故障根因
  ├─ 收集日志、指标、时间线证据
  └─ 在恢复后主导 Post-mortem

计划负责人（Planning Lead）
  ├─ 跟踪行动项
  ├─ 协调后续修复工作
  └─ 确保防复发措施落地
```

## 3. Runbook 设计

### 3.1 Runbook 的必要性

每个告警规则都必须绑定一个 Runbook。没有 Runbook 的告警等于没有告警——on-call 工程师不知道该如何响应。

### 3.2 Runbook 模板

```markdown
# Runbook: [告警名称]

## 告警信息
- **告警名称**：LLM 推理 P99 延迟超过 5 秒
- **告警级别**：P2
- **告警条件**：histogram_quantile(0.99, llm_inference_duration_seconds_bucket[5m]) > 5
- **影响范围**：所有使用 LLM 推理的用户
- **负责人**：AI 平台团队（PagerDuty: ai-platform-oncall）

## 快速诊断（5 分钟内完成）
1. 查看 Grafana 仪表盘 [链接]，确认延迟趋势
2. 检查 GPU 利用率是否 > 90%：`nvidia-smi` 或 DCGM dashboard
3. 检查推理队列深度：`llm_queue_depth` 指标
4. 检查最近是否有模型部署：`kubectl get deployments -n ai-serving`
5. 检查上游依赖（向量数据库、Redis）是否正常

## 常见根因与处置

### 场景 1：GPU 资源不足
- **症状**：GPU 利用率 > 90%，队列深度持续增长
- **处置**：
  ```bash
  # 扩容推理 Pod
  kubectl scale deployment llm-serving --replicas=+2 -n ai-serving
  # 验证新 Pod 就绪
  kubectl rollout status deployment llm-serving -n ai-serving
  ```

### 场景 2：模型版本问题
- **症状**：近期有模型部署，延迟突增
- **处置**：
  ```bash
  # 回滚到上一版本
  kubectl rollout undo deployment llm-serving -n ai-serving
  # 验证回滚
  kubectl rollout status deployment llm-serving -n ai-serving
  ```

### 场景 3：批处理大小过大
- **症状**：GPU 利用率正常但单请求延迟高
- **处置**：调小 `--max-batch-size` 参数并重启服务

## 升级路径
1. 5 分钟内无人响应 → 自动升级到二级 on-call
2. 30 分钟内未恢复 → 通知技术总监
3. 1 小时内未恢复 → 启动 P0 响应流程

## 降级方案
如果无法快速恢复：
1. 启用语义缓存（命中率约 30-40%）
2. 切换到小模型（质量下降但延迟降低）
3. 开启限流（QPS 降至 50%）

## 数据保留
- 推理日志：保留 7 天
- GPU 指标：保留 30 天
- 事件相关日志：打包归档，保留 1 年

## 外部沟通
- 状态页更新模板：「AI 推理服务延迟异常，团队正在调查，预计 XX 分钟内恢复」
- 用户通知阈值：P1 级别且影响 > 10% 用户时通知
```

### 3.3 Runbook 维护要求

- **每次事件后更新**：如果事件中发现了 Runbook 未覆盖的场景，必须补充
- **定期审查**：每季度审查一次，确保步骤和命令仍然有效
- **可执行性测试**：非 on-call 人员应能按 Runbook 步骤执行基本操作

## 4. 止损操作手册

### 4.1 止损操作优先级

```text
止损操作按优先级排序（从快到慢）：

秒级生效：
  ├─ 限流（调整 QPS/TPM 上限）
  ├─ 功能开关关闭（禁用问题功能）
  └─ 语义缓存启用（跳过推理）

分钟级生效：
  ├─ 模型降级（切换到小模型）
  ├─ Prompt 回滚（恢复上一版 Prompt）
  └─ RAG 降级（跳过检索，直接生成）

十分钟级生效：
  ├─ 模型版本回滚
  ├─ 服务回滚（kubectl rollout undo）
  └─ 流量切换（切到备用集群）
```

### 4.2 功能开关设计

```python
class FeatureFlags:
    """AI 服务功能开关"""

    # 功能级开关
    rag_enabled: bool = True           # RAG 检索
    tool_calling_enabled: bool = True  # Agent 工具调用
    streaming_enabled: bool = True     # 流式输出
    multi_modal_enabled: bool = True   # 多模态输入

    # 模型选择开关
    primary_model: str = "gpt-4"
    fallback_model: str = "gpt-4-mini"  # 降级时使用

    # 安全开关
    input_filter_enabled: bool = True   # 输入安全过滤
    output_filter_enabled: bool = True  # 输出安全检查
    max_input_tokens: int = 8192        # 输入长度限制

    # 限流开关
    global_qps_limit: int = 1000
    per_user_qps_limit: int = 10
    per_user_tpm_limit: int = 10000

    async def apply_emergency_config(self, config_name: str):
        """应用紧急配置"""
        configs = {
            "degraded": FeatureFlags(
                tool_calling_enabled=False,
                multi_modal_enabled=False,
                primary_model="gpt-4-mini",
                global_qps_limit=500,
            ),
            "minimal": FeatureFlags(
                rag_enabled=False,
                tool_calling_enabled=False,
                multi_modal_enabled=False,
                streaming_enabled=False,
                primary_model="gpt-4-mini",
                global_qps_limit=200,
            ),
            "emergency": FeatureFlags(
                rag_enabled=False,
                tool_calling_enabled=False,
                multi_modal_enabled=False,
                streaming_enabled=False,
                primary_model="static-cache",  # 仅返回缓存
                global_qps_limit=100,
            ),
        }
        if config_name in configs:
            self.__dict__.update(configs[config_name].__dict__)
```

### 4.3 回滚操作清单

```text
模型版本回滚：
  1. 确认当前版本号：kubectl get deployment llm-serving -o jsonpath='{.spec.template.spec.containers[0].image}'
  2. 执行回滚：kubectl rollout undo deployment llm-serving -n ai-serving
  3. 验证回滚：kubectl rollout status deployment llm-serving -n ai-serving
  4. 验证质量：运行 L0 冒烟测试集
  5. 监控指标：观察 5 分钟，确认延迟和错误率恢复

Prompt 回滚：
  1. 确认当前 Prompt 版本（从配置中心获取）
  2. 回滚到上一版本：更新配置中心的 Prompt 版本号
  3. 等待服务热加载（或触发重启）
  4. 验证：抽样 10 条请求检查输出格式

配置回滚：
  1. 从 Git 历史找到上一稳定配置
  2. 通过配置中心回滚
  3. 验证配置生效
```

## 5. 沟通管理

### 5.1 内部沟通

```text
事件沟通频道结构：
  #incident-active      → 当前活跃事件讨论（仅事件响应人员）
  #incident-updates     → 事件状态更新（全员可见，只读）
  #incident-postmortem  → 事后复盘讨论

更新频率：
  P0：每 15 分钟更新一次
  P1：每 30 分钟更新一次
  P2：每小时更新一次
  P3：解决后总结即可

更新模板：
  【状态更新 #N】事件 [ID]
  当前状态：[调查中 / 止损中 / 恢复中 / 已解决]
  影响范围：[描述]
  已采取措施：[描述]
  下一步计划：[描述]
  预计恢复时间：[ETA 或「待定」]
```

### 5.2 外部沟通

| 沟通对象 | 触发条件 | 沟通方式 | 模板 |
|:---|:---|:---|:---|
| 状态页 | P0/P1 事件 | 自动更新状态页 | "我们正在调查 AI 服务异常，部分用户可能受到影响" |
| 用户邮件 | 数据泄露/安全事件 | 邮件通知受影响用户 | 法务审核后的模板 |
| 监管机构 | 合规性事件（如 EU AI Act） | 正式报告 | 法务/合规团队负责 |
| 媒体公关 | 重大公众影响 | PR 团队负责 | 预先准备的公关声明 |

### 5.3 沟通原则

- **透明**：承认问题，不隐瞒影响范围
- **及时**：宁可信息不完整也要及时沟通
- **准确**：不确定的内容标注"待确认"
- **可执行**：告诉用户可以做什么（如"稍后重试"）

## 6. Post-mortem（事后复盘）

### 6.1 Post-mortem 原则

**Blameless（对事不对人）**：复盘的目的是改进系统，而非追究个人责任。

- ✅ "当时缺少自动化测试覆盖这个场景"
- ❌ "XX 工程师没有手动测试就发布了"

### 6.2 Post-mortem 模板

```markdown
# Post-mortem: [事件标题]

## 事件摘要
- **事件 ID**：INC-2024-0125
- **日期**：2024-01-25
- **持续时间**：2 小时 15 分钟
- **级别**：P1
- **影响**：AI 推理服务延迟 P99 从 2s 升至 15s，影响约 30% 用户

## 时间线
| 时间 | 事件 |
|:---|:---|
| 14:00 | 模型版本 v2.3 部署完成 |
| 14:05 | P99 延迟告警触发 |
| 14:07 | On-call 确认告警 |
| 14:10 | 初步判断为新版本问题 |
| 14:15 | 决定回滚 |
| 14:20 | 回滚完成，延迟开始恢复 |
| 14:30 | 延迟恢复正常 |
| 14:35 | 事件降级为 P3（监控恢复） |
| 15:00 | L0 冒烟测试通过，事件关闭 |

## 影响分析
- **受影响用户**：约 12,000（30%）
- **错误请求数**：约 8,500
- **SLO 消耗**：消耗 15% 月度错误预算
- **业务影响**：约 200 次用户会话中断

## 根因分析（5 Whys）
1. 为什么延迟升高？→ 新模型版本推理速度更慢
2. 为什么推理速度更慢？→ 新版本支持更长上下文，默认 max_tokens 增加
3. 为什么 max_tokens 增加未被发现？→ 部署前未运行性能基准测试
4. 为什么未运行性能基准？→ CI/CD 流程中缺少性能测试阶段
5. 为什么缺少性能测试？→ 性能测试环境与生产环境配置不一致

## 行动项
| 行动项 | 负责人 | 截止日期 | 状态 |
|:---|:---|:---|:---|
| 在 CI/CD 中增加性能基准测试 | 张三 | 2024-02-01 | 进行中 |
| 对齐测试环境与生产环境配置 | 李四 | 2024-02-15 | 待开始 |
| 模型部署增加 max_tokens 配置审查 | 王五 | 2024-02-01 | 完成 |
| 更新 Runbook 补充性能问题诊断步骤 | 赵六 | 2024-02-10 | 待开始 |

## 经验教训
- **做得好的**：告警及时触发；on-call 快速响应；回滚决策果断
- **做得不好的**：部署前缺少性能验证；测试环境配置不一致
- **幸运的**：回滚快速生效；影响时间较短
```

### 6.3 行动项跟踪

行动项必须满足 **SMART 原则**：
- **S**pecific：具体明确
- **M**easurable：可衡量完成度
- **A**ssignable：有明确负责人
- **R**ealistic：可行
- **T**ime-bound：有截止日期

```text
行动项生命周期：
  创建 → 指派负责人 → 设定截止日期 → 定期跟踪 → 完成/验证 → 关闭

跟踪机制：
  ├─ 每周回顾未完成行动项
  ├─ 超期行动项自动升级通知
  └─ 季度统计行动项完成率（目标 > 90%）
```

## 7. 混沌工程与演练

### 7.1 混沌工程原则

混沌工程是**主动注入故障**以验证系统韧性的实践，核心原则：

- 假设系统在故障下仍能正常工作
- 在生产环境或接近生产的环境中测试
- 自动化、持续运行
- 最小化爆炸半径（先小范围测试）

### 7.2 AI 系统混沌演练场景

| 演练场景 | 注入方法 | 验证目标 | 频率 |
|:---|:---|:---|:---|
| **模型服务故障** | 杀死推理 Pod | 熔断器触发、降级路径生效 | 每月 |
| **LLM API 超时** | 注入网络延迟 | 超时机制生效、用户体验可接受 | 每月 |
| **检索服务不可用** | 关闭向量数据库 | RAG 降级为无上下文生成 | 每月 |
| **工具调用失败** | mock 工具返回错误 | Agent 错误处理、替代策略 | 每月 |
| **GPU 不可用** | 标记 GPU 节点不可调度 | 自动扩容或降级触发 | 每季度 |
| **提示注入攻击** | 发送恶意输入 | 安全过滤拦截、告警触发 | 每季度 |
| **数据泄露模拟** | 尝试提取训练数据 | 防泄露机制生效 | 每季度 |
| **错误配置** | 修改关键配置 | 配置校验、回滚机制 | 每季度 |
| **区域级故障** | 模拟可用区不可用 | 流量自动切换到备用区域 | 每半年 |
| **全量回滚** | 从备份恢复整个系统 | 灾难恢复流程有效 | 每年 |

### 7.3 混沌演练流程

```text
演练前准备：
  ├─ 定义演练目标和成功标准
  ├─ 确定爆炸半径（影响的用户比例 < 5%）
  ├─ 准备回滚方案
  ├─ 通知相关团队
  └─ 设定自动终止条件（如错误率 > 10% 自动停止）

演练执行：
  ├─ 在非高峰时段执行
  ├─ 逐步注入故障（从 1% 流量开始）
  ├─ 实时监控指标和用户体验
  └─ 记录系统行为（是否符合预期）

演练后：
  ├─ 恢复正常状态
  ├─ 验证系统完全恢复
  ├─ 记录发现的问题
  └─ 制定改进计划
```

### 7.4 游戏日（Game Day）

**游戏日**是团队定期进行的综合性混沌演练：

```text
游戏日组织流程：

准备阶段（提前 2 周）：
  ├─ 设计演练场景剧本
  ├─ 准备监控和观测工具
  ├─ 分配角色（演练导演、参与者、观察者）
  └─ 设定安全边界

演练日（半天到一天）：
  ├─ 导演按剧本逐步注入故障
  ├─ 参与者按 Runbook 响应
  ├─ 观察者记录响应过程和问题
  └─ 可加入"突发情况"测试应变能力

复盘阶段（演练后 1-2 天）：
  ├─ 梳理响应时间线
  ├─ 识别 Runbook 不足
  ├─ 识别系统弱点
  └─ 制定改进计划
```

## 8. 灾难恢复

### 8.1 灾难恢复策略

| 策略 | 描述 | RTO | RPO | 成本 |
|:---|:---|:---|:---|:---|
| **备份恢复** | 定期备份，故障时从备份恢复 | 小时级 | 小时级 | 低 |
| ** Pilot Light** | 核心服务保持最小运行，故障时扩展 | 分钟级 | 分钟级 | 中 |
| **温备** | 备用环境保持运行但不接流量 | 分钟级 | 秒级 | 中高 |
| **热备/多活** | 多区域同时运行，流量自动切换 | 秒级 | 秒级 | 高 |

> - **RTO**（Recovery Time Objective）：恢复时间目标
> - **RPO**（Recovery Point Objective）：恢复点目标（可接受的数据丢失量）

### 8.2 AI 系统灾难恢复要点

```text
AI 系统特有的灾难恢复考量：

模型文件：
  ├─ 模型权重文件通常较大（数十 GB）
  ├─ 需预先复制到备用区域（跨区域传输耗时）
  └─ 使用对象存储 + CDN 分发

推理状态：
  ├─ 推理服务通常无状态，可直接切换
  ├─ 但 KV Cache 会丢失，切换后首请求延迟较高
  └─ Agent 任务状态需持久化到共享存储

知识库：
  ├─ 向量数据库需定期同步到备用区域
  ├─ 大规模向量索引同步耗时，需增量同步
  └─ 考虑使用多区域复制原生的向量数据库

配置数据：
  ├─ Prompt、功能开关等配置需多区域同步
  └─ 使用多区域配置中心（如 ZooKeeper 多区域部署）
```

### 8.3 恢复验证

恢复后必须验证的维度：

```text
恢复验证清单：

功能验证：
  ├─ L0 冒烟测试全部通过
  ├─ 核心用户流程可正常完成
  └─ 关键工具调用正常

质量验证：
  ├─ L1 回归测试通过率 ≥ 95%
  ├─ 在线评测得分 ≥ 基线 95%
  └─ 抽样人工审查 20 条输出

安全验证：
  ├─ 安全测试集全部通过
  ├─ 输入/输出过滤正常工作
  └─ 审计日志正常记录

性能验证：
  ├─ P99 延迟恢复正常范围
  ├─ 吞吐量满足预期
  └─ GPU 利用率正常

积压处理：
  ├─ 恢复期间积压的请求逐步处理
  ├─ 优先处理高优先级请求
  └─ 必要时通知用户重新提交
```
