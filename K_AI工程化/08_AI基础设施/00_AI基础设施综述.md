# AI 基础设施综述

## 一句话理解

AI 基础设施提供训练、推理和数据管道所需的计算、存储、网络、调度与平台能力，目标是安全地最大化资源利用率、保障可用性，并让研发和运营工程师能高效使用这些资源。

## 1. 领域定义

AI 基础设施涵盖：

- **计算**：GPU/TPU/NPU 硬件及其驱动、库和互联
- **调度**：多租户 GPU 集群管理、作业优先级和弹性伸缩
- **存储**：大规模模型权重、数据集、检查点的分布式存储
- **网络**：节点间高带宽低延迟通信（InfiniBand/RoCE）
- **编译器**：计算图优化、算子融合、代码生成
- **平台服务**：作业管理、镜像仓库、监控告警、配额管理

与 MLOps（关注工作流和生命周期管理）不同，AI 基础设施关注物理资源层面的供给和利用效率。

## 3. 核心组成

### 3.1 GPU 与 CUDA 生态

GPU 是 AI 计算的核心硬件。关键性能维度：

| 指标 | 含义 | 典型值（H100） |
|:---|:---|:---|
| FP16 算力 | Tensor Core 峰值算力 | 989 TFLOPS |
| 显存容量 | 模型权重 + KV Cache 存储 | 80 GB HBM3 |
| 显存带宽 | 决定访存密集任务速度 | 3.35 TB/s |
| NVLink 带宽 | GPU 间互联 | 900 GB/s (NVSwitch) |
| TDP | 功耗 | 700W |

LLM 推理是**访存密集型**（Arithmetic Intensity ≈ 1），显存带宽而非算力是瓶颈。训练是**计算密集型**，算力是主要瓶颈。

### 3.2 Kubernetes 与 GPU 调度

Kubernetes 以声明式方式管理 AI 作业和服务。GPU 调度的特殊需求：

**训练场景（Gang Scheduling）**：
- 多节点作业必须同时获得所有 GPU 才能启动
- 任何节点失败都需要重新分配（弹性训练是例外）
- 工具：Volcano、Koordinator、KAIWO

**推理场景（弹性伸缩）**：
- 基于 GPU 利用率或请求队列触发扩缩容
- 冷启动延迟优化（模型权重预加载）
- 多租户配额与资源隔离

GPU 不能只按卡数分配，需同时考虑：显存大小、互联拓扑（NVLink vs PCIe）、任务生命周期（训练 vs 推理）。

### 3.3 分布式存储与网络

**存储需求**：

| 类型 | 规模 | 需求 | 典型方案 |
|:---|:---|:---|:---|
| 训练数据集 | TB-PB | 高带宽顺序读 | Lustre、GPFS、对象存储 |
| 模型检查点 | GB-TB | 快速写入（训练容错） | NFS、分布式文件系统 |
| 模型权重（推理） | GB-数百GB | 低延迟随机读 | 本地 NVMe、内存映射 |
| 特征数据 | GB-TB | 低延迟在线读 | Redis、Cassandra |

**节点间通信**：
- InfiniBand：高带宽（HDR 200Gb/s，NDR 400Gb/s）、低延迟（~1μs）
- RoCE（RDMA over Converged Ethernet）：基于以太网的 RDMA，成本较低
- NCCL：NVIDIA 集合通信库，实现 AllReduce/AllGather 等操作

### 3.4 编译器栈与中间表示

从 PyTorch 模型到高效执行代码的编译链：

```text
PyTorch Model → torch.compile → TorchInductor → Triton Kernel → PTX → SASS
                                              → CUDA C → nvcc → SASS
                                              
PyTorch Model → ONNX Export → ONNX Runtime → TensorRT Engine
```

关键组件：
- **torch.compile**：PyTorch 2.0 即时编译，自动生成优化 Triton/CUDA Kernel
- **Triton**：OpenAI 的 Python GPU Kernel 编写 DSL，无需写 CUDA C
- **TensorRT**：NVIDIA 推理优化引擎，算子融合 + INT8/FP8 量化
- **XLA**：Google JAX/TensorFlow 的编译后端，用于 TPU

### 3.5 通信库与集合通信

分布式训练的通信原语：

| 操作 | 含义 | 用途 |
|:---|:---|:---|
| AllReduce | 所有节点汇总 → 结果广播给所有节点 | 数据并行梯度同步 |
| AllGather | 每个节点发送数据 → 所有节点获得完整数据 | ZeRO-3 参数收集 |
| ReduceScatter | AllReduce 的分片版本 | ZeRO-2/3 梯度切分 |
| All-to-All | 每个节点向每个节点发送不同数据 | MoE 专家路由 |

NCCL 通过 Ring-AllReduce 算法实现高效的 AllReduce，通信量与节点数无关（只与单个节点的数据量成正比）。

### 3.6 存储 I/O 与检查点系统

大模型训练的检查点工程要求：

- **写入速度**：70B 模型 FP32 权重约 280GB，检查点写入需快于 MTBF
- **异步保存**：不阻塞训练进程（异步 checkpoint）
- **校验**：写入完成后校验哈希，避免损坏检查点
- **自动恢复**：节点故障后自动从最近 checkpoint 恢复
- **存储分层**：NVMe（热检查点）→ 分布式存储（历史版本）→ 对象存储（归档）

### 3.7 异构硬件与能耗调度

- **异构集群**：不同代际 GPU（A100/H100/H200）混合部署
- **任务亲和性**：将 FP8 推理任务调度到 H100，将 INT8 任务调度到 A100
- **能耗感知调度**：电力消耗占数据中心成本约 40%，调度需考虑功耗曲线
- **液冷/浸没冷却**：H100 700W/B200 1000W 需要高密度散热方案

## 4. 云原生 AI 平台

### 4.1 平台架构

```text
用户（研究员/工程师）
    ↓
AI 平台门户（作业提交/资源申请/镜像管理）
    ↓
调度层（Kubernetes + Volcano/KAIWO）
    ↓
资源层（GPU 节点池 + 存储集群 + 网络）
    ↓
监控层（Prometheus + Grafana + 告警）
```

### 4.2 主要云 AI 平台

| 平台 | 提供商 | 特点 |
|:---|:---|:---|
| AWS SageMaker | Amazon | 端到端 ML 平台，托管训练和推理 |
| Google Vertex AI | Google | TPU 原生支持，AutoML 能力 |
| Azure ML | Microsoft | 与 OpenAI 深度集成 |
| Databricks | 独立 | 数据+ML 一体化，Delta Lake |
| 自建 GPU 集群 | — | 完全控制，适合大规模专有训练 |

## 7. 前沿发展

- **CXL 互联**：CPU-GPU-存储统一缓存一致性互联，消除内存墙
- **存算一体**：在存储芯片内执行计算，消除冯·诺依曼瓶颈
- **光子计算**：光信号矩阵乘法，理论能效远超电子芯片
- **开放 AI 网络**（UALink）：非 NVIDIA 的 GPU 互联开放标准联盟
- **超大规模训练集群**：Meta 10 万卡 H100 集群工程经验公开
- **能耗优化**：机器学习感知的动态电压频率调整（DVFS）
- **容错训练**：Elastic Training + In-Flight Checkpoint，支持节点动态增减
