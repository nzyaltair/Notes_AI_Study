# 事件系统与分发语义

## 一句话理解

Cordis 事件不仅是通知机制，也是 DSH 的主要扩展面；选择分发语义决定监听器能否改写、拒绝或仅观察下游行为。

## 四种分发模式（harness 层）

| 模式 | 是否 await？ | 分发顺序 | 是否有返回值？ | 典型用途 |
|---|---|---|---|---|
| `emit` | 否 | 监听器按注册顺序观察 | 否 | 状态变更通知、持久事件广播 |
| `waterfall` | 否（逐个委托） | 监听器按注册顺序，通过 `next()` 传递 | 是 | 策略层、请求改写、结果变换 |
| `parallel` | 是 | 所有监听器并行 | 否 | 独立副作用（如 flush） |
| `serial` | 是 | 监听器按注册顺序 | 是 | 最终检查点（如 `agent/turn-stopping`） |

> 分发模式是事件公开约定的一部分，不能随意改变。harness 新事件通过 `@mode` 标签记录模式，以供生成目录交叉校验。

## Waterfall 规则

`agent/pre-step`、`agent/request`、`llm/stream`、`tools/pre-execute`、`tools/execute`、`tools/post-execute`、`agent/request-error` 均为 waterfall。规则：

- 监听器接收 `(...args, next)`，调用 `next()` 委托后续处理；
- 不调用 `next()` 直接返回 = 短路，下游监听器不执行；
- 短路是设计意图（策略监听器持有决策权），仅做观察的监听器**必须**委托；
- 包装 `next()` 的监听器保留下游消息，除非有意替换。

## 事件域选择

| 场景 | 事件域 |
|---|---|
| 需要刷新、恢复、fork 后仍存在的事实 | `session/event`（会话事件） |
| 需要干预当前运行的 Agent | `agent/*` |
| 需要横切某项能力的策略 | `tools/*`、`fs/*`、`llm/*` 等能力事件 |
| 无需进入模型历史的人类控制 | `ctx.commands`（命令平面，非事件） |
