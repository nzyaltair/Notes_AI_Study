# 协作、竞争与任务分配

## 一句话理解

协作的关键是把可分解目标分配给能力互补的主体，并将局部结果整合为可验证的整体；竞争与博弈则用于建模资源冲突、谈判和对抗环境——MAS 中"什么时候协作、什么时候竞争"取决于任务结构、激励机制和环境约束。

## 概述

在 [[../01_理论与通信/01_MAS理论与通信|MAS 理论与通信]] 建立了通信和组织结构的基础后，MAS 面临的核心工程问题就是：**如何将任务分配给最合适的 Agent？** 以及**多个 Agent 应该在什么情况下协作、什么情况下竞争？**

协作产生"1+1>2"效应的前提是：Agent 的能力、信息或视角确实互补，且协作收益大于通信和协调成本。竞争发生在资源有限、目标冲突的场景中，需要博弈论和机制设计来推理最优策略。[[../00_Multi-Agent系统_综述|Multi-Agent 系统综述]] 提到"拆分 Agent 的前提是信息、工具或评估视角确实互补"，本笔记聚焦协作与竞争的具体机制和任务分配方法。

## 核心概念

### 协作的三种类型

- **共享目标协作**：所有 Agent 有完全相同的目标，协作是为了更快、更可靠地完成——如多个搜索 Agent 各自搜索不同来源
- **互补目标协作**：Agent 有不同子目标，但子目标组合起来实现全局目标——如编程 Agent 分工：架构师+开发者+测试
- **互惠协作**：Agent 帮助其他 Agent 完成目标，期望未来得到回报——如临时资源共享

### 竞争与博弈

MAS 中的竞争通常用博弈论建模（[[../../A_基础与范式/01_数学基础/13_博弈论与机制设计]]）：

- **零和博弈**：一方所得等于另一方所失，如资源竞争
- **非零和博弈**：可能存在共赢或共输，如协作中的激励设计
- **合作博弈**：Agent 可以形成联盟，联盟内部分配收益

## 技术原理

### 任务分配方法

**合同网协议（Contract Net Protocol）**：

```text
① 任务发布（Manager）：将任务描述广播给所有 Agent
② 竞标（Bidder）：Agent 评估自身能力并提交标书
③ 授标（Manager）：选择最优标书，授予任务
④ 执行（Bidder）：执行任务，提交结果
⑤ 验收（Manager）：验证结果，完成交易
```

合同网适合动态任务分配，Agent 的角色（Manager/Bidder）可以动态切换。

**集中训练-分散执行（CTDE）**：

CTDE 是 MARL 中的主流范式：训练时 Agent 可以访问全局信息（包括其他 Agent 的状态），学习协作策略；部署时每个 Agent 只使用自己的局部观察做决策，无需通信。代表方法：QMIX、MADDPG、MAPPO。

**市场机制**：

将任务分配视为"市场"：Agent 发布任务（购买服务）、竞标（出售服务）、价格信号调节供需。适合 Agent 能力动态变化、任务需求波动的场景。

### 协作的收益与成本

协作收益 = 单 Agent 无法完成的任务价值 + 并行带来的效率提升 + 交叉验证带来的质量提升

协作成本 = 通信 Token 消耗 + 协调延迟 + 冲突解决开销 + 额外系统复杂度

**协作的净收益 = 协作收益 - 协作成本 - 单 Agent 基线**

只有净收益为正时，多 Agent 协作才有意义。

### 协同规划

当多个 Agent 的计划存在依赖关系时（如 Agent A 的输出是 Agent B 的输入），需要协同规划来协调时序、资源和依赖关系：

- **共享计划**：所有 Agent 共享一个完整计划，各自负责自己的部分
- **部分计划交换**：Agent 只交换与自身计划相关的部分，不共享全部计划
- **增量式规划**：Agent 逐步调整计划，根据其他 Agent 的反馈动态适应

## 关键方法与模型

| 方法 | 机制 | 适用场景 |
|:---|:---|:---|
| 合同网 | 任务发布-竞标-授标 | 动态任务分配，能力标签明确 |
| 协同规划 | 共享约束与依赖 | 子任务有依赖关系 |
| CTDE (QMIX/MAPPO) | 集中训练+分散执行 | 部分可观测，连续决策 |
| 市场拍卖 | 价格信号调节 | 资源竞争，供需波动 |
| 博弈论 | 策略推理 | 对抗性场景，谈判 |

## 优势与局限

**协作的优势**：可以覆盖单 Agent 无法完成的任务；并行提升效率；多视角交叉验证提升质量。

**协作的局限**：通信成本抵消并行收益；高度耦合的任务拆分后可能增加协调成本、降低质量；Agent 能力互补不充分时，协作收益有限。

**竞争的优势**：通过竞争选出最优方案；激励 Agent 提升自身能力。

**竞争的局限**：可能造成资源浪费（重复劳动）；竞争失败者可能被排斥，降低系统整体能力。

## 应用场景

- **多 Agent 编程**：架构师 Agent（高层设计）+ 开发者 Agent（编码）+ 测试 Agent（验证）
- **多 Agent 搜索**：多个搜索 Agent 并行搜索不同数据源，文摘 Agent 汇总
- **多 Agent 仓储**：搬运 Agent 和拣选 Agent 协作完成订单
- **多 Agent 辩论**：多个 Agent 从不同角度分析问题，通过辩论达成共识

## 前沿发展

- **自动任务分解**：LLM 自动将任务分解为子任务，并分配合适的 Agent
- **学习最优通信结构**：Agent 通过 RL 学习何时需要通信、与谁通信
- **动态角色分配**：Agent 角色不再固定，根据任务需求动态调整
- **协作效率度量**：开发标准化指标衡量协作增益，指导多 Agent 系统设计

## 常见问题

**Q: 什么时候应该用多 Agent 而不是单 Agent？**
当满足以下条件之一时考虑多 Agent：任务需要多种互补能力（一个 Agent 无法全部拥有）；任务可以自然地并行分解；需要多个独立视角交叉验证结果；系统的容错性要求高（单点故障不允许）。

**Q: 多 Agent 为什么会比单 Agent 差？**
常见原因：通信成本过高抵消了并行收益；任务高度耦合，拆分后协调成本超过单 Agent 处理成本；Agent 分工不明确，导致重复劳动或冲突；所有 Agent 共享相同的数据/模型先验，出现"多数幻觉"。
