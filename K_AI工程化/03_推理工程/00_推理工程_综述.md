# 推理工程综述

## 一句话理解

推理工程把训练好的模型以可预测的延迟、吞吐、成本和可靠性交付给应用。LLM 的 prefill/decode 分离、KV Cache 显存压力和动态请求调度，使其成为区别于传统模型部署的独立工程领域。

## 1. 领域定义

推理工程（Inference Engineering）关注：

- **服务化**：将模型封装为多租户、流式、可弹性伸缩的 HTTP/gRPC 服务
- **调度**：高效利用 GPU 时间和显存，处理并发请求
- **优化**：通过量化、编译、算子融合等手段降低延迟和成本
- **部署**：在云端、边缘和本地不同环境安全稳定地运行模型

与训练工程（最大化吞吐、数天级任务）不同，推理工程需要同时满足延迟 SLA、高并发、成本约束和可用性要求。

## 3. LLM 推理特性与挑战

### 3.1 Prefill vs Decode

LLM 推理分为两个截然不同的阶段：

| 阶段 | 特性 | 瓶颈 | 关键指标 |
|:---|:---|:---|:---|
| **Prefill**（处理输入） | 并行处理所有输入 Token，计算密集 | GPU 算力 | 首 Token 延迟 (TTFT) |
| **Decode**（逐 Token 生成） | 每步只生成 1 个 Token，访存密集 | KV Cache 带宽 | 每 Token 延迟 (TPOT) |

这一分离导致 LLM 服务的 GPU 利用率远低于训练（推理 ~5-15%），是优化的主要目标。

### 3.2 KV Cache 显存压力

每个 Token 需要缓存所有层的 Key/Value：

```
KV-Cache Size = 2 × n_layers × n_kv_heads × d_head × seq_len × dtype_size
```

LLaMA-3-70B (FP16) 约 320 KB/token；批处理 64 请求、上下文 4096 时，KV Cache 超过 80 GB。显存容量而非算力是 LLM 推理的核心瓶颈。

### 3.3 动态调度难点

- 请求生成长度不可预测，导致资源利用不均
- 静态批处理浪费显存和 GPU 时间
- KV Cache 碎片化降低最大并发数

## 4. 主要技术分支

### 4.1 高吞吐调度

- **连续批处理（Continuous Batching）**：请求完成即释放，新请求动态加入，消除队头阻塞
- **PagedAttention**：OS 分页机制管理 KV Cache，消除碎片，吞吐提升 2-4x
- **前缀缓存（Prefix Caching）**：共享相同系统提示的 KV Cache，减少重复计算
- **Chunked Prefill**：将长 Prefill 切块，与 Decode 交错执行，降低 TTFT

### 4.2 量化与压缩

| 技术 | 精度 | 特点 |
|:---|:---|:---|
| INT8 (W8A8) | 8-bit 权重+激活 | 无精度损失，2x 加速 |
| GPTQ | 4-bit 权重 | PTQ，消费级 GPU 可用 |
| AWQ | 4-bit 权重 | 激活感知，精度更好 |
| FP8 | 8-bit 浮点 | H100 原生支持 |
| GGUF/llama.cpp | 多精度 | CPU 友好，本地部署 |

### 4.3 推理框架生态

| 框架 | 核心特性 | 适用场景 |
|:---|:---|:---|
| vLLM | PagedAttention、连续批处理、OpenAI 兼容 API | 高吞吐 LLM 服务 |
| TensorRT-LLM | NVIDIA 内核级优化、FP8 | 生产低延迟推理 |
| SGLang | RadixAttention、结构化生成 | Agent/Tool Calling |
| llama.cpp | CPU/GPU 混合、GGUF 量化 | 本地/边缘部署 |
| TGI | Rust 内核、HuggingFace 生态 | 标准化部署 |

### 4.4 投机解码

小模型（Draft Model）生成多个候选 Token，大模型并行验证，将 Arithmetic Intensity 从 ~1 提升至 ~k，GPU 利用率显著提高。延迟降低 2-3x，无精度损失。

### 4.5 模型格式与转换

训练框架（PyTorch）与推理引擎（TensorRT/ONNX）之间需要格式转换。ONNX 作为中间表示跨框架部署；TensorRT Engine 为 NVIDIA 硬件优化；GGUF 为本地 CPU 推理优化。

### 4.6 云端与本地部署

- **云端**：弹性伸缩、托管 GPU、Serverless LLM（按请求计费）
- **边缘/本地**：Ollama、llama.cpp、端侧 NPU 量化部署

## 5. 关键性能指标

| 指标 | 含义 | 典型目标 |
|:---|:---|:---|
| TTFT | 首 Token 延迟（从发送请求到收到第一个 Token） | < 200ms (在线) |
| TPOT | 每 Token 生成延迟 | < 50ms/token |
| E2E Latency | 端到端延迟 | 与输出长度相关 |
| Throughput | tokens/s（系统级） | 取决于 GPU 型号和配置 |
| GPU Utilization | GPU 计算利用率 | > 50% 为健康 |
| Cost/Token | 每 Token 的计算成本 | 需要与业务价值对比 |

容量规划需按输入/输出长度分布、并发数、缓存命中率和 SLA 估算，不能只看 QPS。

## 8. 前沿发展

- **Disaggregated Serving**：Prefill 节点与 Decode 节点分离，独立弹性扩展（Mooncake、DistServe）
- **Speculative Decoding 规模化**：Eagle、Hydra 等高效 Draft 模型让投机解码生产可用
- **KV Cache 卸载与压缩**：CPU/SSD 卸载突破显存限制；KV Cache 量化降低显存占用
- **多 LoRA 动态服务**：单基础模型同时服务数百个 LoRA 适配器（S-LoRA）
- **MoE 推理优化**：专家路由批处理、Expert Offloading 处理大规模稀疏模型
- **FP4 推理**：NVIDIA Blackwell B200 原生 FP4 支持，推理速度再翻倍
- **Serverless LLM**：按请求计费、冷启动优化（模型权重缓存、快照恢复）
