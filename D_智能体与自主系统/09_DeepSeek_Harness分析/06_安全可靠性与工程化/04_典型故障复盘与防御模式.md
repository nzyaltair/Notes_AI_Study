# 典型故障复盘与防御模式

## 一句话理解

DSH 的可靠性规则来自生命周期、并发、子进程与清理中的真实失效类型；设计时应将独立事实分开报告、明确异步边界，并让 dispose 等到完全停稳。

## 六条核心防御规则

### 规则一：正交结果独立上报

进程可能已经超时，却仍以退出码 0 结束（因为它捕获了终止信号）。每个独立事实（`timedOut`、`signal`、`exitCode`）都应单独上报；**绝不把一个标志的上报嵌套在另一个标志的分支中**，否则调用方可能把提前终止的运行误判为正常成功。

### 规则二：公共约定两侧都要遵守

当一个实现收到同一结果的多种表示时，应在通过公共 API 返回前规范化。`LlmAdapter.stream()` 的实现可以抛出异常或发出 `finish {kind:'error'|'aborted'}`，但 `LlmRuntime.stream()` 只通过终止型 finish 分片暴露请求失败；middleware 缺陷与消费方缺陷仍以异常形式抛出。这使消费方不必猜测异常来自提供方、包装层还是自身。**在类型定义处记录规范化后的约定；通过真实消费方覆盖每种来源形式。**

### 规则三：异步状态不是同步状态

`agent.followup()` 没有逐消息的完成状态或结果；后台任务的完成与轮次边界存在竞争；`reader.close()` 在 EOF 和 dispose 两种情况下都会触发。**切勿把 `agent/status` 或 `whenIdle()` 当作某次 `followup()` 的结果**：多条已排队的后续消息、steering 和注入工作可能共用同一个 `running` 区间，取消或 dispose 可能丢弃尚未启动的项。真正拥有一次运行的自动化调用方必须显式定义区间（从消息入队回执到整个 agent 下一次进入 idle），并将选取的输出描述为整个区间的输出。等待的转换永远不会发生时应显式处理「无需等待」的分支，否则会挂起。

### 规则四：dispose 必须达到完全停稳，而不仅仅是请求停止

清理流程只发出终止或中止信号便返回，而不等待工作真正停止，就会留下孤儿进程。**清理逻辑应采用异步流程，等待子进程退出（发出终止信号后等待 `done`）；还应在终止进程前关闭监听器注册表和通知注册表**，使迟到的完成事件保持静默。

### 规则五：在分发器中隔离回调异常

用户提供的监听器如果抛出异常，不得导致它所在的 promise 被 reject，也不得饿死排在它后面的监听器。**用 try/catch 包裹分发循环并记录日志；一个行为不当的订阅者绝不能破坏核心生命周期。**

### 规则六：绝不将环境变量或可预测路径暴露给不可信输出

启动的命令应使用经过清理的环境变量，移除名称匹配 `*KEY*`、`*SECRET*`、`*TOKEN*` 或 `*PASSWORD*` 的项，防止凭证通过命令输出、`env` 或 spill 文件泄漏。**临时文件和 spill 文件应放在权限为 0700 的私有目录中，使用随机文件名，并以独占且仅所有者可访问的方式打开（`'wx'`、`0o600`）**；可预测且全局可读的路径会引发符号链接竞态和信息泄露。

> 附加规则：可能是符号链接或 Windows junction 的路径，应先用 `lstatSync().isSymbolicLink()` 判断，再用 `unlinkSync` 删除（unlink 只删除链接本身，绝不跟随链接进入其目标；真实目录才使用带 `recursive` 的 `rmSync`）。

## 从防御模式到测试

| 风险 | 防御规则 | 测试验证方式 |
|---|---|---|
| 超时但退出码为 0 | 独立上报 `timedOut`/`signal`/`exitCode` | 单元测试：覆盖每种来源组合 |
| 同一失败多种表示 | 在公共 API 边界规范化 | 通过真实消费方断言规范化后的约定 |
| 把 idle 当单条消息结果 | 显式定义运行区间 | e2e：从入队回执到 idle 的完整区间 |
| 清理只发停止信号 | 等待进程/任务真正结束 | 测试 dispose 后注册消失（HMR 安全测试） |
| 订阅者异常破坏分发 | 隔离回调异常 | 注入抛出异常的监听器，断言后续监听器仍执行 |
| 凭据泄露或临时文件竞态 | 清理环境变量；私有随机目录 | e2e：断言 spill 文件路径不可预测 |
| 删除链接穿透目标 | 先 `lstat` 再 `unlink` | 单元测试：符号链接删除不影响目标 |

每条防御规则都应有能重新引入回归并失败的测试。单元测试全绿不代表产品路径正确；插件导出、文件系统工具、GUI 当前状态与子进程失败分类等跨边界问题，需要真实组合测试覆盖。

## 四个典型事故复盘

以下四个案例来自 DSH 事故复盘（postmortem）系列，每条规则背后都有真实失败。它们是防御规则的来源依据，也是"单元测试全绿但产品坏了"的经典样本。

### 事故 0001：`export default` 丢弃了插件的 `inject`

**摘要**：ACP 服务器在真实 Zed 编辑器连接时立即崩溃，报错 `cannot get property "agents" without inject`。176 个单元测试全绿、100% 覆盖率，但 bridge 在生产环境完全无法工作。

**根因**：`packages/acp/acp/src/index.ts` 多了一行 `export default apply`。Cordis Loader 的 `unwrapExports` 逻辑优先解析 `.default`，从而把整个模块命名空间丢弃了，`inject`/`name`/`Config` 全部消失。`apply` 在没有任何注入服务的 fiber 中运行，第一次访问 `ctx.agents` 就崩溃。

**第二个根因**：`session/load` 崩溃在 `sessionPersistence`——这是不同机制：`AgentLoop` 通过 shadow 上下文的可追踪代理访问未注入的可选服务时，Cordis 的 fiber 遍历**只向祖先方向**，无法找到位于兄弟分支的提供方，到达 root 后抛错。而测试从顶层直接调用时走的是绕过拓扑的 `reflect.get(name, false)` 路径，因此测试全通过但产品必崩。

**防护措施**：
- 命名空间插件（`name`/`inject`/`Config`/`apply`）绝不添加 `export default apply`；
- 对机会性读取但未在 `static inject` 中声明的服务，使用 `ctx.get('serviceName')`，而非 `ctx.<name>`（属性代理走 fiber 遍历，`ctx.get` 走拓扑无关的 isolate-keyed 查找）；
- 产品可见插件至少一个测试必须经 Loader 的真实导入路径加载，而不是手工 `ctx.plugin({...})`。

**教训**：100% 行覆盖率证明代码被执行过，不证明功能按交付方式正常工作。相信跟踪结果，不要迷信理论。

### 事故 0002：`!!js` 对象永久禁用了文件系统工具

**摘要**：ACP 示例用 `disabled: !!js ...` 试图有条件地启用文件系统插件，但 Cordis 仅对插件 `config` 内的字段进行 JS 表达式插值，不对 `disabled` 字段求值。原始表达式对象为 truthy，因此文件系统栈始终被禁用。快照刷新随后将 `UNKNOWN_TOOL` 结果作为新的预期输出接受了下来。

**根因**：`Entry._resolveConfig()` 对 `entry.options.config` 进行插值，但 `Entry.disabled` 直接读取 `entry.options.disabled`，不经插值。YAML 标签语法合法，加载过程不产生任何诊断信息。快照框架把任何确定性的 transcript 都视为有效行为，刷新时语义断言在 `UNKNOWN_TOOL` 被拒绝之前就已重写了 fixture。

**防护措施**：
- `!!js` 仅在插件 `config` 内有效；条件式组合应使用 overlay（专门的 `.cordis.yml`），而非 `disabled` 字段表达式；
- 静态分析工具 `verify-cordis-config` 拒绝 Loader 配置项元数据中的表达式节点；
- 快照套件在全新运行和已提交 fixture 中拒绝结构化的 `UNKNOWN_TOOL` 结果，防止其被当作预期输出提交。

**教训**：快照刷新是 fixture 生产过程，不是正确性审查；诸如已注册工具缺失这类语义上不可能的结果，需要独立于预期输出的断言。

### 事故 0003：Web Agent 验收了替代服务器，而非承载其会话的 GUI

**摘要**：Web agent 修改了 GUI 源码，却在裸 Vite 返回 HTTP 200 的情况下宣布成功（彼时 `window.__DSH_BOOT__` 缺失、白屏）；最终在端口 3334 启动了一个不受管理的替代服务器并验收，而用户原本在 3081 端口的页面早就已经通过构建重载生效。

**根因**：Web 组合没有向模型提供当前 GUI 的规范 URL 和运行模式信息。HTTP 就绪、构建成功、启动 manifest 存在是三个不同事实，不能互相替代。Agent 通过 shell `&` 绕过了后台进程语义，任务身份、完成通知和清理机制均未生效。

**防护措施**：
- Web 启动器在日志区段和 `$DSH_WEB_URL`/`$DSH_WEB_MODE` 环境变量中发布规范环回 URL 和实际模式；
- `apps/web` 的独立 Vite 服务模式在配置阶段拒绝启动（验证 `window.__DSH_BOOT__` 注入的完整性）；
- 验收必须明确指定确切 origin，并从外部观察改动是否在该 origin 生效，而不是检查替代服务。

**教训**：HTTP 就绪、构建成功和启动 manifest 是不同事实；替代服务无法证明既有页面已改变；确实收到启动长时间运行进程请求时，应使用受管任务生命周期。

### 事故 0004：Landlock 部分强制执行通知导致子进程失败被误归类

**摘要**：在 Landlock ABI 较旧的内核上，launcher 在执行每个子进程前打印无害的 `landlock-run: partial enforcement (older Landlock ABI)` 通知。harness 把这个前缀与任意非零退出组合，误判为 launcher 失败，于是 ripgrep 无匹配时的退出码 1 等合法结果呈现为 `SANDBOX_UNAVAILABLE`。

**根因**：公开的沙箱结果类型仅能表达一组子字符串签名，无法区分「信息性通知」与「致命诊断」——两者共享 `landlock-run:` 前缀，但只有致命诊断伴随退出码 125。测试矩阵与这种表示方式一致：真实 Landlock 测试依赖主机 ABI，完整 ABI 的主机无法覆盖部分通知的情况。

**防护措施**：
- `RunnerFailureRule` 携带可选的允许退出码、逐行致命签名，以及按整行精确匹配排除的信息性行；
- `dsh-sandbox-local` 把 Landlock 映射为退出码 125 加一行非通知的致命诊断，精确区分两类行；
- 原生边界回归用例（`partial-landlock.spec.ts`）覆盖信息性通知、致命证据和前台/后台分类；组装后的产品路径由快照组合固定。

**教训**：进程归因需要多项独立证据同时成立；信息性诊断与致命诊断可以共享命名空间，因此排除规则必须精确且范围狭窄；平台相关行为需要在原生边界放置确定性模拟实现。
