# AI 可靠性工程综述

## 一句话理解

AI Reliability Engineering 将 SRE 的可用性实践与模型不确定性、数据漂移和外部工具风险结合——它保证系统不仅在线，而且在错误输入、依赖故障和模型退化时能以可预测的方式安全降级。

## 1. 领域定义

AI 可靠性工程关注：

- **服务可用性**：系统在约定 SLA 内可用并响应
- **模型质量持续性**：模型输出质量不悄然退化
- **安全降级**：外部依赖失败时系统行为可预测
- **事件响应**：快速识别、定位和恢复故障

与传统 SRE（关注服务在线率）不同，AI 系统还面临：模型输出不确定性、数据/概念漂移、外部工具失败的链路放大、提示注入等 AI 特有风险。

## 2. 发展历史

| 时间 | 里程碑 | 意义 |
|:---|:---|:---|
| 2003 | Google SRE 实践 | SLI/SLO/错误预算框架建立 |
| 2016 | *Site Reliability Engineering* 出版 | SRE 实践标准化 |
| 2019 | ML 系统可靠性开始关注 | 数据漂移检测、模型监控成为独立领域 |
| 2022 | LLM 生产部署 | 非确定性输出、幻觉、越狱等新型故障模式出现 |
| 2023 | Agent 系统可靠性 | 工具调用失败的级联效应、长任务中断恢复 |
| 2024 | AI SRE 形成 | AI 特有可靠性实践逐步形成独立框架 |

## 3. 核心概念

### 3.1 SLI / SLO / 错误预算

- **SLI（Service Level Indicator）**：实际测量的服务指标（延迟、成功率、质量）
- **SLO（Service Level Objective）**：SLI 的目标值（P99 延迟 < 2s，成功率 > 99.9%）
- **错误预算**：1 - SLO，允许的"不达标"空间，用于平衡可靠性与迭代速度

AI 系统需为多个维度定义 SLO：

| SLO 类型 | 示例目标 |
|:---|:---|
| 服务可用性 | > 99.9%（月均停机 < 43 分钟） |
| P99 TTFT | < 2 秒 |
| 任务成功率 | > 95%（Agent 任务完成） |
| 输出质量 | 在线评测得分 > 基线 95% |
| 安全拦截率 | 有害内容拒答率 > 99.5% |

### 3.2 AI 特有故障模式

| 故障类型 | 描述 | 检测方法 |
|:---|:---|:---|
| 模型退化 | 更新模型后质量下滑 | 在线质量监控 + A/B 对比 |
| 数据漂移 | 用户输入分布偏离训练分布 | 统计检验（KS test、MMD） |
| 概念漂移 | 同样输入的正确答案随时间变化 | 人工标注对比 |
| 幻觉增加 | 模型开始生成更多虚假信息 | 事实核验评测 |
| 上下文长度溢出 | 请求超出 context window | 输入长度监控 + 自动截断 |
| 工具调用失败 | 外部 API/工具不可用 | 工具调用错误率监控 |
| Prompt 注入 | 用户输入覆盖系统指令 | 安全过滤 + 意图检测 |

## 4. 容错设计模式

### 4.1 基础容错模式

| 模式 | 作用 | AI 场景 |
|:---|:---|:---|
| **超时** | 防止慢请求阻塞 | LLM 生成超时 → 截断或放弃 |
| **重试** | 处理瞬时失败 | 幂等推理请求 3 次重试 |
| **熔断** | 防止级联故障 | LLM API 不可用时停止调用 |
| **限流** | 保护服务容量 | 按用户/团队限制 token/分钟 |
| **降级** | 用简化服务替代完整服务 | 主模型不可用 → 小模型替代 |
| **隔离** | 防止故障传播 | Agent 工具执行在沙箱中 |
| **缓存** | 减少对下游的依赖 | 语义缓存相似查询结果 |

### 4.2 AI 特有降级策略

AI 系统降级时必须保持**安全**：

```text
正常路径:  用户请求 → RAG 检索 → LLM 生成 → 带引用的答案
             ↓ 检索服务故障
降级路径1: 用户请求 → LLM 生成（无上下文）+ 声明"知识可能不完整"
             ↓ LLM 服务故障
降级路径2: 用户请求 → 小模型或缓存答案 + 声明"服务受限"
             ↓ 完全不可用
降级路径3: 用户请求 → 静态提示"服务暂时不可用，请稍后重试"
```

原则：**宁可明确告知能力受限，也不伪造确定答案**。

### 4.3 Agent 特有容错

- **显式停止条件**：最大步数、最大时间、最大成本
- **任务持久化**：中断后可从检查点恢复
- **人工接管**：高风险操作或连续失败后转人工
- **幂等工具设计**：工具调用失败可安全重试

## 5. 模型失败与漂移处理

### 5.1 漂移检测方法

- **输入漂移**：监控输入 token 长度分布、词汇分布、嵌入空间分布
- **输出漂移**：监控输出长度分布、情感极性、拒绝率变化
- **性能漂移**：与历史基准相比的在线评测指标变化
- **统计检验**：KS Test（单变量分布比较）、MMD（高维分布比较）

### 5.2 回滚决策

```text
检测到质量下降
    ↓
确认是模型变更、Prompt 变更还是数据漂移
    ↓
模型变更导致 → 回滚到上一版本
Prompt 变更导致 → 回滚 Prompt
数据漂移导致 → 评估是否需要重新训练/微调
```

## 6. 事件响应与恢复

### 6.1 事件响应流程

```text
告警触发（自动检测）
    ↓
On-Call 确认（5 分钟内）
    ↓
初步影响评估（P0/P1/P2/P3 定级）
    ↓
临时缓解（降级、限流、回滚）
    ↓
根因分析
    ↓
永久修复 + 事后回顾（Post-mortem）
```

### 6.2 Runbook 要求

每个告警规则必须绑定 Runbook，包含：
- 告警含义解释
- 初步诊断步骤
- 常见根因与对应处置
- 升级路径（谁来处理）
- 影响评估方法

## 9. 前沿发展

- **自愈系统**：基于监控指标自动触发扩容、回滚或降级，减少人工介入
- **混沌工程（Chaos Engineering）**：主动注入故障验证系统韧性
- **AI 系统合规性**：EU AI Act 要求的可靠性文档和风险评估
- **多智能体可靠性**：协作 Agent 系统的故障隔离和一致性保证
- **LLM 防御**：提示注入检测、越狱防御的工程化实践
