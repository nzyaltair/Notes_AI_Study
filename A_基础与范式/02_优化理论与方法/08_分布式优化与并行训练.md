# 分布式优化与并行训练

## 1. 概述

分布式优化与并行训练是 [[00_大语言模型核心架构_综述|大语言模型]] 训练的工程基础。当单个 GPU 无法容纳整个模型或训练速度无法满足需求时，需要将训练过程分布到多个 GPU 甚至多个节点上。并行策略包括数据并行、模型并行（张量并行、流水线并行）以及它们的组合（3D 并行）。ZeRO 和 FSDP 等技术进一步模糊了数据并行和模型并行的边界，成为大模型训练的标准方案。

## 2. 发展历史

| 年代 | 里程碑 | 意义 |
|------|--------|------|
| 2012 | Parameter Server (Dean et al.) | Google DistBelief 分布式训练框架 |
| 2015 | All-Reduce 并行 (Baidu) | Ring All-Reduce 成为标准 |
| 2016 | Layer-Parallel / Pipeline (PipeDream) | 流水线并行原型 |
| 2019 | Megatron-LM (NVIDIA) | 张量并行训练大模型 |
| 2019 | GPipe (Google) | 同步流水线并行 |
| 2019 | ZeRO (Microsoft) | 零冗余数据并行 |
| 2020 | FSDP (PyTorch) | 原生完全分片数据并行 |
| 2021 | Megatron-LM 3D 并行 | 数据 + 张量 + 流水线组合 |
| 2022 | DeepSpeed Ulysses | 高效序列并行 |
| 2023 | Ring Attention | 跨设备长序列分布式注意力 |

## 3. 硬件架构差异：TPU vs GPU

理解并行策略选择的前提是理解不同硬件平台在网络拓扑上的根本差异，这直接决定了哪种并行策略能高效运行。

| 平台 | 拓扑结构 | 特点 | 适用场景 |
|------|---------|------|----------|
| **TPU** | 环形网格（Torus/Mesh） | 每个芯片只连邻居，邻居首尾相接；扩展时邻居数不变 | 密集模型（TP）、点对点通信 |
| **GPU** | 胖树（Fat Tree） | 全对全模式，底层 NVLink 极快，上层交换机逐级扩展 | 灵活的全互联通信 |

**关键差异**：
- TPU 的环形网格用极简拓扑实现无限扩展，邻居数恒定，适合高度规则的通信模式（如张量并行）
- GPU 的胖树随节点增加，通信成本和拓扑复杂度上升，但更灵活
- **演进趋势**：随着 MOE 成为主流，token 路由需要更彻底的全互联。Google TPU 也开始采用更偏向 All-to-All 的树状拓扑（如 IronIC、VERAL 网络），向 GPU 靠拢

**华为 Ascend 910B 方案**：用光纤交换机连接 384 个芯片装在一个大机架内，单芯片性能虽不如 H200，但通过蛮力扩展更多芯片来弥补，代价是功耗约为 NVIDIA 系统的 4 倍。这展示了硬件设计中"省电好造"与"蛮力硬解"两种截然不同的权衡。

**核心启示**：工作负载（密集 vs MOE）决定了网络需求，网络拓扑决定了并行策略选择，不同硬件平台的最优并行配置可能截然不同。

## 4. 核心概念

- **数据并行**：每个 GPU 持有完整模型副本，处理不同数据子集，梯度同步后统一更新
- **模型并行**：模型本身被切分到多个 GPU 上
  - **张量并行**（Tensor Parallelism）：将单个矩阵乘法切分到多个 GPU
  - **流水线并行**（Pipeline Parallelism）：将不同层分配到不同 GPU，数据流水通过
- **3D 并行**：数据并行 + 张量并行 + 流水线并行的组合
- **All-Reduce**：多 GPU 间的集合通信原语，将所有 GPU 的梯度求和并广播
- **通信-计算重叠**：将梯度同步通信与计算重叠以隐藏通信延迟

### 并行度的关系

| 维度 | 切分对象 | 典型规模 |
|------|---------|---------|
| 数据并行 | Batch | 数十~数千 GPU |
| 张量并行 | 矩阵维度 | 通常 2-8 GPU（受 NVLink 限制） |
| 流水线并行 | 模型层数 | 4-16 级 |
| 序列并行 | 序列长度 | 2-8 GPU |

### 集合通信原语详解

分布式训练的基础构建块是集合通信（Collective Communication）原语。这些原语并非为 LLM 训练而发明，而是源自 1980 年代的并行编程传统，指定跨多设备的通用通信模板，而非管理点对点通信。

**基本术语**：一组参与通信的设备称为 **ranks**，每个 rank 对应一个设备（GPU/TPU），设备总数称为 **world size**。

| 操作 | 说明 | 在训练中的用途 |
|------|------|---------------|
| **Broadcast** | 一个 rank 的数据复制到所有 rank | 初始化阶段广播检查点 |
| **Scatter** | 一个 rank 的张量切分后分发给各 rank | 理解 Reduce-Scatter 的基石 |
| **Gather** | 各 rank 的数据片段汇聚到一个 rank | 理解 All-Gather 的基石 |
| **Reduce** | 各 rank 的数据执行规约（sum/max），结果放在一个 rank | 理解 All-Reduce 的基石 |
| **All-Gather** | 对所有 rank 执行 Gather，每个 rank 都获得完整数据 | ZeRO-3 前向参数收集、TP 前向激活汇聚 |
| **Reduce-Scatter** | 对每个维度执行 Reduce，结果 Scatter 到各 rank | ZeRO-3 梯度切分、TP 反向梯度分发 |
| **All-Reduce** | 对所有 rank 执行 Reduce，结果复制到所有 rank | DDP 梯度同步 |
| **All-to-All** | 每个 rank 向其他每个 rank 发送特定数据 | MoE 专家路由 |

**关键关系**：

$$\text{All-Reduce} = \text{Reduce-Scatter} + \text{All-Gather}$$

这个分解是理解 ZeRO/FSDP 的核心——通过将 All-Reduce 拆分为两个步骤，可以在中间插入参数分片逻辑。

**All-to-All** 在负载均衡时本质上是一次矩阵转置：每个 rank 持有数据的一个切片和一组专家子集，通过 All-to-All 将数据路由到对应专家所在设备。

## 5. 技术原理

### 5.1 数据并行（Data Parallelism）

**基本流程**：

1. 每个 GPU 持有完整模型副本
2. 将 mini-batch 均分到各 GPU
3. 各 GPU 独立前向+反向计算梯度
4. All-Reduce 同步梯度（求平均）
5. 各 GPU 独立执行相同的优化器更新

```
GPU 0: [Batch 0] → Model → Grad 0 ─┐
GPU 1: [Batch 1] → Model → Grad 1 ─┤ All-Reduce → 平均梯度
GPU 2: [Batch 2] → Model → Grad 2 ─┤
GPU 3: [Batch 3] → Model → Grad 3 ─┘
                                     ↓
                              各 GPU 更新参数
```

**Ring All-Reduce**：GPU 排成环形，每步与邻居交换部分梯度，$K$ 个 GPU 需 $2(K-1)$ 步完成。通信量为 $\frac{2(K-1)}{K} \cdot |\text{grad}|$，与 GPU 数 $K$ 近似无关。

**PyTorch DDP 实现**：

```python
from torch.nn.parallel import DistributedDataParallel as DDP

model = Model().cuda()
model = DDP(model, device_ids=[local_rank])
# 自动梯度同步
```

### GPU 互联硬件拓扑

理解并行策略选择的前提是理解 GPU 之间的物理连接方式，因为通信带宽直接决定策略可行性。

| 层级 | 互联方式 | 特点 | 典型带宽 |
|------|---------|------|----------|
| 单节点内 | NVLink + NVSwitch | GPU 间直连，任意 GPU 对均可直接通信 | NVLink5: ~900 GB/s |
| 跨节点 | InfiniBand (IB) | 专用网络，支持 RDMA | ~400 GB/s |
| 跨 Pod | Ethernet | 通用网络，延迟高、带宽低 | 视配置而定 |

**关键概念**：
- **RDMA（Remote Direct Memory Access）**：GPU 直接读写另一 GPU 的内存，无需 CPU 介入，大幅降低延迟。NVLink/NVSwitch 和 InfiniBand 均支持 RDMA
- **RoCE（RDMA over Converged Ethernet）**：基于融合以太网实现 RDMA，是以太网对标 InfiniBand 的替代方案，Meta 在 LLaMA 训练中可能使用了 RoCE
- **NVL72**：NVIDIA 为 B200/B300 推出的产品，将 72 个 GPU（9 个托盘 × 8 GPU/托盘）全部接入同一 NVLink 域，远超普通 8 GPU 节点的 NVLink 范围

**拓扑层次与延迟关系**：
```
L1/L2 Cache → Shared Memory → HBM → NVLink → InfiniBand → Ethernet
\_________________________/    \_____________________________/
        单 GPU 内部                    多 GPU 之间
```

随着 GPU 数量增长，必须从 NVSwitch 域扩展到 InfiniBand Pod 再到 Ethernet，带宽逐层下降。选择并行策略时必须匹配此拓扑：
- **张量并行**：通信频繁且大流量，限在 NVLink 域内（通常单节点 8 GPU 或 NVL72）
- **流水线并行**：点对点通信，容忍较高延迟，可跨节点使用 InfiniBand
- **数据并行**：All-Reduce 通信量大但可重叠计算，适合最外层跨节点扩展

### NCCL 与 torch.distributed

**NCCL（NVIDIA Collective Communications Library）** 是底层通信库，负责将高层集合操作（All-Reduce、Reduce-Scatter 等）转换为实际的 GPU 间数据传输。NCCL 会分析硬件拓扑结构，确定最优通信路径（环形或树形），并启动通信 kernel。

**torch.distributed** 是 PyTorch 提供的分布式编程接口，封装了集合通信原语：

```python
import torch.distributed as dist

# 初始化进程组
# 后端选择：GPU 用 NCCL，CPU 用 Gloo

dist.init_process_group(backend="nccl", init_method="env://")

# All-Reduce 示例
dist.all_reduce(tensor, op=dist.ReduceOp.SUM)
# 就地写入，结果在所有 rank 上一致

# Reduce-Scatter 示例（非就地，需要输出缓冲区）
dist.reduce_scatter(output_tensor, input_list, op=dist.ReduceOp.SUM)

# All-Gather 示例
dist.all_gather(output_list, input_tensor)

# 同步屏障
rank = dist.get_rank()
world_size = dist.get_world_size()
```

**异步通信**：设置 `async_op=True` 可使集合操作立即返回，允许计算与通信重叠。完成后通过 `wait()` 或 `barrier()` 确认完成。

```python
# 异步执行 All-Reduce
handle = dist.all_reduce(tensor, op=dist.ReduceOp.SUM, async_op=True)
# ... 执行其他独立计算 ...
handle.wait()  # 等待通信完成
```

### 通信带宽基准测试

**有效带宽**计算公式（以 All-Reduce 为例）：

$$\text{Bandwidth} = \frac{\text{数据大小} \times 2 \times (\text{world\_size} - 1)}{\text{world\_size} \times \text{持续时间}}$$

- 因子 2：发送 + 规约各一次
- 因子 $(\text{world\_size} - 1) / \text{world\_size}$：Ring All-Reduce 需要 $K-1$ 步
- 当 world size 增大时，$(K-1)/K \to 1$，带宽近似独立于 GPU 数量

**关键结论**：
- All-Reduce = Reduce-Scatter + All-Gather，因此 All-Reduce 移动两倍数据量，但耗时也约两倍，两者有效带宽相近
- 带宽独立于拓扑结构（环形或树形由 NCCL 自动确定）

**同步 vs 异步**：
- **同步 SGD**：等待所有 GPU 完成再更新，等价于大 batch SGD
- **异步 SGD**：不等待，使用陈旧梯度更新，吞吐更高但可能收敛差

### 5.2 张量并行（Tensor Parallelism）

将单个矩阵乘法 $\mathbf{Y} = \mathbf{X}\mathbf{W}$ 切分到多个 GPU：

**列切分**（Column Parallel）：

$$\mathbf{W} = [\mathbf{W}_1, \mathbf{W}_2, \dots, \mathbf{W}_K]$$

$$\mathbf{Y} = [\mathbf{X}\mathbf{W}_1, \mathbf{X}\mathbf{W}_2, \dots, \mathbf{X}\mathbf{W}_K]$$

每个 GPU 计算输出的不同列，前向无需通信，反向需要 All-Reduce。

**行切分**（Row Parallel）：

$$\mathbf{W} = \begin{bmatrix} \mathbf{W}_1 \\ \mathbf{W}_2 \\ \vdots \\ \mathbf{W}_K \end{bmatrix}, \quad \mathbf{X} = [\mathbf{X}_1, \mathbf{X}_2, \dots, \mathbf{X}_K]$$

$$\mathbf{Y} = \sum_{i=1}^K \mathbf{X}_i \mathbf{W}_i$$

前向需要 All-Reduce，反向无需通信。

**Megatron-LM 的 MLP 层**：交替使用列切分和行切分，使前向仅需一次 All-Reduce：

```
输入 X
  │
  ├─ Column Parallel → GeLU → Row Parallel → Y
  │                    (GPU 间无通信)        │
  └──────────────────────────────────────────┘
                              ↓
                         All-Reduce
```

**适用场景**：需要在 NVLink 域内（通常单节点 8 GPU），因为通信频繁且低延迟要求高。

**从零实现关键细节**（CS336 课程）：
- 列张量并行中，每个 rank 持有参数矩阵的一部分列，前向传播中对激活执行 All-Gather 汇聚完整输出
- 反向传播中，All-Gather 的对偶操作是 Reduce-Scatter：各 rank 的梯度分片需要规约后分发
- 这种 All-Gather（前向）↔ Reduce-Scatter（反向）的对偶性是张量并行的核心通信模式
- 标准 `loss.backward()` 不会自动处理这些通信，需手动管理或使用框架封装（如 Megatron-LM）

### 5.3 流水线并行（Pipeline Parallelism）

将模型的不同层分配到不同 GPU：

```
GPU 0: Layer 1-4
GPU 1: Layer 5-8
GPU 2: Layer 9-12
GPU 3: Layer 13-16
```

**朴素流水线的问题**：只有一个 batch 在流水线中，大部分 GPU 空闲（气泡）。

**GPipe 方案**：将 mini-batch 切分为 $M$ 个 micro-batch，依次填充流水线：

```
时间 →
GPU 0: [m1][m2][m3][m4] -- -- -- -- [m1][m2][m3][m4]  ← 反向
GPU 1: -- [m1][m2][m3][m4] -- -- [m1][m2][m3][m4] --
GPU 2: -- -- [m1][m2][m3][m4] [m1][m2][m3][m4] -- --
GPU 3: -- -- -- [m1][m2][m3][m4][m3][m2][m1] -- -- --
```

气泡比例：$\frac{K-1}{M+K-1}$，$K$ 为流水线级数，$M$ 为 micro-batch 数。

**1F1B 调度**（Megatron-LM）：交替执行前向和反向，减少激活值内存：

```
GPU 0: [F1][F2][F3][F4][B1][B2][B3][B4]...
```

**Interleaved 1F1B**：将每级分为多个虚拟级，进一步减少气泡。

**从零实现关键细节**（CS336 课程）：
- 流水线并行使用点对点通信（Send/Recv）而非集合通信
- 每个 rank 接收上一 rank 的激活，执行本地层前向，发送给下一 rank
- 朴素实现（单 micro-batch）会导致严重气泡：大部分 GPU 空闲等待
- Micro-batch 切分：将 batch 拆为 $M$ 个 micro-batch 依次填充流水线，减少气泡比例
- **计算-通信重叠**对流水线并行至关重要：使用异步 Send/Recv（`isend`/`irecv`），在计算当前 micro-batch 的同时收发下一个 micro-batch 的数据

**零气泡流水线（Zero Bubble Pipeline）**：

传统流水线调度中气泡不可避免。零气泡方案的关键洞察是：反向传播中实际上包含**两种不同操作**：

| 操作 | 说明 | 时间敏感性 |
|------|------|-----------|
| **B（Backward-Input）** | 将偏导数沿计算图往回传 | **关键**：信号没传回去，下一阶段无法工作 |
| **W（Backward-Weight）** | 计算当前层权重的梯度 | **不关键**：权重的导数是叶节点，随时可算 |

零气泡策略：**尽快执行 B，将 W 延迟到计算空隙**。通过将 B 和 W 拆分为独立操作，在流水线空隙中插入 W 计算，几乎完全消除气泡。具体效果取决于 B 和 W 各自的工作负载比例。

**流水线并行的通信优势**：
- 通信只涉及激活值（$B \times S \times H$），是点对点通信（层与层之间），而非全对全
- 数据量通常远小于传输整个参数矩阵
- 因此 PP 适合放在通信最慢的链路上（跨 Pod、跨数据中心）

**流水线并行的代价**：
- 性能高度依赖批次大小：需较大 batch size + 较大 pipeline size 才能维持高利用率
- 气泡比例随 pipeline stage 增加而增大，需要更多 micro-batch 来填充

### 5.4 序列并行（Sequence Parallelism）/ 上下文并行（Context Parallelism）

针对长序列场景，将序列维度切分到多个 GPU。**注意**："序列并行"这个名称有误导性，更准确的叫法是"上下文并行"。

**激活内存公式**（存储所有激活值时的经验公式）：

$$\text{Activation Memory} \approx 34 \times S \times B \times H + 5 \times a \times \frac{S^2}{H}$$

其中 $S$ = 序列长度，$B$ = batch size，$H$ = 隐藏层维度，$a$ = 注意力头数。

- 第一项（$34 \times SBH$）：来自 MLP 和注意力的线性层激活值，其中约 24 份是 MLP 部分
- 第二项（$5 \times aS^2/H$）：来自二次注意力项（包括 dropout 等），使用 Flash Attention 可通过重计算省掉此项

**各并行策略对激活内存的影响**：

| 策略 | MLP/注意力部分 | LayerNorm 等逐点操作 | 最终激活内存 |
|------|---------------|---------------------|-------------|
| 无并行 | $34 \times SBH$ | 不拆分 | $34 \times SBH$ |
| 张量并行（TP=$T$） | $\div T$（MLP+注意力可拆） | **不拆分**（仍为 $10 \times SBH$） | $\sim 34/T \times SBH + 10 \times SBH$ |
| 张量并行 + 序列并行 | $\div T$ | $\div T$（沿序列轴拆分） | $34/T \times SBH$ |
| 上述 + 激活重计算 | — | 省掉第二项 | $\approx \frac{34}{T} \times SBH$（**合理下限**） |

**序列并行的核心思路**（与 FSDP 类似）：
- 对 LayerNorm、Dropout 等计算量小的逐点操作，沿**序列轴**（而非隐藏轴）拆分存储
- 需要时通过 All-Gather（前向）/ Reduce-Scatter（反向）收集
- 前向 G 走 All-Gather、G 上走 Reduce-Scatter；反向互换——与 TP 的对偶关系一致

**主要方法**：
- **DeepSpeed Ulysses**：在注意力计算前后通过 All-to-All 通信在序列维度和注意力头维度间转换
- **Ring Attention / Context Parallelism**：KV 块在 GPU 间环形传递，无需完整加载序列。最早在 TPU 的环形网格拓扑上验证效果极佳

**适用场景**：超长上下文（100K+ tokens）训练与推理，突破单 GPU 显存限制。

**激活重计算的权衡**：
- Attention 的重计算开销较小（可按 tile 处理），通常值得做
- MLP 的重计算开销大（需在反向传播时再跑一遍 MLP），通常不想做
- 重计算省下的内存可转化为更大 batch size → 更好的 GPU 利用率（反直觉但有效）

### 5.5 专家并行（Expert Parallelism）

MoE 模型的标配策略，将不同专家分配到不同 GPU。本质类似于张量并行（都是拆分 MLP/FFN 组件），但有关键区别：

**EP vs TP 对比**（CS336 / Megatron-LM 并行指南）：

| 维度 | 张量并行（TP） | 专家并行（EP） |
|------|---------------|---------------|
| **拆分方式** | 将单个矩阵乘法按维度切分 | 将整个 FFN（专家）分配到不同设备 |
| **通信内容** | 密集且庞大的矩阵乘法激活值 | 稀疏的 token 路由激活值 |
| **GPU 利用率** | 矩阵切得太碎 → 维度变小 → 利用率下降 | token 精确路由到该去的专家，跳过不必要的计算 |
| **通信模式** | All-Gather / Reduce-Scatter | All-to-All（每次碰到 MoE 层都要路由 token） |
| **延迟敏感性** | 中等 | **高**：计算必须等 token 到达才能继续 |

**核心结论**：如果你在做 MoE，几乎总是应该优先选 EP 而非 TP（NVIDIA Megatron-LM 官方建议）。

**EP 的复杂性**：
- 每次碰到 MoE 层都需要大量 All-to-All 分发，延迟非常关键
- 负载不均衡：不同专家接收的 token 数量不均匀
- EP 并行度有上限——它是 DP 划分的一个子集，DP 的并行度限制了 EP 能达到的程度
- DeepSeek 开发了专门的库（DeepEP）用于高效专家并行路由，甚至挖掘了未公开的 PTX（GPU 机器码）指令来榨取性能
- NVIDIA 也有 HybridEP 库做类似的事

**EP 与其他策略的兼容性**：FSDP、PP、TP 在 MoE 模型中仍然适用，标准做法是将 TP 替换为 EP。

### 5.6 3D 并行

组合三种并行策略：

```
         ┌─────────────┐
         │ 数据并行 (DP) │  ← 最外层，跨节点
         ├─────────────┤
         │ 流水线并行(PP) │  ← 中间层，跨节点
         ├─────────────┤
         │ 张量并行 (TP) │  ← 最内层，NVLink 域内
         └─────────────┘
```

**典型配置**（175B 模型）：
- TP = 8（单节点 8 GPU，NVLink 互联）
- PP = 16（跨 16 个节点）
- DP = 4（4 路数据并行）
- 总计 512 GPU

### 5.7 ZeRO 与 FSDP

详见 [[07_大模型训练优化]]。ZeRO 将数据并行中的冗余状态（优化器状态、梯度、参数）分片，使数据并行也能训练超大模型。

**内存构成分析**：训练时需存储的内容远超参数本身——经验法则约需 5 份权重副本，每参数 16 字节。Adam 优化器需同时跟踪一阶矩和二阶矩（可能需高精度存储），这些**优化器状态**占内存大头，其次是梯度，最后是参数。

**ZeRO 三阶段详细工作流程**：

| 阶段 | 切分对象 | 通信操作 | 通信开销 | 内存节省 |
|------|---------|---------|---------|---------|
| **ZeRO-1** | 优化器状态 | Reduce-Scatter（梯度）+ All-Gather（参数） | 与朴素 DP 相同（= 1× All-Reduce） | 优化器状态 ÷ N |
| **ZeRO-2** | 优化器状态 + 梯度 | 逐层 Reduce-Scatter（梯度）+ All-Gather（参数） | 与朴素 DP 相同 | 优化器状态 + 梯度 ÷ N |
| **ZeRO-3 / FSDP** | 优化器状态 + 梯度 + 参数 | 2× All-Gather（前向+反向参数）+ 1× Reduce-Scatter（梯度） | 比朴素 DP 多一次 All-Gather | 全部 ÷ N |

**ZeRO-1 工作流程**：
1. 各 GPU 计算完整梯度
2. Reduce-Scatter：各 GPU 只接收自己负责参数块对应的梯度分片（通信量 = 1× 参数量）
3. 各 GPU 用本地优化器状态更新自己负责的参数块
4. All-Gather：将更新后的参数块广播给所有 GPU（通信量 = 1× 参数量）
5. 总通信量 = Reduce-Scatter + All-Gather = All-Reduce，与朴素 DDP 完全相同——**内存节省是"免费"的**

**ZeRO-2 关键技巧**：不再一次性物化完整梯度向量，而是沿计算图反向遍历时，算完某一层梯度后立即 Reduce-Scatter 发给对应工作节点，计算图不再需要时立刻释放——**边算边发**。

**ZeRO-3 / FSDP 工作流程**：
1. 前向传播：按需 All-Gather 收集当前层参数 → 计算 → 释放参数
2. 反向传播：All-Gather 收集当前层参数 → 计算梯度 → Reduce-Scatter 分发梯度 → 释放参数
3. 最后更新权重
4. 每层做 2 次 All-Gather + 1 次 Reduce-Scatter，但每层数据量小，可被计算重叠隐藏

**FSDP 计算-通信重叠**（关键性能优化）：
- 使用独立流（stream）：计算流 + 通信流并行执行
- 在计算第 $i$ 层前向时，同时对第 $i+1$ 层做 All-Gather 预取参数
- 只要计算耗时 ≥ 通信耗时，通信开销几乎完全隐藏
- FSDP 的 GPU 利用率可非常接近单卡性能

**ZeRO vs 模型并行**：
- ZeRO-3/FSDP 在数学上等价于一种特殊的模型并行 + 数据并行
- ZeRO 不改变计算图，实现更简单（只需包装器）
- ZeRO-3 的通信模式是 All-Gather + Reduce-Scatter，与张量并行的通信不同
- FSDP 的局限：不减少激活值内存；消耗全局批次大小资源

### 5.8 通信优化

| 技术 | 原理 | 效果 |
|------|------|------|
| 梯度压缩 | 量化/稀疏化梯度 | 减少通信量 4-8 倍 |
| 梯度累积 | 多步本地累积后同步 | 减少通信频率 |
| 通信-计算重叠 | 异步通信与计算并行 | 隐藏通信延迟 |
| 拓扑感知 | 根据 NVLink/InfiniBand 拓朴分配通信路径 | 提高带宽利用 |
| 1-bit Adam | 梯度符号化传输 | 通信量减少 32 倍 |

## 6. 并行策略选择指南

### 6.1 按模型规模的简化决策表

| 模型规模 | GPU 数 | 推荐策略 |
|---------|--------|---------|
| < 1B | 1-8 | DDP |
| 1B-10B | 8-64 | DDP / FSDP |
| 10B-70B | 64-512 | FSDP / 3D 并行 |
| 70B-175B | 512-2048 | 3D 并行 (TP+PP+DP) |
| 175B+ | 2048+ | 3D 并行 + ZeRO + 序列并行 |

### 6.2 CS336 简化决策规则（4D 并行）

CS336 课程给出的实用决策流程：

1. **模型放不进单 GPU → 切开**：用 TP 或 EP（针对高速互联，通常限制在 NVLink 域内 = 单节点 8 GPU）
2. **切完后还放不下 → 用 PP 或 ZeRO-3/FSDP** 塞进剩余层
3. **模型放得下后 → 剩余 GPU 全用 DP**
4. **batch size 太小 → 梯度累积** 提升利用率

**核心准则**：
- **能少用模型并行就少用**，尽量把 DP 拉满
- TP/EP 不要超出 NVLink 范围（单机箱）
- 跨节点扩展用 PP 或 FSDP
- 当 batch size 减小到 FSDP 遇到通信瓶颈时，叠加 TP/EP 将效率曲线外推

**Megatron-LM 的 MOE 并行指南**（同样适用于稠密模型，顺序相反）：
1. 优先用大部分 GPU 做 DP 分片
2. EP 和 TP 限制在 NVLink 域内
3. 跨节点用 PP

### 6.3 临界批次大小与效率曲线

**核心洞察**：只要计算耗时 ≥ 通信耗时，通信开销就能被计算重叠隐藏。

```
效率
 ↑
100%─┐───────────────────────────
     │ ╱ ╱ ╱ ╱ ╱ ╱ ← 计算受限区
     │╱╱╱╱╱╱╱╱╱╱╱
     │ ← 临界批次大小
     │ ← 通信受限区
     │
     └────────────────────────→ batch size
```

- batch size 够大时，纯 FSDP 表现极好，瓶颈完全在计算
- batch size 减小 → 遇到通信瓶颈 → 叠加 TP/MP 将效率曲线外推
- 这就是"4D 并行"的含义：DP + TP + PP + SP（或 EP）同时使用

**激活重计算的反直觉收益**：重计算多做计算 → 省内存 → 更大 batch size → 更好的 GPU 利用率

## 7. 优势与局限

### 优势

- 使超大模型训练成为可能（千亿/万亿参数）
- 数据并行线性扩展吞吐量
- 3D 并行充分利用硬件拓扑
- ZeRO/FSDP 降低实现复杂度

### 局限

- 通信开销随 GPU 数增加而增大
- 流水线并行存在气泡，GPU 利用率 < 100%
- 异步 SGD 可能因梯度陈旧影响收敛
- 实现复杂度高，调试困难
- 故障容错挑战：数千 GPU 中单个故障可能导致训练中断

## 10. 实际训练案例

CS336 课程结合公开细节，分析了几个近期大规模训练案例的并行策略配置：

| 模型 | 参数量 | 架构 | 并行策略 | 备注 |
|------|--------|------|---------|------|
| **OLMo** (AI2) | 7B | 稠密 | 纯 FSDP | FSDP 扩展性出奇好，~7B 参数纯靠 FSDP 训练 |
| **DeepSeek V1** | — | 稠密 | DP + TP + PP | 经典 3D 并行组合 |
| **DeepSeek V3** | — | MoE | DP + **EP(64路)** + PP | 用 EP 替代 TP；8 台机器为一组构成 EP 域；沿用 PP 技巧保证利用率；自研 DeepEP 库 |
| **Qwen** | — | MoE | ZeRO-1 + EP + PP | EP 效率稍高于 TP 的替代方案 |
| **Llama 3 405B** | 405B | 稠密 | TP=8 + SP=1 + PP=16 + DP=1280 | 稀有地完整披露并行配置的报告；长上下文扩展阶段拉高 SP、降低 DP |
| **Gemma 2** | — | 稠密 | FSDP + TP + SP | Google 的开源模型，用 FSDP 而非纯 TP |

**Llama 3 405B 细节**：
- 预训练主阶段：TP=8（NVLink 域）+ PP=16（跨节点）+ DP=1280（大规模数据并行）
- 长上下文扩展阶段：拉高上下文并行（SP），降低 DP——因为长上下文极度吃内存
- 是稠密模型，用 TP 而非 EP
- 训练过程中 GPU 故障了约 400 次，凸显大规模训练的容错挑战

**DeepSeek V3 细节**：
- 64 路 EP 是非常规的大规模专家并行，跨 8 台机器（每组 8 GPU × 8 = 64 设备）
- 沿用流水线并行中的调度技巧（如 1F1B）来保证 EP 不出现利用率低谷
- 自研 DeepEP 库，甚至挖掘未公开的 PTX 指令来优化 All-to-All 路由延迟

**关键启示**：
1. 小模型（~7B）纯 FSDP 足够，扩展性极好
2. 超大稠密模型用经典 3D 并行（TP + PP + DP），Llama 3 是最佳参考
3. MoE 模型将 TP 替换为 EP，其余策略不变
4. 长上下文训练需要 SP/CP，以 DP 缩减为代价
5. 大规模训练中 GPU 故障是常态，需要冗余和容错机制

## 11. 前沿发展

- **Ring Attention / Blockwise Ring Attention**：超长序列分布式注意力
- **零气泡流水线**：分离 B/W 操作几乎完全消除气泡（§5.3）
- **异构训练**：CPU+GPU+TPU 混合训练
- **弹性训练**：GPU 动态加入/退出，支持抢占式云实例
- **去中心化训练**：跨数据中心训练，应对网络延迟
- **通信压缩**：1-bit Adam、PowerSGD、DeepComp 等梯度压缩方法
- **自动并行**：Alpa、Unity 等自动搜索最优并行策略
- **专用 EP 库**：DeepEP（DeepSeek）、HybridEP（NVIDIA）等针对 MoE All-to-All 路由优化的底层库
- **4D/5D 并行**：DP + TP + PP + SP + EP 的全策略组合，在最大规模训练中已成标配
