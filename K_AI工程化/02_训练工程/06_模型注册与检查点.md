# 模型注册与检查点

## 一句话理解

检查点是训练过程的可恢复快照，模型注册表是可发布模型的受控版本目录；两者共同构成从训练产出到安全发布的质量保障链条。

## 概述

训练过程中产生的模型权重如果不做版本管理，就无法回答"这个模型用了什么数据训练的""上线版本和上一版有什么区别""能否回滚到上一个稳定版本"等基本问题。模型注册表是 MLOps 中连接训练和部署的关键组件。

本笔记回答的核心问题：
- 检查点应保存什么内容？如何管理？
- 模型注册表应记录哪些元数据？
- 从训练检查点到可发布模型需要经过什么流程？

## 发展历史

| 时间 | 里程碑 | 意义 |
|---|---|---|
| 2015 | DVC 早期版本 | 数据和模型版本管理 |

| 2022+ | 企业级 Model Registry | 多团队协作的模型治理 |

## 核心概念

### 检查点 vs 模型注册

| 维度 | 训练检查点 | 模型注册版本 |
|---|---|---|
| 目的 | 训练恢复和实验复现 | 生产发布和版本管理 |
| 状态 | 开发中 | 已审核、已批准 |
| 生命周期 | 短期（训练结束后可清理） | 长期（需长期保存） |
| 完整度 | 包含优化器状态、调度器状态等 | 仅模型权重 + 配置 |
| 变更性 | 可覆盖、可删除 | 不可变（Immutable） |

### 模型版本状态机

```
开发中 (Development) → 候选 (Staging) → 生产 (Production) → 归档 (Archived) → 废弃 (Deprecated)
```

每个状态转换需要审批和记录。

## 技术原理

### 检查点内容

一个完整的训练检查点必须包含：

| 类别 | 内容 | 用途 |
|---|---|---|
| 模型状态 | 权重（所有分片） | 恢复模型 |
| 优化器状态 | Adam 动量和方差（FP32） | 恢复优化器 |
| 调度器状态 | 当前学习率、步数 | 恢复学习率调度 |
| 数据状态 | 数据游标、epoch 计数 | 恢复数据读取位置 |
| 随机状态 | RNG 种子 | 恢复随机性 |
| 拓扑状态 | 并行配置（TP/PP/DP 分组） | 恢复并行拓扑 |
| 元数据 | 代码版本、配置文件、训练指标 | 可追溯性 |

### 检查点格式

| 格式 | 说明 | 适用场景 |
|---|---|---|
| PyTorch `.pt` | pickle 序列化 | 简单场景 |
| Safetensors | 无 pickle，安全加载 | 推荐格式 |
| 分布式分片 | 每卡保存自己的分片 | ZeRO-3 / FSDP |
| 统一分片格式 | 如 Megatron 格式 | 跨拓扑恢复 |

### 模型注册表元数据

每个注册版本应记录：

```
模型名称 + 版本号
├── 权重 URI（不可变）
├── 架构配置
│   ├── 模型类型（GPT、LLaMA 等）
│   ├── 参数配置（层数、维度、头数等）
│   └── Tokenizer 配置
├── 血缘信息
│   ├── 训练数据版本与 manifest
│   ├── 代码版本（commit hash）
│   ├── 配置文件版本
│   └── 基础模型（如果是微调）
├── 评测报告
│   ├── Benchmark 分数
│   ├── 安全评测结果
│   └── 人工评测结果
├── 合规信息
│   ├── 许可证
│   ├── 安全限制
│   └── 审批记录
└── 状态信息
    ├── 当前状态（开发/候选/生产/归档）
    ├── 创建时间与创建者
    └── 变更历史
```

### 发布流程

```
训练完成 → 保存检查点 → 转换为推理格式 → 评测通过 → 注册为候选版本 
→ 审批通过 → 升级为生产版本 → 通知部署系统
```

关键原则：
- 发布服务只能引用已批准的不可变版本
- 回滚应指向已验证的前一版本，而非临时训练产物
- 版本号应语义化，便于追溯

## 关键方法与模型

### 主流工具

| 工具 | 定位 | 特点 |
|---|---|---|
| MLflow Model Registry | 通用模型注册 | 开源、框架无关 |
| Hugging Face Hub | 模型分发 | 开源社区标准 |
| W&B Artifacts | 实验平台集成 | 与训练追踪深度集成 |
| Vertex AI Model Registry | 云平台 | GCP 生态 |
| 自建注册表 | 企业定制 | 可定制审批流程和合规要求 |

### Safetensors 格式

Hugging Face 推出的安全模型序列化格式：

- 无 pickle 反序列化，避免代码执行风险
- 零拷贝加载（mmap）
- 支持张量级别的惰性加载
- 已成为 Hugging Face 默认格式

## 优势与局限

### 优势

- 版本可追溯，任何模型可追溯到训练数据和代码
- 回滚安全，始终有验证过的历史版本
- 审批流程保证发布质量

### 局限

- 大模型检查点体积巨大（175B 模型约 700GB），存储和传输成本高
- 跨框架格式转换可能损失信息
- 元数据管理容易被忽视

## 应用场景

- 预训练：定期保存检查点，最终版本注册
- 微调：每个微调实验产出一个注册版本
- A/B 测试：不同版本同时部署对比效果
- 合规审计：追溯任何上线模型的训练来源

## 前沿发展

- **增量检查点**：只保存变化部分，减少存储和 I/O
- **模型指纹**：用哈希值快速验证模型一致性
- **自动评测流水线**：注册后自动触发评测和审批
- **模型卡（Model Card）标准化**：结构化记录模型能力和限制

## 常见问题

- **检查点应该保留多久？**：训练期间保留最近 N 个；训练结束后保留最终检查点和关键里程碑检查点。中间检查点可在训练稳定后清理。
- **如何处理跨框架格式转换？**：保存为 Safetensors 等统一格式。从 ZeRO-3 分片格式转换为统一格式需要专门的转换工具。
- **模型注册表和 Git 有什么区别？**：Git 管理代码版本，注册表管理大文件（模型权重）及其元数据。两者互补，注册表记录代码 commit hash 但不替代代码版本管理。
